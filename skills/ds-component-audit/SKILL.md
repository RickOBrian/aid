# DS Component Audit — v1.1.0

Принимает screenshot или Figma-ссылку и определяет, есть ли уже такой
компонент в системе (Match), нужно ли завести новый (New), неясно ли это
(Ambiguous), или вход вообще не компонент дизайн-системы (Not a DS
component). Спецификацию не пишет — только идентичность и вердикт.

---

## Активация — строго по команде

Skill запускается **только** по явной команде `/audit_component`.

- Команда без вложения (screenshot или Figma-ссылка) → попроси прикрепить
  вложение и жди. Не запускай логику вердикта без него.
- Screenshot или Figma-ссылка, приложенные **без** команды
  `/audit_component` → не интерпретируются как запрос на аудит, skill не
  запускается сам по себе.
- Общие фразы вида «проверь компонент», «это уже есть в системе?» без
  явной команды — не триггер. Попроси использовать `/audit_component`.

## Шаг 1. Прими вход, определи технический статус

Зафиксируй: `source: screenshot | figma`; для `figma` дополнительно
`source_type: frame | component_instance` (ссылка на весь экран/секцию
даёт менее надёжный вердикт, чем ссылка на именованный компонент).

Если вход нечитаем/недоступен (битый скрин, недоступная Figma-ссылка,
нечитаемое изображение) → вердикт **"Cannot analyze input"** с причиной.
Останови обработку здесь. Не путай с Ambiguous.

---

## Шаг 2. Определи платформу(ы)

Предположи платформу(ы) по визуальным паттернам (нативные контролы,
типографика, safe area). Покажи предположение мне для подтверждения.
Множественный выбор: `Web`, `iOS`, `Android`, либо «не удалось
определить». Не угадывай молча при неочевидности.

---

## Шаг 3. Определи тип кадра

- **Единый композитный виджет** (Structural View, композиция вложенных
  частей осмысленна как целое) → вердикт по виджету целиком. Вложенные
  компоненты — как «составные части», без отдельного полного вердикта по
  каждой, если уже описаны в системе.
- **Несколько независимых компонентов** случайно в одном кадре → разложи
  на части, вердикт по каждой отдельно.
- **Неочевидно** → явно спроси меня, не решай сам.

Компонент явно микро-уровня (Item / простой Surface View без вариантов и
состояний — Dot, Icon, простая Divider-линия) → можно пропустить
неприменимые шаги (например, Шаг 6). Пропуск проговаривай одной строкой:
«шаг N пропущен — компонент не имеет вариантов/состояний».

---

## Шаг 4. Сопоставь с системой — Match / New / Ambiguous / Not a DS component

Сравнивай по роли и составу, не только по внешнему виду. Базой известных
компонентов считай `docs/storybook/components/*.html` и записи из
`memory/ds-component-spec/log.*.json` / `memory/ds-component-audit/log.*.json`.

**Порог для New — высокий.** При сомнении дефолт — **Ambiguous**, не New.

**Not a DS component:** если вход в принципе не имеет смысла
сопоставлять с системой (случайный скрин, сторонний сайт, нерелевантный
кроп) → явный отдельный вердикт **"Not a DS component"** с кратким
объяснением, без предложения что-либо создать/дополнить.
Не путай с Ambiguous: Ambiguous — похоже на что-то существующее, но
неясно, на что конкретно; "Not a DS component" — сопоставлять с системой
не имеет смысла в принципе.

**Два близких кандидата с близкой confidence** (например, похоже и на
Badge, и на Chip) — двухшаговая проверка:
1. Прежде чем выбирать между ними — оцени, не третий ли это,
   не описанный компонент со своей ролью, просто визуально похожий на
   оба (общая форма/размер). Если оснований для New достаточно (порог
   выше) → вердикт **New**; оба похожих компонента — «визуально близкие
   для сравнения», не конкурирующие Match-кандидаты.
2. Если New не подтверждается → покажи оба кандидата с confidence и
   коротким обоснованием отличия. Финальный выбор — за мной: явно
   предложи `существующий A` / `существующий B` / `третий, новый`.
   Не решай сам. Вердикт для Шага 10 в этом случае — **Ambiguous**
   (оба кандидата — конкурирующие Match, единственно верный не выбран).

**Platform scope extension:** если Match указывает на компонент с
ограниченным набором платформ в спеке, а вход показывает ту же роль на
платформе, которой в спеке ещё нет → отдельный вердикт **"Platform scope
extension"**, не «новое состояние»/«новый вариант» (Шаг 6). Проверь явно:
совпадает ли семантическая роль на новой платформе с уже описанной, или
под тем же именем скрывается разное поведение — расхождение проговаривай
явно. Параметры новой платформы фиксируются отдельно от существующих
platform-specific данных, без перезаписи.

**Legacy-проверка:** если Match указывает на компонент со статусом
Legacy — явно предупреди «это Legacy, предназначен на замену», вместо
тихого предложения дополнить устаревшую сущность.

**Variant/state vs new composite:** при частичном совпадении (похоже на
существующий + один новый элемент) — явно реши: дополнение того же
уровня архитектуры или новый Structural View, оборачивающий существующий
Surface View. Не выбирай автоматически «дополнить» без этой проверки.

---

## Шаг 5. Naming collision (только при вердикте New)

Проверь имя не только на смысловое совпадение с ролью, но и на конфликт
нейминга с существующими компонентами по всей системе
(`docs/storybook/components/*.html`, `memory/ds-component-spec/log.*.json`).
При конфликте — предложи альтернативу с явной причиной.

---

## Шаг 6. State vs Variant (только при Match с дополнением)

Явно укажи, что обнаружено — **новое состояние** или **новый вариант** —
с обоснованием. Не используй общее «дополнить компонент» без разделения.

---

## Шаг 7. Cross-check с ds-component-spec

Перед финальным вердиктом сверься не только с `memory/ds-component-audit/log.*.json`,
но и с `memory/ds-component-spec/log.*.json`. Если там уже есть
`open_questions` или записи по этому же компоненту — упомяни явно в
выводе, не игнорируй как отдельную базу.

---

## Шаг 8. Проверь память на повторный вход

Ищи в `memory/ds-component-audit/log.*.json` совпадения с текущим входом
(по имени компонента / визуальному сходству):

- **`status: rejected`** — не предлагай повторно без явно новых
  оснований (новый источник, другая платформа, изменённый визуальный
  признак). Без новых оснований — сошлись на прошлый rejected-вердикт.
- **`status: approved`** — считай **Match с высокой confidence**, сославшись
  на прошлое решение (id записи, дата).
- **`status: proposed`** — трактуй как открытый вопрос; при совпадении
  упомяни, что уже есть непринятое предложение по этому компоненту.

---

## Шаг 9. Дедупликация при нескольких входах за раз

- Входы, распознанные как один и тот же компонент → объедини в **одно**
  предложение, но внутри перечисли все отличия по каждому входу
  (состояние/вариант/платформа/источник) — без усреднения.
- Если хотя бы один вход батча даёт другой вердикт (например, 4 скрина →
  Match с Badge, пятый → Ambiguous/New) — вынеси его в отдельное
  предложение, не подгоняй под большинство.
- Смешанные источники (screenshot + Figma) внутри объединённого
  предложения — явно указывай `source` для каждого элемента.
- Неочевидно, один ли это компонент → не группируй автоматически,
  спроси меня перед объединением.

---

## Шаг 10. Выдай вердикт

ALWAYS use this exact structure. Each section is mandatory unless marked
optional. Компактный вывод для простых однозначных случаев (высокий
confidence, нет конфликтов, нет пересечений с Legacy/platform scope) —
секцию «Подробности» и «Пропущенные проверки» можно свести к «нет».
Разворачивай «Подробности» при Legacy-предупреждении, platform scope
conflict, конкурирующих Match-кандидатах, вердикте New (naming collision)
или Ambiguous (все кандидаты с confidence).

    # Аудит: [краткое описание входа]
    Источник: [screenshot | figma] [/ source_type: frame | component_instance]
    Платформа(ы): [Web / iOS / Android / не удалось определить] (confidence платформы: ...)

    ## Вердикт: [Match / New / Ambiguous / Not a DS component / Cannot analyze input / Platform scope extension]
    Компонент: [имя, если применимо]
    Confidence: [high / medium / low]
    Обоснование: [одна строка]

    ## Состав предложения (только для объединённых по Шагу 9 батчей — иначе не показывай секцию)
    - [source: screenshot|figma] — [состояние/вариант/платформа этого конкретного входа] — [что отличается от других входов группы]
    - [повторить построчно для каждого входа группы, без усреднения]

    ## Подробности
    нет / [что применимо из: Legacy-предупреждение, Platform scope conflict,
    конкурирующие кандидаты с confidence, Naming collision, State vs Variant,
    Cross-check со spec-логом, совпадение с прошлым аудитом (status + ссылка)]

    ## Пропущенные проверки
    нет / [шаг N пропущен — причина]

    ## Следующий шаг
    [например: «Согласуй вердикт → зафиксирую в памяти и подготовлю
    structured handoff для ds-component-spec (запускается отдельно)»]

Для батча из нескольких входов — повтори секцию «Вердикт» для каждого
предложения, оставшегося после дедупликации (Шаг 9). Не смешивай их.

## Structured handoff в ds-component-spec

После согласования вердикта со мной сформируй handoff-блок с полями,
совместимыми по формату с `memory/ds-component-spec/log`
(`id`, `component`/`level`/`platforms`/`stage`/`open_questions`/`missing_tokens`):

```json
{
  "component": "[ComponentName]",
  "level": "[item | surface-view | structural-view | layout | требует уточнения]",
  "category": "[из component-categories-guide.md, если применимо]",
  "verdict": "[match | new | ambiguous | not-a-ds-component | platform-scope-extension]",
  "confidence": "[high | medium | low]",
  "platforms": ["web", "ios", "android"],
  "source": "screenshot | figma"
}
```

Не запускай `ds-component-spec` автоматически — это отдельное явное
действие с моей стороны, не продолжение сразу после вердикта аудита.

## Встроенные правила уровней

*Используются только если `skills/_shared/ds-component-architecture-guide.md` не найден.*

- **Item** — только контент, без фона/формы/отступов (Icon, Dot, Text).
- **Surface View** — один основной контент-элемент в оболочке (фон +
  форма + отступы), максимум один вспомогательный элемент без
  именованного слота (Badge, ButtonIcon, Chip).
- **Structural View** — два и более именованных слота (ListRow,
  WidgetBalance, FieldSearch).
- **Layout** — только расстановка, без своего дизайна (VStack, Grid).

Если уровень неочевиден — говори явно, не угадывай.

## Память

Файл: `memory/ds-component-audit/log.<имя>.json`
Имя берётся из `.claude/intake-user`.

Формат одной записи:

```json
{
  "id": "audit-001",
  "component": "BadgeStatus",
  "verdict": "match",
  "level": "surface-view",
  "category": "indicators",
  "confidence": "high",
  "platforms": ["web"],
  "source": "screenshot",
  "source_type": null,
  "status": "approved",
  "date": "2026-07-03",
  "notes": "",
  "_owner": "sergej"
}
```

Поле `status`:
- `proposed` — вердикт предложен, ещё не согласован со мной
- `approved` — согласовано, финальное решение
- `rejected` — отклонено, нужны новые основания для повторного предложения

**После каждого согласованного аудита:**
1. Добавь/обнови запись в файле памяти со статусом `approved` или `rejected`.
2. Синхронизируй по командам из `skills/_shared/git-workflow.md`.
   Если файл недоступен — используй встроенные команды:

```bash
git pull --rebase
git add memory/ds-component-audit/log.<имя>.json
git commit -m "audit([ComponentName]): [match|new|ambiguous] verdict"
git push
```

**Если среда не сохраняет файлы между сессиями** — предупреди один раз:
«Память не переживёт этот чат. Сохрани вердикт вручную.»

**При следующем запуске** читай все `memory/ds-component-audit/log.*.json` — см. Шаг 8.

## Тон

Каждый вердикт — с явным confidence и обоснованием, не только вывод.
Неочевидные уровень архитектуры, платформа или тип кадра — проговаривай
явно, не угадывай молча. Недоступный внешний инструмент (Figma MCP) —
говори явно, предлагай ручной путь. Финальное решение в неоднозначных
случаях (двойной Match, дедупликация, тип кадра) — всегда за Principal
Designer, не за skill.
