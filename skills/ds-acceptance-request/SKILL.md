# Запрос приёмки

Задача standards-19 / AID-98 (issue #604). Слово PD 2026-11-25 «Да, все»
на список скиллов из разбора чатов. Протокол — `figma-library-workflow`
0.10.0: приёмка аудита §3.1 и §3.4 (этап 4), приёмка сборки §3.8 (этап 7).

Зачем: запросы приходили в разном виде — где-то без id набора, где-то
без PR, решения PD пересказом, must после правок без узлов. Standards
тратил время на сбор, а не на проверку. Скилл только собирает текст:
в Figma и репозитории он ничего не меняет, кроме pending-JSON своей
задачи (шаг 1).

---

## 1. Когда и кому

| Вид | Когда | Что просят |
|---|---|---|
| `audit` | Аудит готов, блок 8 разобран с куратором | Принять аудит (§3.1, §3.4) |
| `construction` | Сборка готова: компонент, гайд 1–8, 10, 11, Changelog | Принять сборку (§3.8) |
| `recheck` | Вердикт «принять после правок», правки внесены | Перепроверить только названные must |

Получатель — Standards. Компоненты и служебные страницы Persefona —
Standards · Persefona (`docs/hub/agents/standards.md`).

Один запрос — один компонент и один вид. Исключение: сборку начали по
слову PD до вердикта аудита — тогда аудит и сборка одним запросом, двумя
разделами, вердикт будет один.

**Запрос не отправляется**, если:

- скилл `ds-component-check` не прогнан на текущем состоянии пейджа или
  в его отчёте есть must без принятого отклонения;
- pending-JSON задачи нет в PR или в нём нет id узлов (раздел 3);
- PR не открыт. CI может идти — тогда так и написать.

---

## 2. Порядок

**Шаг 1. Pending-JSON.** Открыть `changes/<продукт>/pending/<id>.json`
задачи и дописать то, чего не хватает для запроса (раздел 3). Pending —
единственный источник id: узел, которого нет в pending, в запрос не
попадает, его сначала дописывают в pending тем же PR. Запись должна
проходить схему `skills/_shared/schemas/pending-item.schema.json`; когда
Штаб подключит схему в `scripts/check-docs.mjs`, это проверит CI.

**Шаг 2. Проверка.** Прогнать `ds-component-check` подагентом с чистым
контекстом (его раздел 6). Если после последнего прогона Figma не
менялась — приложить тот отчёт. Для `recheck` прогон тоже обязателен:
правка одного места ломает соседнее (клонирование вариантов сбрасывает
привязки).

**Шаг 3. Решения.** Выписать решения PD и куратора из `decisions`
pending-JSON и блока 8 — дословно, с датой и автором. Пересказ вместо
цитаты не годится. Цитаты нет — написать «цитаты нет, решение из <где>».

**Шаг 4. Текст.** Собрать по шаблону раздела 4. Пустой раздел — «нет»,
не пропускать: Standards должен видеть, что пункт не забыт.

**Шаг 5. Отправка.** Текст — в чат Standards (или Standards · Persefona)
по правилам карточки роли (`docs/hub/agents/designer.md`). Штабу — не
писать: приёмка идёт напрямую. В issue и PR запрос не дублировать.

## 3. Что нужно в pending-JSON

Поля по схеме `pending-item.schema.json`. Для запроса — обязательно:

| Поле | Что | Пример |
|---|---|---|
| `taskKey`, `issue`, `task` | Задача на доске | `AID-95`, `598`, `designer-34` |
| `pr` | PR с этой записью | `611` |
| `taskType`, `currentVersion`, `proposedVersion`, `proposedSemVerImpact` | Тип задачи и версия (§3.3) | `create`, `null`, `1.0.0`, `initial` |
| `figma.fileKey` | Библиотека | `79UryRdexwKAv8vDIV5v4v` |
| `figma.auditPage`, `figma.auditSection`, `figma.auditBlocks` | Пейдж аудита (до переноса в `Archive`), секция, блоки `cover`, `0`…`8` | `2341:2`, `2341:6635` |
| `figma.auditPrototypes` | Прототипы аудита | `{".Route Row · audit": "2341:95"}` |
| `figma.constructionPage`, `figma.components`, `figma.componentKey` | Сборка: пейдж, набор или мастер, ключ | `2349:8766`, `{"Switch": "2349:8768"}` |
| `figma.guide`, `figma.guideBlocks`, `figma.changelogSection` | Сборка: гайд, блоки `cover`, `1`…`8`, `10`, `11`, Changelog | `2349:8795`, `2349:9237` |
| `figma.input` | Вход задачи | `{"fileKey": "…", "node": "7734:232693"}` |
| `decisions` | Решения дословно: `date`, `by`, `quote` | см. `component-route-row` |
| `openQuestions` | Открытые вопросы — строкой, с блоком | «Линия маршрута а/б (блок 7, вопрос 2)» |

После переноса аудита в `Archive` на этапе сборки `figma.auditPage` —
`null`: пейдж удалён, id секции остаётся прежним (§3.1 п.6, решение PD
2026-11-26).

## 5. Правила

1. Id — только из pending-JSON и из Figma этого прогона, не из памяти
   чата: узлы переезжают при переносе аудита, после клонирования
   меняются id вариантов.
2. Решения — дословно. Пересказ решения PD в запросе Standards примет за
   цитату.
3. Отход от стандарта без записи — не отклонение, а нарушение: сначала
   вопрос Standards (§3.4), потом запрос.
4. `recheck` — только must вердикта и что с ними сделано. Should, на
   которые ответили правкой, — одной строкой. Новое, чего не было в
   вердикте, — отдельным разделом «Сверх вердикта»: Standards проверит и
   его.
5. Тексты на пейдже — рыба, не боевые (`ds-component-check` §4.4 п.1):
   если отчёт проверки это отметил, должно быть исправлено до запроса.
6. Запрос — не место для новых вопросов к PD. Вопрос к PD — через
   куратора, в запросе — только его статус в «Открытых вопросах».
