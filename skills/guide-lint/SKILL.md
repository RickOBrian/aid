## Контекст окружения

Читай перед запуском:
- `skills/_shared/semantic-color-tokens-guide.md` — эталон структуры
- `skills/_shared/token-rules.md` — правила токенов и нотации
- `.claude/space-context.md` — терминология, принятые решения
- `.claude/git-workflow.md` — правила коммитов

## Параметры запуска

Пользователь может указать:
- `все` или без уточнения → аудировать все `*-guide.md` в `skills/_shared/`
- `имя-файла.md` → только этот файл
- `--dry-run` → только отчёт, без исправлений и коммитов
- `--auto` → исправить всё без дополнительных вопросов

Если параметр не указан — работать в интерактивном режиме (шаг 4).

## Шаг 1. Прочитай эталон

Открой `semantic-color-tokens-guide.md`.
Зафикси для себя:
- порядок полей в frontmatter
- формат заголовка и строки статуса
- нумерацию разделов
- оформление таблиц (выравнивание пробелами)
- формат Changelog

## Шаг 2. Проверь каждый файл по чеклисту

FRONTMATTER:
- [ ] `destination` — первое поле
- [ ] `name` — совпадает с именем файла без расширения
- [ ] `metadata.version` — semver
- [ ] `metadata.platforms` — массив `[web, ios, android]`
- [ ] `metadata.owner` присутствует
- [ ] `description` — многострочный (`>`), на русском

СТРУКТУРА:
- [ ] Заголовок h1: `# Название гайда`
- [ ] Строка статуса сразу после h1: `> Статус: Draft|Stable · vX.X.X`
- [ ] Горизонтальный разделитель `---` после строки статуса
- [ ] Все разделы нумерованы: `## 1.`, `## 2.` и т.д.
- [ ] Нет заголовков h4 и ниже (максимум h3)
- [ ] Раздел Changelog присутствует и является последним разделом
- [ ] Каждая запись Changelog: `- **X.X.X** — описание`

СТИЛЬ:
- [ ] Таблицы выровнены пробелами (не минимальный pipe-синтаксис)
- [ ] Токены в тексте и коде: дефисная нотация (`bg-accent-main`, не `bg.accent.main`)
- [ ] Нет HTML-тегов в тексте гайда
- [ ] Блоки кода имеют явный язык (` ```swift `, ` ```kotlin `, ` ```tsx `, ` ```json `)

ЗАПРЕЩЕНО ТРОГАТЬ при исправлении:
- Текст внутри разделов (содержимое, объяснения, примеры)
- Примеры токенов и их значения
- Существующие записи в Changelog
- Любые данные в таблицах (только выравнивание разрешено)

## Шаг 3. Выведи отчёт

ALWAYS use this exact structure:

    ## Отчёт guide-lint

    ### [имя-файла.md] · текущая версия vX.X.X
    | Пункт                        | Статус | Комментарий |
    |------------------------------|--------|-------------|
    | destination первым полем     | ✅/❌  | ...         |

    **Итого по файлу:** X ошибок, Y предупреждений

    ---
    ### Сводка
    | Файл | Ошибок | Предупреждений | Требует исправления |
    |------|--------|----------------|---------------------|
    | ...  | ...    | ...            | да/нет              |

## Шаг 4. Подтверждение (только в интерактивном режиме)

Спроси одной строкой:
«Исправить: [все] / [имя файла] / [пропустить] / [--dry-run завершён]»

В режиме `--auto` этот шаг пропускается.

## Шаг 5. Исправь файлы

Для каждого файла с ошибками:
1. Исправь только пункты из чеклиста
2. Добавь patch-bump к `metadata.version` (`1.2.0` → `1.2.1`)
3. Добавь в Changelog новую запись первой строкой:
   `- **X.X.X** — guide-lint: нормализация структуры и оформления`
4. Сохрани файл

## Шаг 6. Коммиты

После исправления каждого файла — отдельный коммит по `git-workflow.md`:

```
chore(guide-lint): normalize [имя-файла] → vX.X.X
```

Не объединяй несколько файлов в один коммит.
