# Бриф пейджа аудита и сборки

Задача standards-18 / AID-97 (issue #603). Слово PD 2026-11-25 «Да, все» на
список кандидатов-скиллов из разбора чатов.

Сейчас каждый чат пишет бриф подагенту на пейдж сам, и от брифа к брифу
теряются одни и те же правила: ночь, 360, рыба, привязки, TagMarker. Скилл —
одно место, откуда бриф берётся целиком. Designer (или Штаб) заполняет вход
(раздел 1), вставляет шаблон (раздел 7) в Agent и получает пейдж и отчёт с
id узлов. Решения по существу — не у подагента: он собирает то, что уже
договорено, а пробелы приносит списком.

**Версия протокола — фиксирована:** скилл сверен с `figma-library-workflow`
0.10.0 (аудит при сборке — сразу в `Archive`, решение PD 2026-11-26). Блоки, их номера и имена — только из таблиц
протокола §3.1 п.4 и §3.8 п.4; здесь — как их собрать в Figma. Новая
версия протокола — новая версия скилла.

Пара скиллов:

| Шаг | Скилл | Кто |
|---|---|---|
| Собрать пейдж | `ds-figma-page-brief` (этот) | подагент по брифу |
| Проверить перед приёмкой | `ds-component-check` | другой подагент, с чистым контекстом |
| Принять | приёмка Standards (протокол §3.4, §3.8 этап 7) | Standards |

Сборщик пейджа свой пейдж не проверяет — это делает `ds-component-check`.

## 1. Вход

Бриф без этих строк не запускать: подагент додумает, а додуманное
приходит на приёмку как must.

| Что | Аудит | Сборка | Откуда |
|---|---|---|---|
| Режим | `audit` | `construction` | — |
| Продукт и `fileKey` библиотеки | да | да | `products/<id>/product.json`, `figmaFiles` |
| Компонент — имя по `naming-conventions` §4, как мастер | да | да | предаудит, ответ Standards на запрос имени |
| Задача: AID-номер, issue, PR (pending) | да | да | доска `docs/hub/BOARD.md` |
| Тип задачи и предложенная версия | да | да | pending `changes/<продукт>/pending/component-<slug>.json` (протокол §3.3) |
| Вход: id экземпляра в макете (не мастер), скрин или текст | да | — | вход PD (протокол §2) |
| Предаудит: что договорено, кто хозяин открытых вопросов | да | — | файл предаудита |
| Решения приёмки аудита: блок 8 со статусом «Принято» | — | да | пейдж аудита, чат приёмки |
| id пейджа `👀 · audit` и его секции; id пейджа `Archive` | — | да | для переноса аудита в `Archive` |
| Старая версия компонента (ключ, id) | если есть | если есть | для «было» и таблицы замены (§3.9) |
| Превью анимации в Presentbook | — | если есть анимация | PR превью (`persefona-figma-pages` §6.9) |
| Принятые отклонения и литералы | если есть | если есть | блок 8, записи исключений, описание мастера |

Пустая строка «Решения» — тоже вход: подагент пишет «нет» и всё спорное
выносит в блок 8 (аудит) или в отчёт (сборка).

## 2. Обязательное — вшито в бриф

Каждый пункт — с нормой. Нарушение любого — must на приёмке.

**Работа с Figma**

1. Перед первым `use_figma` загрузить скилл `figma:figma-use` (в
   `skillNames` — `figma-use`). Правки — только `use_figma`; смотреть —
   `get_screenshot`, `get_metadata`.
2. Править только свой пейдж. Чужие пейджи, мастера других компонентов,
   библиотеки токенов и иконок, комментарии Figma — не трогать.
   Публикация, версия в таблице чейнжлога, удаление пейджей — не
   подагента (протокол §3.2, `release-gate`).
3. После каждого блока — `get_screenshot` этого блока и сверка с
   задуманным: текст не вылез, ночь видна, экземпляры не потеряли
   подписи. Скриншот, а не структура слоёв (`WORKING-RULES` §7).
4. В отчёт — id каждого созданного или перемещённого узла (раздел 6).

**Вид — Kit Persefona** (`persefona-figma-pages` §6.6)

5. Шапка — `HeaderPage`, одна на пейдж; секции — `HeaderSection`;
   карточки — `IslandBlock`; таблицы — `TableCell`; статусы — `Badge`;
   пометки — `Banner`; схемы анатомии — `TagMarker`; сцены продукта —
   `IslandExample`. Вне сцены — только переменные и стили Kit, без
   `neutral-x/-y` и сырых значений.
6. Чего в Kit нет — не собирать молча: lookup по Kit, фреймом из
   переменных Kit до решения, строка в отчёт «нужен компонент Kit»
   (§6.6, «Чего в Kit нет»).
7. Содержимое — в секциях; узлы внутри рамки своей секции, секции не
   пересекаются, зазор 80; вырос блок — подогнать секцию и сдвинуть
   соседей в той же правке (§6.3). Фон секции — `bg-surface-main`.
8. Ссылка на другое место — гиперссылкой на узел, `text-accent-vivid` и
   `→` перед текстом; не «см. пейдж X» (§6.3, §6.6).

**Содержимое**

9. **Две темы.** Каждый пример — днём и ночью, режимом переменных на
   экземпляре, не перекраской; ночь — на тёмной сцене (протокол §3.1 п.3,
   §3.8 п.3; `persefona-figma-pages` §6.3).
10. **Вьюпорт 360** — минимальный; 320 и меньше не использовать.
11. **Токены.** Цвет, отступ, радиус, размер — переменными продукта;
    текст — стилем. В аудите новый визуал — хексом-допущением с пометкой
    (протокол §3.5); в сборке хексов нет. Хекс у тона `Custom` — не
    нарушение. Нет токена — не подбирать «похожий»: строка в отчёт
    (пробелы одной анкетой, `token-integrity`).
12. **Действующие имена токенов** в текстах и подписях: без `Pastel/*`,
    `Tint/*` (с 2.0.0 — `Background/* Tint`), `Line/*`, `text icon/*`.
    Историческое «было» — с пометкой.
13. **Рыба в примерах.** «Заголовок статуса», «Описание статуса», не
    боевые тексты продукта — иначе их примут за чистовик. Длинная рыба —
    до края второй строки, чтобы обрезка или фейд были видны.
14. **Анатомия** — номера `TagMarker` (Kit, `Set=Main`) поверх
    компонента по строкам таблицы и слой отступов; одной таблицы мало.
15. **Одинаковые привязки.** У слоя по одному пути во всех вариантах
    набора — одни и те же привязки свойств и переменных. Клонирование
    варианта сбрасывает привязки: после клонирования — проверить скриптом
    по всем вариантам (протокол §3.1 п.5, §3.8 п.5).
16. **Pressed** — слой цвета содержимого 12 % поверх заливки варианта, не
    отдельная заливка (`component-states-guide` §2.1). Иное — только
    принятым отклонением.
17. **Описание мастера** — оба поля, `description` и
    `descriptionMarkdown`, без `&quot;` `&gt;` `&lt;` `&amp;`. В сборке
    первая строка — `<Компонент> · <версия из pending> · не опубликовано`
    (протокол §3.3, §3.8 блок 1).
18. **Имена** слоёв, свойств и значений — латиницей, как в коде;
    значения с заглавной, `True/False` (`naming-conventions`).
    Кириллица — только в текстах.
19. **Только факт.** На пейдже нет «решение PD», «(sergej …)», «(PD …)»,
    дат решений — кроме блока 8 аудита (протокол §3.1 п.1).
20. **Для людей.** Тексты — для дизайнера; технические детали — строкой
    «Для инженера» внизу блока; важное — иллюстрацией «так / не так»,
    аннотации Dev Mode только дублируют.

## 3. Пейдж аудита — `👀 <Компонент> · audit`

Протокол §3.1. Пейдж — в целевом файле библиотеки, 👀 с создания и до
переноса в `Archive` на этапе сборки; в зоне 3 — среди `· audit` по алфавиту
(`persefona-figma-pages` §6.4.1). Шапка `HeaderPage`: заголовок — имя без
значка, метка «Смотреть и решать», метка задачи и «кого ждут».

Блоки — секцией `<Компонент> · audit`, сверху вниз. Номера и имена — из
таблицы §3.1 п.4, не менять.

| # | Блок | Как собрать |
|---|---|---|
| — | Обложка | `IslandBlock`: как читать пейдж, содержание со ссылками на блоки |
| 0 | Вход | Экземпляр исходного компонента, не мастер; если вставить нельзя — скрин и ссылка на узел экземпляра |
| 1 | Дерево компонентов | Узлы со статусом только из таблицы §3.1: «Есть», «Есть, нужно развитие», «Нет — новый компонент», «Не компонент, а часть» (причина одной строкой). Своих слов («Создаём», «в сборке») нет |
| 2 | Что увидели в макете | Что есть и как собрано, ошибки сборки — с картинкой |
| 3 | Токены: варианты и рекомендация | Таблица «значение → токен», пробелы отдельно; при сомнении — варианты рядом с цветом из макета, днём и ночью |
| 4 | Состояния и интерактив | Прототип: набор `.<Компонент> · audit` (точка — не публикуется), interactive components; Pressed — `WHILE_PRESSING` с возвратом |
| 5 | Сборка | Архитектура и разбиение; анатомия `TagMarker` + слой отступов; черновик таблицы замены свойств (§3.9), если есть старая версия |
| 6 | Трудные случаи | 360, длинная рыба до края второй строки, максимум и минимум элементов (`component-standards.md` §10) — днём и ночью |
| 7 | Было → Стало | Экземпляр в боевом макете рядом с исходным экраном, днём и ночью; «было» — копия с подписью «векторная копия», если не экземпляр |
| 8 | Что ждёт решения по аудиту | По вопросу: варианты а, б, в; рекомендация ★; хозяин; якорь — гиперссылка на узел **своего** пейджа, где пункт разобран; `Badge` статуса из таблицы §3.1 |

Иконки из макета — рядом как кандидаты, вместе с похожими из библиотеки
продукта (§3.1 п.3). Новый компонент по ходу — в дерево и в блок 8, не
мастером молча (`component-gate`).

## 4. Пейдж сборки — `🚧 <Компонент> · construction`

Протокол §3.8. 🚧 до публикации, на приёмке тоже. В зоне 3 — среди
`· construction` по алфавиту (§6.4.1). Шапка: метка «В работе», задача,
«кого ждут»; в содержании последним — «Changelog →».

**Шаг 1. Аудит — сразу в `Archive`** (протокол §3.1 п.6,
`persefona-figma-pages` §7.1, решение PD 2026-11-26). На пейдж сборки
аудит не переносится:

1. Снимок «до» пейджа `👀 · audit`: число узлов, число текстов, список
   ссылок и прототипов.
2. Секции аудита **переместить** (не копировать — id сохраняются) в одну
   секцию `<Компонент> · audit · ГГГГ-ММ-ДД` (дата переноса) на пейдже
   `Archive`, по `persefona-figma-pages` §7.3 (причина «сборка» и номер
   задачи, новые сверху). Нет пейджа `Archive` — завести (§3, §4.3).
3. Мастера аудита — с точкой в начале имени.
4. Сверка «после»: узлы, тексты, ссылки, прототипы совпадают со снимком.
5. Пустой пейдж `· audit` подагент не удаляет: в отчёт — «пустой, сверка
   совпала, удалить»; удаляет вызвавший после чтения отчёта.

**Шаг 2. Гайд** — секция `<Компонент>`, блоки сверху вниз. Номера и имена
— из таблицы §3.8 п.4: в гайде 1–8, 10, 11; 9 — отдельная секция.

| # | Блок | Как собрать |
|---|---|---|
| 0 | Обложка | Компонент, задача, тип (создание или развитие), версия из pending, этап; одна ссылка «Аудит — для истории →» на секцию аудита в `Archive` |
| 1 | Компоненты | Единственное место мастеров: набор `<Компонент>` с полным набором сочетаний вариантов; описание — п.17 раздела 2. Служебные мастера — с точкой |
| 2 | Когда применять | «Да / нет» сценариями; пара «так / не так» днём и ночью |
| 3 | Анатомия и токены | `TagMarker` поверх экземпляра + слой отступов; таблица «слой → токен, размер»; литерал — только принятый, со ссылкой на запись |
| 4 | Темы и платформы | Экземпляры днём и ночью режимом; отличия платформ картинкой; ограничения Figma и что делать руками |
| 5 | Поведение | Состояния; Pressed — п.16; анимация — таблица фаз и кнопка «Превью анимации ↗» на превью в Presentbook (`persefona-figma-pages` §6.9), без GIF, видео и прототипов |
| 6 | Трудные случаи | 360, длинная рыба, максимум и минимум элементов — экземплярами, днём и ночью |
| 7 | Связи | «Внутри», «Можно вставить», «Используется в» — списком из скрипта по мастерам; иконки и токены не входят |
| 8 | В боевом макете | Экземпляр на реальном экране продукта, днём и ночью |
| 10 | Отчёт автопроверки | Место под таблицу `ds-component-check`: `Banner` «ждёт проверки», таблицу вставляет Designer после прогона |
| 11 | Соответствие для замены | «Старое свойство или слой → новое», имена текстовых слоёв (§3.9); если старой версии нет — «Замены нет: новый компонент» |

Все примеры — экземпляры мастеров блока 1, не копии и не скрины.

**Шаг 3. Changelog** — секция `Changelog · <Компонент>` справа от гайда,
верхним краем по верху, зазор 80 (`persefona-figma-pages` §6.5). Таблица —
из `TableChangelog` Kit, сразу Detach; одна строка «Не опубликовано»;
слои `Changelog Table Body`, `Changes Row`, `__Changelog Badge` не
переименовывать. Таблица уже есть — перемещать, не пересоздавать: копия
получает новый id и ломает `figmaTable`.

## 5. Чего подагент не делает

- не создаёт компонент, которого нет в дереве и брифе (`component-gate`);
- не заводит токены и не подставляет значение без токена — пробел в
  отчёт (`token-change-gate`, `token-integrity`);
- не пишет версию и changelog, кроме строки «Не опубликовано»
  (`release-gate`);
- не решает открытые вопросы — выносит в блок 8 или в отчёт;
- не публикует библиотеку, не удаляет пейджи, не отвечает на комментарии
  Figma;
- не проверяет свою работу вместо `ds-component-check`.

## 6. Отчёт подагента

```markdown
## Пейдж · <Компонент> · <audit|construction> · <дата>

Файл <fileKey> · пейдж <имя> (<id>) · задача AID-<n>
Шапка <id> · секции: <имя> <id>, …

| # | Блок | Узел | День / ночь | Скриншот сверен | Заметка |
|---|---|---|---|---|---|
| 0 | Вход | 2312:8654 | да / да | да | — |

Мастера: <набор id, ключ, варианты id>; привязки одинаковые — да/нет (где нет)
Перенос аудита в Archive (сборка): секция <id>; до N узлов / M текстов → после N / M; пустой пейдж <id> — удалить
Пробелы: токен <что, где> · компонент Kit <что> · вопрос <кому>
Литералы и хексы: <узел — почему, где записано>
Дальше: ds-component-check подагентом с чистым контекстом
```

У каждой строки — id узла. Без id отчёт не принимается: по нему приёмка
находит место за секунды.

## 7. Шаблон брифа

Designer или Штаб запускает так (Agent, `general-purpose`), заполнив
раздел 1:

> Собери в Figma пейдж <аудита | сборки> компонента по
> `skills/ds-figma-page-brief/SKILL.md` (прочитай целиком; протокол —
> `skills/_shared/protocols/figma-library-workflow.md` §3.1 | §3.8, вид —
> `products/persefona/rules/persefona-figma-pages.md` §6.2–6.6).
> Режим: <audit | construction>. Продукт: <id>. Файл: <fileKey>.
> Компонент: <имя>. Задача: AID-<n>, issue #<n>, PR #<n>.
> Тип и версия: <создание 1.0.0 | развитие X.Y.Z → X.Y.Z>.
> Вход: <id экземпляра | скрин | текст>. Старая версия: <ключ/id | нет>.
> Договорено: <список или «нет»>. Открыто, хозяин: <список или «нет»>.
> Принятые отклонения и литералы: <список или «нет»>.
> (Сборка) Пейдж аудита: <id>, секция <id>. Превью анимации: <url | нет>.
> Первым — скилл `figma:figma-use`. Правь только этот пейдж. Каждый блок
> сверяй скриншотом днём и ночью. Верни отчёт по разделу 6 с id узлов.

Историю чата подагенту не пересказывать: всё нужное — в строках брифа.
Чего нет в строках — подагент не додумывает, а пишет в «Пробелы».
