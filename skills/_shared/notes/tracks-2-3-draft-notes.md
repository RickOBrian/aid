## Трек 2 — зачистка следов Claude Code

### Почему это важно (аргумент пользователя)

Пользователь планировал в прошлом использовать помимо Cursor ещё и Claude Code, отсюда легаси `.claude/` в структуре. По факту используется и будет использоваться только Perplexity + Cursor. Смешение путей/упоминаний Claude создаёт риск багов и недопонимания: Cursor может ориентироваться на буквальные пути, и расхождение инструкций (`.claude/` в одном документе, `skills/_shared/` в другом) либо создаёт дублирующиеся источники правды, либо приводит к тому, что Cursor выбирает путь произвольно, либо триггерит эвристики "здесь была Claude Code конфигурация" и подтягивает ненужные конвенции.

### Уже известный факт

В `cursor-component-pipeline-context.md` уже зафиксировано решение (было принято до этого разговора): "Claude Code не используется. В августе 2026 legacy-папка `.claude/`, `perplexity-skills/` и Claude-specific материалы удалены из репозитория." Проблема в том, что решение исполнено не полностью — `destination: .claude/` продолжал всплывать в новых документах (включая `space-context.md` и `github-sync-architecture.md` до правки 05.09.2026).

### Принятое решение по пути

Все документы, которые раньше метились `destination: .claude/`, переезжают в `skills/_shared/` (уже применено к `github-sync-architecture.md` 05.09.2026). Решение пока не принято, было предложено две опции, пользователь не выбрал.

## Трек 3 — синхронизация понимания между Cursor и Perplexity

### Проблема, как её сформулировал пользователь

Часть работы с Cursor выполняется без участия Perplexity. Из-за этого структура файлов, видимая в Perplexity Space (через Project Files), может не совпадать с реальным состоянием репозитория, с которым работает Cursor. При расхождении раньше был риск, что Perplexity ошибочно посчитает состояние репозитория багом (или наоборот) — хотя на самом деле это ожидаемое следствие асинхронной работы в двух независимых контурах.

### Принятый принцип

При расхождении между Project Files в Perplexity Space и фактическим состоянием репозитория/отчётом Cursor — **репозиторий (то, что видит и меняет Cursor) считается источником правды**, а не Project Files в Space. Этот принцип уже вписан явной строкой в `skills/_shared/architecture/github-sync-architecture.md` (секция "Примечание о синхронизации этого файла"), но пока только для этого одного документа — не как общее правило для всех Project Files в Space.

### Что это означает для поведения Perplexity (уже применяется с 05.09.2026)

- Не считать расхождение автоматически поводом для тревоги/аудита — это нормальное следствие независимых сессий, не аномалия.
- Если Project File в Space давно не обновлялся, а промт для Cursor на него опирается — явно предупреждать пользователя о возможной устарелости, а не молчаливо считать файл актуальным.
- Не считать автоматически багом ситуацию, когда Cursor создал/изменил что-то, чего нет в Project Files Perplexity — это ожидаемый результат работы без участия Perplexity.

### Что предлагалось, но не решено окончательно

1. Зафиксировать общий принцип (не только для одного файла) в `space-context.md` как явную инструкцию Space — предложено дважды, пользователь пока не подтвердил.
2. Завести привычку: после существенных самостоятельных сессий с Cursor — приносить в Space обновлённые версии ключевых "живых" документов (в первую очередь статусные/архитектурные файлы вроде `github-sync-architecture.md`), не после каждой мелкой правки, а перед тем как просить Perplexity подготовить следующий большой промт, опирающийся на текущее состояние.
3. Помечать в самих "живых" документах дату последней ручной синхронизации с Perplexity Space (уже сделано разово для `github-sync-architecture.md` — "Дата последней ручной синхронизации: 05.09.2026"), сделать это общей конвенцией для всех подобных файлов.
