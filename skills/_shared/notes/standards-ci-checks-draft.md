# Набросок: какие правила стандартов проверяемы машиной

Набросок Стандартов к следующему шагу после standards-6 (автопроверка
стандартов в CI, ждёт «да» PD). Цель — чтобы правило не зависело от того,
прочитал ли его Claude инженера: плагин учит, CI ловит.

Принцип: проверка сравнивает артефакт с **каноном в репо** (реестр,
токены, шаблон), а не с мнением. Где канона нет — сначала канон, потом
проверка.

## 1. Уже проверяется

| Правило | Чем | Где |
|---|---|---|
| Форма документа: frontmatter, строка статуса, нумерация, Changelog | `scripts/check-docs.mjs` | CI «Документы» |
| Реестр ↔ файлы: версия, статус, kind, путь | `scripts/check-docs.mjs` | CI «Документы» |
| Ссылки на файлы в документах ведут в существующие пути | `scripts/check-docs.mjs` | CI «Документы» |
| У каждого токенного файла есть чейнжлог | `pages/aid-portal/scripts/ensure-token-changelogs.mjs` | сборка Портала |

## 2. Проверяемо сразу — канон уже есть

| Правило | Источник канона | Как проверить | Цена ложной тревоги |
|---|---|---|---|
| Нет HEX/RGB/HSL-литералов вне `:root` Core в `*.css`/`*.scss`/`*.html` | `no-hardcode-color-protocol`, гейт `token-integrity` | регэксп по диффу PR, исключения — файлом | низкая |
| CSS-переменная `--…` в коде есть в токенах продукта | `pages/aid-portal/products/<id>/` (`tokenDataFiles`) | сверка имён `var(--x)` с выгрузкой | низкая |
| Дефисная нотация токенов в документах (`bg-accent-main`, не `bg.accent.main`) | `naming-conventions`, STANDARDS-WORK «Терминология» | регэксп по `skills/_shared/**/*.md`, исключение — iOS Asset Catalog | средняя |
| Версия и запись чейнжлога меняются только вместе | `changelog-guide`, `release-gate` | дифф: `currentVersion` вырос → есть запись этой версии, и наоборот | низкая |
| Запись чейнжлога токенов — по схеме (`version`, `date`, `type`, `changes[].kind`) | `changelog-guide` §3 | JSON Schema по `tokens/*-changelog.json` | низкая |
| Pending-запись не несёт версию | `changelog-guide` §4 | `changes/*/pending/*.json` без `version` | низкая |
| Иконка в каталоге Presentbook — SVG с размерами | `ensure-icon-dimensions.mjs` | перевести из «чинит молча» в «падает» | низкая |

## 3. Проверяемо после канона — сначала правило

| Правило | Чего не хватает | Предложение |
|---|---|---|
| Имена иконок: `ic_<имя>[_<вид>]`, snake_case, словарь видов (`_fill`, `_outline`, `_color`, `_mini`, `_bold`) | В `naming-conventions` про иконки одна строка «asset id / filename»; словарь видов живёт только в библиотеке Rider Icons (публикация 2026-10-21) | Раздел «Иконки» в `naming-conventions` (minor) → проверка имён SVG в `public/icons/<id>/` и в индексе библиотеки |
| Ломающее изменение библиотеки Figma (удаление, переименование) → major | Нет машинного снимка состава библиотеки в репо | Снимок состава (имя + префикс ключа) в `products/<id>/`, CI сравнивает с прошлым и требует bump |
| Гайд по шаблону «Как в AID» для гайдов-продуктов (тип Guide) | Тип Guide ещё не заведён (standards-4, п. 1) | После standards-4 — тот же `check-docs` по маске гайдов |
| Подписи ссылок по смыслу | Правило есть (`guide-template` §6), но «по смыслу» машина не судит | Проверяемо только грубо: ссылка, чей текст — голый ID узла (`\d+:\d+`) или номер, — предупреждение |

## 4. Не проверяемо машиной

- «Не создавать компонент молча» и «пробелы — одной анкетой»: это про
  ход разговора, а не про артефакт. Ловится косвенно: новый компонент в
  `components/` без записи в pending — ошибка (это уже §2).
- Разбор аудита с PD по номерам, приём «стало» по снимку — процесс.
- Отклонение продукта «оформлено записью»: проверяемо только наличие
  записи в `products/<id>/deviations.json` (черновик — `skills/_shared/notes/product-deviations-draft.md`), а не её обоснованность.

## 5. Порядок, если PD скажет «да»

1. Отчётом, без падения CI — неделя, чтобы увидеть шум.
2. Правила §2 — в «Документы» как ошибки; исключения — файлом рядом с
   правилом, а не флагом в коде.
3. §3 — по мере появления канона, каждое правило отдельным PR.

Правка `checks.yml` — «Только PD» и DevOps по задаче; Стандарты пишут
сами проверки (`scripts/`) и канон.
