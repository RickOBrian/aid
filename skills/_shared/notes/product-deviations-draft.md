# Реестр отклонений продукта — черновик формата

> Статус: Draft · v0.2.0 · обновлено 2026-10-22
>
> Механизм — кто утверждает, что считается обоснованием, условие снятия —
> предложен в standards-11: `changes/standards-11-exceptions-proposal-2026-10-22.md`.
> До решения PD (Q-25) — заметка, гейты по ней не работают.

Решение PD 2026-10-18: стандарт — идеал, к которому стремятся; продукт
может отклониться, если того требует продукт (иначе назвать токен,
состояние компонента и т. п.). `conformance-levels` §6 уже требует
оформлять продуктовые исключения записью, но постоянного места для записи
нет: `changes/<id>/pending/` — очередь изменений, запись из неё уходит
при релизе. Отклонение же живёт, пока живёт продукт.

## Где лежит

`products/<id>/deviations.json` — рядом с `product.json`, в папке,
которой владеют Стандарты. Один файл на продукт. Нет файла — нет
отклонений.

## Формат

```json
{
  "product": "driver",
  "deviations": [
    {
      "id": "driver-dev-001",
      "standard": "component-states-guide",
      "rule": "state-names",
      "level": "should",
      "ideal": "hover",
      "product": "pressed-light",
      "scope": ["button", "chip"],
      "basis": "product-specific",
      "reason": "Почему продукту так нужно — одной-двумя фразами",
      "decision": { "by": "PD", "date": "2026-10-18", "ref": "ссылка на PR, issue или запись в DECISIONS.md" },
      "exit": { "kind": "none", "what": null, "ref": null },
      "status": "accepted",
      "review": "2027-04-18"
    }
  ]
}
```

| Поле | Обязательно | Смысл |
|---|---|---|
| `id` | да | `<продукт>-dev-NNN`, не переиспользуется |
| `standard` | да | `id` стандарта из `standards-registry.json` |
| `rule` | да | `id` правила из машинного слоя; пока у стандарта нет машинного слоя — якорь раздела гайда (`#4-…`) |
| `level` | да | уровень правила по `conformance-levels`: `must`, `should`, `may` |
| `ideal` | да | что требует стандарт |
| `product` | да | как сделано в продукте |
| `scope` | нет | на что распространяется: компоненты, токены, коллекции; пусто — на весь продукт |
| `basis` | да | основание: `migration-cost`, `platform`, `product-specific`, `upstream-defect`; другие не принимаются |
| `reason` | да | почему продукту так нужно |
| `reuseJustification` | для `must` | почему артефакт всё равно годится для переиспользования |
| `decision` | да, кроме `proposed` | кто, когда и где решил (`decision:pd`); без решения запись не действует |
| `exit` | да | условие снятия: `kind` — `event`, `fix`, `standard-change`, `none`; `what` — что должно случиться; `ref` — задача или PR |
| `guard` | для `exit.kind: fix` | проверка, которая упадёт, когда дефекта не станет |
| `status` | да | `proposed` — ждёт решения PD; `accepted` — действует; `retired` — продукт вернулся к стандарту; `absorbed` — стандарт принял вариант продукта |
| `review` | для `exit.kind: none` | дата пересмотра, не дальше 12 месяцев; прошла — аудит пишет «исключение истекло» |

## Правила

- Утверждает PD (`decision:pd` в issue или PR, либо строка в «Решения
  PD»); запись готовят и вносят Стандарты.
- Отклонение, которое повторяется в другом продукте или которое правило
  не описывает, — пробел стандарта: временная запись с
  `exit.kind: standard-change` и правка стандарта отдельной задачей.
- Отклонение от правила уровня `must` — только с явным решением PD и
  обоснованием, почему артефакт всё равно годится для переиспользования
  (`conformance-levels` §4).
- Запись не удаляется: при отмене меняется `status`. История отклонений —
  материал для развития стандарта.
- Одно и то же отклонение в двух и более продуктах — повод для Стандартов
  предложить PD поменять стандарт; после смены записи получают `absorbed`.

## Кто читает

| Читатель | Зачем |
|---|---|
| Стандарты — lookup для Designer | ответ «по стандарту X, в продукте принято Y» |
| Аудит (`audit-gate`) | находка по правилу с записью → `accepted-exception` |
| AID Style Migration | не предлагать «исправить» принятое отклонение |
| Presentbook | показать отклонения на странице продукта |
| Замер внедрения (AID-21) | не считать отклонение нарушением |

## Что меняется в стандартах при принятии

- `conformance-levels` §4 и `dispositionOverrides`: ссылка
  `accepted-exception` ведёт на запись в `products/<id>/deviations.json`,
  а не в `changes/<id>/pending/` — изменение контракта, MINOR.
- `audit-gate`: шаг сверки с реестром отклонений.
- Стык в корневом `CLAUDE.md`: «Отклонения продукта — Стандарты; читают
  аудит, Style Migration, Presentbook» — через PD.

## Открытые вопросы

1. Согласовать формат с Designer, Style Migration и Presentbook через
   Штаб — они читатели.
2. Правила без `id` в машинном слое: ссылаться на якорь гайда или сначала
   дать правилам `id` (связано с доводкой токенных гайдов до alpha).
3. Переносить ли в реестр уже принятые исключения из
   `changes/driver/pending/` — вопрос PD, Q-25 п. 5.
