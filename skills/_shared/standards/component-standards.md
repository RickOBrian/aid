# Стандарты компонентов

> Статус: Alpha · v3.0.0 · обновлено 2026-09-20

---

## 1. Назначение

Документ фиксирует, каким должен получиться компонент дизайн-системы:
контракт API, варианты, состояния, привязка к токенам, доступность,
документация и условия готовности к релизу.

Компонент, не отвечающий этим требованиям, не считается готовым к релизу,
даже если визуально совпадает с макетом.

Границы документа:

- **здесь** — каким компонент должен быть;
- **не здесь** — можно ли его вообще создавать: это решает
  `skills/_shared/protocols/gates/component-gate.md`;
- **не здесь** — на каком уровне архитектуры компонент живёт: это
  `ds-component-architecture-guide.md`.

Стандарт платформо-независим. Конкретный стек продукта читается из
`products/<id>/product.json` → `platformModel`. Если там `declared: false`,
стек нужно уточнить, а не подставлять умолчание.

> **Как читать.** Таблицы и списки — норма, их достаточно для сверки.
> Блоки «Почему так» объясняют решение и нужны, когда правило спорят или
> изучают. Машинная копия правил — `component-standards.json` рядом.

## 3. Уровни соответствия

Требования ниже не бинарны. У каждого есть уровень — `must`, `should` или
`may`; что означает расхождение на каждом уровне, описано в
`conformance-levels.md`. Уровни хранятся в машинном слое
`component-standards.json`, в прозе не дублируются.

Уровня `must` в этом стандарте удостоены пять правил:

| Правило | Почему без него артефакт не компонент дизайн-системы |
|---|---|
| Уровень архитектуры определён | Пока неизвестен уровень, неизвестно и какие требования применимы — компонент нечем проверять |
| Имя по канону нейминга | Имя — это идентичность. Компонент с произвольным именем нельзя найти, сопоставить с чужим и переиспользовать |
| Публичный типизированный контракт | Без опубликованного контракта компонент нельзя применить снаружи, не читая его исходник |
| Цвет — через токен, не через литерал | Литерал цвета ломает темизацию и делает компонент непереносимым между продуктами и режимами |
| Состояние и обработчики связаны реально | Заглушенный компонент выглядит рабочим и не работает. Это отказ, а не расхождение со вкусом |

Всё остальное — `should` и `may`. Компонент, выполняющий пять правил выше,
уже является компонентом дизайн-системы; дальше измеряется дистанция до
эталона, а не годность.

> **Почему список такой короткий.** Критерий попадания в `must` —
> «без правила артефакт нельзя опознать, использовать или безопасно
> переиспользовать», а не «так лучше». Расширение списка — изменение
> MAJOR: артефакты, считавшиеся корректными, перестают ими быть задним
> числом.

## 4. Применимость по уровням архитектуры

Требования зависят от уровня компонента. Уровень определяется по
`ds-component-architecture-guide.md`.

| Требование | Item | Surface View | Structural View | Layout |
|---|---|---|---|---|
| Контракт API | да | да | да | да |
| Варианты | нет | да | да | нет |
| Состояния | нет — наследует от родителя | да | да | нет |
| Слоты | нет | нет | да | нет |
| Токены | только цвет и типографика | полный набор | полный набор | только `gap-*` |
| Escape hatches | да | да | да | да |
| Устойчивость к контенту | да | да | да | нет |
| Доступность | через родителя | да | да | нет |
| Тесты | unit | unit + visual + a11y | unit + visual + a11y | unit |
| Документация | пример использования | полный набор | полный набор | пример использования |
| Definition of Done | сокращённый | полный | полный | сокращённый |

Сокращённый Definition of Done — пункты 1, 2, 6, 9, 10 из раздела 14.

> **Почему так.** Прежняя редакция стандарта описывала только Surface View
> и выше. Item и Layout при этом существуют, релизятся и требуют проверки —
> просто другой. Без этой таблицы аудит компонента уровня Item не на что
> опереть, и проверяющий либо придумывает требования на ходу, либо
> пропускает компонент вовсе.

## 5. Состав компонента

Компонент уровня Surface View и выше включает:

1. **Реализацию** — на стеке, объявленном в `platformModel` продукта.
2. **Контракт API** — типизированный, экспортируемый как публичный.
3. **Варианты** — визуальные различия одного и того же смысла.
4. **Состояния** — интерактивность и обратная связь.
5. **Анатомию** — перечень зон и значений с указанием вида каждого значения
   (раздел 8).
6. **Документацию** — пример, таблица пропов, матрица, границы применения.

Item включает пункты 1, 2, 6. Layout — пункты 1, 2, 6.

## 6. Структура файлов

Имена файлов следуют имени компонента. Стек берётся из `platformModel`
продукта; ниже — раскладка для трёх распространённых стеков.

**React**

```text
ButtonText/
├── ButtonText.tsx          реализация
├── ButtonText.types.ts     контракт API (если выносится отдельно)
├── ButtonText.stories.tsx  примеры для Presentbook
├── ButtonText.test.tsx     unit и a11y
└── index.ts                публичный экспорт
```

**SwiftUI**

```text
ButtonText/
├── ButtonTextView.swift        реализация
├── ButtonTextStyle.swift       варианты и размеры
├── ButtonTextPreviews.swift    превью
└── ButtonTextTests.swift       тесты
```

**Compose**

```text
buttontext/
├── ButtonText.kt           реализация
├── ButtonTextDefaults.kt   варианты, размеры, значения по умолчанию
├── ButtonTextPreview.kt    превью
└── ButtonTextTest.kt       тесты
```

Если продукт объявил стек `cmp`, раскладка Compose применяется к общему
модулю, а платформенные отличия выносятся в `expect`/`actual`.

Путь размещения компонента определяет `componentsRoot` продукта. Пока он
`null`, файлы не создаются без подтверждения — см. Component Gate.

## 7. Контракт API

### 6.1 Именование

| Вид пропа | Правило | Пример |
|---|---|---|
| Булев | префикс `is` | `isDisabled`, `isLoading`, `isSelected` |
| Колбэк | префикс `on` | `onClick`, `onChange`, `onBlur` |
| Вариант, размер | `variant`, `size` — перечисление, не свободная строка | `variant="primary"` |
| Слот | канон из архитектурного гайда | `leading`, `content`, `trailing` |

Платформенное исключение: в Compose булев проп доступности называется
`enabled`, а не `isEnabled` — это конвенция платформы, зафиксированная в
`platforms.md`. Смысловой паритет пропов важнее буквального совпадения имён.

### 6.2 Обязательное и опциональное

- Обязателен только тот проп, без которого компонент теряет смысл.
- Всё, у чего есть разумное значение по умолчанию, — опционально с этим
  значением.
- Значение по умолчанию указывается в таблице пропов, а не только в коде.

### 6.3 Типизация

- Перечисления — union-типы, не объекты-enum и не свободные строки.
- Слоты типизируются платформенным типом узла, `any` запрещён.
- Контракт экспортируется: он часть публичного API наравне с самим
  компонентом.

### 6.4 Управляемость

| Режим | Признак | Требование |
|---|---|---|
| Управляемый | `value` и `onChange` приходят снаружи | `value` без `onChange` означает read-only и должен быть описан как read-only |
| Неуправляемый | внутреннее состояние и опциональный `defaultValue` | `defaultValue` не комбинируется с `value` |

Компонент не меняет режим в течение жизни. Переход управляемый ↔
неуправляемый на лету — ошибка реализации, а не возможность.

### 6.5 Слоты

Именованные слоты — только из канона `ds-component-architecture-guide.md`,
раздел «Слоты Structural View». Стандарт не заводит собственного списка:
пока их было три, они разошлись. Платформенные синонимы запрещены —
`leading`, а не `leftContent` и не `startSlot`.

**Repeatable Slot** — слот, повторяющийся переменное число раз (2..N),
когда количество определяется данными, а не дизайном. В контракте
обозначается с диапазоном: `cell (repeatable, 2..N)`.

- Объединение соседних элементов (`colSpan`, `rowSpan`) задаётся пропом на
  самом повторяющемся элементе, не на родителе.
- В таблице пропов repeatable-слот показывается отдельной строкой с
  диапазоном и указанием, где живёт span.

### 6.6 Escape hatches

Точки расширения, без которых продукт начинает форкать компонент.

| Правило | Требование |
|---|---|
| Передача ссылки на узел | Интерактивный компонент обязан пробрасывать ссылку на корневой узел |
| Классы и инлайн-стили | Допустимы только на корневом узле; на внутренние зоны не пробрасываются |
| Атрибуты доступности | `aria-*` и идентификаторы пробрасываются всегда |
| Хук для тестов | Атрибут для тестового селектора обязателен на корневом узле |
| Полиморфизм | Смена корневого тега допустима только для Layout |
| Рассыпание остальных пропов | Неизвестные пропы не пробрасываются молча — контракт перечисляет то, что принимает |

> **Почему так.** Escape hatch — это не послабление, а замена форку. Если
> продукту нужно чуть иное поведение и легального способа нет, он копирует
> компонент к себе, и дизайн-система теряет над ним контроль. Ограничение
> «только корневой узел» сохраняет внутреннюю анатомию неприкосновенной.

### 6.7 Размер и плотность

Проп `size` меняет визуальные размеры: отступы, типографику, размеры
иконок, геометрию.

Инварианты, которые `size` не меняет никогда:

- область нажатия не опускается ниже минимума платформы (44×44 на Web и
  iOS, 48×48 на Android) — при малых размерах область расширяется за
  пределы видимой границы;
- набор вариантов и состояний одинаков для всех размеров;
- имена токенов не зависят от размера — различается ступень, не роль.

## 8. Варианты и состояния

### 7.1 Варианты

Вариант описывает оформление при одном и том же смысле действия.

| Вариант | Назначение |
|---|---|
| `primary` | Основное действие |
| `secondary` | Вторичное действие |
| `ghost` | Минимальный визуальный вес |
| `destructive` | Опасное действие |

`destructive` — вариант оформления, а не состояние и не отдельный
компонент. Красная кнопка «Удалить» — это `variant="destructive"`, а не
состояние `error` и не `ButtonDestructive`.

### 7.2 Вариант или новый компонент

| Признак | Решение |
|---|---|
| Меняются только значения токенов, анатомия та же | Вариант |
| Меняется набор слотов или их назначение | Новый компонент |
| Меняется уровень архитектуры | Новый компонент |
| Меняется смысл действия, а не его оформление | Новый компонент |
| Вариантов становится больше пяти и они перестают быть сравнимыми | Повод пересмотреть: вероятно, внутри прячется второй компонент |

### 7.3 Состояния

Состояние — это режим взаимодействия или обратной связи. Имена — из
`component-states-guide.md`, он источник истины.

| Состояние | Когда | Уровни |
|---|---|---|
| `default` | Базовое | Surface View, Structural View |
| `hovered` | Курсор над компонентом — только стек с курсором | Surface View, Structural View |
| `pressed` | Нажатие удерживается | Surface View, Structural View |
| `focused` | Фокус клавиатуры или скринридера | Surface View, Structural View |
| `selected` | Выбран | Surface View, Structural View |
| `disabled` | Недоступен | Surface View, Structural View |
| `loading` | Короткое ожидание внутри компонента | Surface View, Structural View |
| `skeleton` | Первичная загрузка, данных ещё нет | Surface View, Structural View |
| `error` | Ошибка валидации — только контролы форм | Surface View, Structural View |

Дополнительно для Structural View: `expanded` / `collapsed`, а также
составные `loading` и `disabled`, когда отдельные зоны находятся в этом
режиме независимо друг от друга.

**Состояние против значения.** Не всё, что меняет вид компонента, является
состоянием.

| Признак | Состояние | Значение |
|---|---|---|
| Возникает от взаимодействия с компонентом | да | нет |
| Поглощается `disabled` | да | нет |
| Живёт в матрице вариант × состояние | да | нет |
| Пример | `pressed`, `loading` | `checked: true / false / mixed` |

Поэтому `indeterminate` у чекбокса — **третье значение**
(`checked: 'mixed'`), а не десятое состояние. Оно сохраняется при
`disabled` и не возникает от нажатия.

> **Почему так.** Без этого различения список состояний растёт бесконечно:
> в него попадает всё, что влияет на вид. Матрица вариант × состояние
> при этом раздувается комбинациями, которых не бывает, а токен-маппинг
> приходится описывать для несуществующих сочетаний.

### 7.4 Матрица вариант × состояние

- Каждое допустимое сочетание имеет привязку к токенам.
- Матрица строится **только из допустимых** комбинаций
  `component-states-guide.md`. Недопустимые не попадают ни в документацию,
  ни в снимки визуальных тестов.
- Матрица обязательна в документации компонента.

Недопустимые сочетания, которые чаще всего пытаются нарисовать:
`disabled + loading`, `pressed + disabled`, `loading + pressed`,
`skeleton + focused`, `skeleton + loading`, `error + disabled`.

## 9. Значения и токены

Компонент ссылается только на semantic-токены; прямая ссылка на Core —
расхождение уровня `should`, см. `token-rules.md`. Исключение — цвет: он
уровня `must`, потому что литерал цвета ломает темизацию и переносимость.

Категории, которые компонент потребляет: цвет, типографика, пространство
(`inset-*`, `gap-*`), радиусы, тени, иконки. Конкретные файлы значений
продукта перечислены в `products/<id>/product.json` → `tokenDataFiles`;
в стандарте они не дублируются.

**Классификация значений.** Не всякое значение без токена — нарушение.
Вид значения определяется по шкале из
`skills/_shared/protocols/gates/token-integrity.md`:
`semantic-token`, `platform-convention`, `raw-value`, `hardcode`.

- вид указывается явно в анатомии компонента;
- значение без указанного вида приравнивается к `hardcode`;
- `hardcode` цвета — уровень `must`;
- `hardcode` остальных категорий — уровень `should`: фиксируется как
  дистанция, не блокирует.

```tsx
// норма
backgroundColor: 'var(--bg-accent-main)';
padding: 'var(--inset-control-h-m)';

// must: литерал цвета
backgroundColor: '#0057FF';
padding: '16px';
```

Отсутствие нужного токена не разрешает хардкод: пробел фиксируется по
процедуре Token Integrity Gate, работа останавливается до решения.

## 10. Устойчивость к контенту

Компонент проверяется не на идеальных данных.

| Случай | Требование |
|---|---|
| Длинный текст | Заданное поведение: обрезка с многоточием или перенос. «Как получится» — не поведение |
| Пустое значение | Определено, что показывается: заглушка, скрытие зоны или нулевое значение |
| Локализация | Раскладка выдерживает рост длины строки примерно в полтора раза |
| Направление письма | Если продукт поддерживает RTL — зеркалятся `leading` и `trailing`, а не левое и правое |
| Числа | Формат и разрядность заданы; поведение при переполнении разряда определено |
| Отсутствие изображения | Определён запасной вид: инициалы, иконка, нейтральный фон |

В документации компонента обязателен пример «худший случай»: максимальная
длина, пустые значения и предельное число одновременно.

> **Почему так.** Компоненты ломаются не на макете, а на реальных данных.
> Дефекты этого класса находят в продукте, а не в дизайн-системе, и чинят
> в продукте — форком компонента. Один пример «худший случай» в
> документации стоит дешевле, чем разбор такого форка.

## 11. Доступность

Полные требования — в `accessibility.md`. Он источник истины: контраст,
управление фокусом, клавиатура, скринридеры, платформенные API.

Компонентная дельта, проверяемая на уровне компонента:

| Проверка | Требование |
|---|---|
| Область нажатия | Не ниже минимума платформы при любом `size` — см. 6.7 |
| Видимый фокус | Через semantic-токен, не через отключение обводки |
| Недоступность | Отражается согласованно во всех источниках: визуально, в атрибутах, в поведении фокуса |
| Состояние без цвета | Ни одно состояние не передаётся только цветом |
| Иконка без подписи | Имеет текстовую альтернативу |

Приглушение недоступного элемента — `platform-convention` (раздел 8), а не
хардкод. Требование контраста к недоступным контролам не применяется:
это явное исключение WCAG, и оно не повод считать приглушение нарушением.

## 12. Тестирование

Полная стратегия — в `testing-strategy.md`. Компонентная дельта:

| Уровень | Что проверяется на компоненте |
|---|---|
| Unit | Значения по умолчанию, отрисовка каждого варианта, поведение в `disabled` и `loading`, вызов колбэков |
| Визуальный | Снимок каждого **допустимого** сочетания вариант × состояние, в обеих темах |
| Доступность | Атрибуты, порядок фокуса, контраст |
| Интерактивность | Чеклист из `platforms.md`: состояние и обработчики связаны реально, а не заглушены константой или пустой функцией |

Чеклист интерактивности обязателен и для примеров кода, которые не
собирались. Если код не запускался — это указывается явно рядом с ним.

## 13. Документация компонента

Страница компонента включает:

1. **Пример** — минимум один интерактивный на каждый вариант.
2. **Таблицу пропов** — имя, тип, значение по умолчанию, описание;
   устаревшие пропы помечены отдельно.
3. **Матрицу вариант × состояние** — только допустимые сочетания.
4. **Пример «худший случай»** — см. раздел 9.
5. **Границы применения** — когда брать этот компонент, а когда другой,
   от двух до пяти пунктов на каждую сторону.

Требования к самой странице в Presentbook — в
`skills/_shared/protocols/component-page-baseline.md`.

## 14. Версионирование и устаревание

Версия компонента — независимый SemVer, см. `semver-guide.md`.

| Изменение | Уровень |
|---|---|
| Удалён или переименован проп, вариант, слот; изменилось значение по умолчанию так, что меняется вид | MAJOR |
| Новый вариант, состояние, слот, проп с обратной совместимостью | MINOR |
| Визуальная правка, доработка документации, исправление доступности без изменения API | PATCH |

**Устаревание.** Проп нельзя удалить сразу.

1. Проп помечается устаревшим в таблице пропов с указанием замены.
2. В режиме разработки использование выводит предупреждение.
3. Проп живёт минимум один MINOR-релиз.
4. Удаление — в MAJOR, с записью в changelog и указанием пути миграции.

Во время реализации изменения накапливаются в `changes/<id>/pending/`.
Версия и запись changelog появляются только на границе релиза — см.
`skills/_shared/protocols/gates/release-gate.md`.

> **Почему так.** Без жизненного цикла устаревания единственный легальный
> способ убрать проп — сразу MAJOR. В результате либо мажорная версия
> выпускается ради одной чистки, либо проп не убирают никогда, и контракт
> растёт только вверх.

## 15. Готовность к релизу

Компонент готов, когда выполнены все пункты. Для Item и Layout —
сокращённый набор: 1, 2, 6, 9, 10.

1. Уровень архитектуры определён, имя соответствует формуле Role + Entity.
2. Контракт API опубликован: перечисления, значения по умолчанию,
   управляемость, escape hatches.
3. Варианты и состояния реализованы; матрица содержит только допустимые
   сочетания и имеет привязку к токенам.
4. Все значения классифицированы; `hardcode` отсутствует.
5. Устойчивость к контенту проверена, пример «худший случай» есть.
6. Доступность: область нажатия, видимый фокус, согласованная
   недоступность, состояние не только цветом.
7. Тесты: unit, визуальные по допустимым сочетаниям, доступность.
8. Чеклист интерактивности пройден: состояние и обработчики связаны.
9. Документация: пример, таблица пропов, границы применения.
10. Изменения записаны в `changes/<id>/pending/`; версия и changelog —
    на границе релиза, не раньше.

Пройденный Component Gate не заменяет этот список: гейт решает, можно ли
начинать, а список — закончено ли.

## 16. Changelog

  `ds-component-architecture-guide.md` — в корпусе нашлись три
  несовпадающих набора, и стандарт не должен держать четвёртый.
- **2.0.0** — 2026-09-20. Крупная переработка, ломающая прежние ожидания.
  Добавлены: применимость по уровням архитектуры (Item и Layout больше не
  вне стандарта), полный список состояний и различение состояния и

  источник истины перенесён в `accessibility.md` и `testing-strategy.md`.
  Продуктовые пути убраны: файлы значений читаются из манифеста продукта.
  Ссылки на правила Cursor заменены на протоколы гейтов.
