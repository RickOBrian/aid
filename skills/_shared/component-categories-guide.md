# Категории компонентов дизайн-системы — v1.1.0

> Статус: Draft · v1.1.0

---

## Зачем отдельная классификация

Архитектурный уровень (`ds-component-architecture-guide.md`) отвечает на вопрос
«как компонент устроен» — важно для разработки и ревью спек.

Категория отвечает на вопрос «что компонент делает» — важно для навигации
в Storybook, чтобы дизайнер или PM быстро находили нужный компонент без
знания архитектурных уровней.

Эти две классификации не пересекаются и не заменяют друг друга. Уровень
компонента отображается внутри его карточки. Категория используется только
для группировки в навигации хаба.

---

## Категории — таблица

| Категория | Назначение | Компоненты (текущие) |
|---|---|---|
| **Controls** | Инициируют действие пользователя | ButtonIcon, StorybookButton, Switch, Checkbox, Radio |
| **Inputs** | Ввод и редактирование данных | Search, TextField, Select |
| **Indicators** | Статус/классификация без действия | Badge, Chip, Tag, Dot |
| **Media** | Представление сущности (пользователь, продукт, бренд) | Avatar, AvatarButton |
| **Surfaces** | Generic-контейнеры без собственного смысла | Card, IconSurface, MediaSurface |
| **Data display: metrics** | Метрики и аналитика | StatTile, WidgetBalance |
| **Data display: tabular** | Построчные табличные данные с заголовком и повторяющимися строками (Table, TableRow). Отличается от Surfaces (единичный контент) и Data display: metrics (StatTile, WidgetBalance) наличием построчной структуры с переиспользуемым Row-паттерном. | Table |
| **Navigation** | Навигация по продукту | NavBar, TabBar, Menu |
| **Overlays** | Временно перекрывают контент | BottomSheet, Dialog, Toast, SidePanel |
| **Layout** | Только расстановка группы компонентов | VStack, HStack, Grid |
| **Feedback** | Обратная связь пользователю о состоянии/результате | EmptyState, Banner |
| **Documentation utilities** | Не UI-компоненты продукта, инструменты документации ДС | ColorSwatch |

## Разрешённые спорные случаи

- **Search** — Inputs, не Controls. Основная функция — ввод данных, а не
  инициация разового действия.
- **Toast** — Overlays, не Feedback. Toast технически перекрывает контент
  временным слоем, даже если по смыслу это обратная связь. Feedback
  зарезервирован для компонентов без overlay-поведения (EmptyState, Banner).
- **Avatar** — Media, не Surfaces. Avatar не generic-контейнер, а
  представление конкретной сущности с фиксированным смыслом.

## Правило для новых компонентов (обязательно к соблюдению)

Когда появляется компонент, которого нет в таблице выше:

1. **Сначала попробовать существующую категорию.** Определить по вопросу
   «что этот компонент делает по назначению», не «как он устроен архитектурно».
   Использовать формулировки «Назначение» из таблицы как критерий.

2. **Проверить пограничные случаи по аналогии с разделом выше.** Если новый
   компонент похож по функции на уже разрешённый спорный случай — применить
   то же решение (пример: любой будущий компонент ввода → Inputs, не Controls).

3. **Новую категорию создавать только если компонент не подходит ни под одну
   из существующих ни по каким критериям.** Один компонент — недостаточное
   основание для новой категории. Порог: если видно, что в перспективе
   появится семейство из 2+ компонентов с этим назначением — категория
   оправдана. Если это единичный случай — временно определить в наиболее
   близкую существующую категорию и отметить как "требует уточнения" в
   карточке компонента, а не создавать категорию под один компонент.

4. **Если создание новой категории неизбежно** — Cursor обязан:
   - предложить имя категории и однострочное назначение в том же стиле,
     что и существующие строки таблицы
   - **не добавлять категорию автоматически без подтверждения** —
     зафиксировать предложение как открытый вопрос в выводе (например,
     в конце сгенерированной страницы или в отдельном changelog-разделе),
     адресованный Principal Designer
   - использовать эту новую категорию для текущего компонента временно,
     явно пометив «pending review»
   - после подтверждения Principal Designer — добавить строку в таблицу
     этого файла и повысить версию гайда

5. **Никогда не переносить компонент между категориями без объяснения.**
   Если следующий батч показывает, что ранее отнесённый компонент на самом
   деле принадлежит другой категории — зафиксировать это как явное решение
   с аргументацией, по аналогии с разделом «Разрешённые спорные случаи».

## Формат вывода при создании новой категории

```
⚠️ Новая категория предложена: [Имя]
Назначение: [одна строка, в стиле существующих]
Компонент-триггер: [ComponentName]
Обоснование: [почему не подошла ни одна существующая категория]
Статус: pending review — требует подтверждения Principal Designer
```

## Changelog

- **1.1.0** — 2026-07-03. Added "Data display: tabular" category for
  row-based table components. Категория "Data display" переименована в
  "Data display: metrics" для явного разграничения с новой категорией
  (обе описывают разные назначения: метрики vs построчные табличные
  данные). Первый компонент новой категории — Table (по итогам аудита
  audit-002, `memory/ds-component-audit/log.sergej.json`).
- **1.0.0** — первая версия. Зафиксированы 10 категорий, 3 разрешённых
  спорных случая (Search → Inputs, Toast → Overlays, Avatar → Media),
  правило добавления новых категорий с порогом "2+ компонента" и
  обязательным pending review перед фиксацией.
