# Component Migration — Guide — v1.1.1

> Статус: Draft · v1.1.1

---

## 1. Назначение

Гайд объясняет процесс переноса legacy-реализаций (старая разметка/классы)
на уже утверждённый canonical-компонент дизайн-системы — например
`.table-wrap` → `Table`/`TableRow`.

**Когда использовать `ds-component-migration`:** у компонента есть спека
в `ds-component-spec` (audit уже отражён в самой спеке) и в репозитории
есть старая разметка/классы, которые физически реализуют роль этого
компонента, но не признаны им официально. Нужен постепенный, проверяемый
перенос — не одноразовый find & replace по всему сайту.

**Когда НЕ использовать:** для первичной идентификации компонента —
это `ds-component-audit`; для написания самой спеки — `ds-component-spec`.

**Важно — это два разных порога, не один:**
- **Старт Discovery/Pilot** — спека компонента **существует**, `stage:
  draft` допустим (Discovery/Pilot идут read-only-совместимо, с явной
  пометкой черновика).
- **Старт Rollout** — строже: спека компонента **и всех**
  `related_components` должна быть `stage: final`, `open_questions: 0`.

Подробно — раздел 4, «Rollout readiness», и Шаг 0.1 (Порог 1/Порог 2)
в SKILL.md.

## 2. Входы процесса

| Вход | Источник |
|---|---|
| **Component spec** | `memory/ds-component-spec/log.*.json` — `stage`, `open_questions` целевого компонента и связанных подкомпонентов |
| **Migration log** | `memory/ds-component-migration/log.*.json` — состояние текущей/прошлой сессии по этому компоненту |
| **Код/доки в scope** | пути, заданные при запуске (`docs/`, `storybook/` и т.п.) — что реально сканируется |
| **Rollout readiness / blockers** | производное значение: спека компонента и всех связанных подкомпонентов должна быть `stage: final`, `open_questions: 0` |

Без первых двух входов процесс не стартует — см. Шаг 0.1 в SKILL.md:
Порог 1 (нет спеки → стоп; спека `draft` → discovery/pilot разрешены
read-only) и Порог 2, строже (rollout заблокирован, пока спека
компонента и всех `related_components` не станет `final`).

## 3. Как это работает — простыми словами

Скилл ищет старую разметку, предлагает, во что она должна превратиться,
и переносит её маленькими проверяемыми шагами — вместо того чтобы
переписать весь сайт за один проход.

**Обычный порядок использования:**

1. Спросить «найди legacy-реализации компонента X» → скилл делает
   discovery + предлагает mapping, ничего не меняя.
2. Согласовать спорные места (если есть вопросы — не больше трёх,
   в формате A/B/C).
3. Попросить pilot на 1–2 файлах → посмотреть на реальный результат.
4. Отдельно, явно подтвердить batch rollout — только тогда меняются
   остальные файлы скоупа.
5. Проверить cleanup/follow-up — что осталось, что требует ручного
   разбора.

**Фазы коротко:** Discovery → Mapping → Pilot → Batch Rollout →
Cleanup/Follow-up. Подробное описание каждой — в SKILL.md, здесь —
только ориентир для человека.

**Где обязательно отдельное подтверждение:**
- переход к Pilot (после согласования mapping);
- переход к Rollout (после одобрения pilot) — это самый жёсткий гейт,
  один общий «ок» в начале разговора не покрывает его;
- любой `git commit`;
- `git push` — отдельно от commit, даже если commit только что одобрен.

**Команды, которые обычно пишет дизайнер/разработчик** — см. раздел 8.

## 4. Фазы — нормативная часть

### Status / Discovery

Читает scope, ищет маркеры legacy-паттерна, группирует находки
(точные совпадения / похожие паттерны / неоднозначные / вне скоупа).
Ничего не меняет. Может запускаться как `/migrate_component [Name]`
(первый заход) или `/migrate_component status` (перечитать состояние
активной сессии без пересканирования репозитория).

### Pilot

Переносит только 1–2 файла из точных совпадений, после того как mapping
подтверждён (вопросов не осталось). Показывает компактные «Было/Стало»
на файл. Риск слома структуры — файл помечается `manual_review`, не
форсируется.

### Rollout readiness

Не отдельная команда в SKILL.md, а производная проверка — Порог 2 из
Шага 0.1: спека целевого компонента **и всех** `related_components`
должна быть `stage: final`, `open_questions: 0`. Пока это не так —
discovery/pilot всё ещё допустимы read-only с пометкой `⚠️ spec draft`
(Порог 1 ниже Порога 2), а rollout заблокирован независимо от
подтверждений человека. `/migrate_component status` — самый дешёвый
способ проверить readiness без пересканирования кода.

### Rollout

Применяет уже подтверждённый mapping к прямым совпадениям, оставшимся
после pilot. Требует отдельное явное подтверждение, полученное **после**
того, как readiness подтверждена. Неоднозначные случаи не трогаются
эвристически, только по отдельному подтверждённому mapping. Похожие
паттерны, генерируемые JS (не статичным HTML), — отдельный именной gate
в SKILL.md (Phase 2/4, `deferred`): даже при визуальном совпадении с
direct replace такая группа не наследует общее подтверждение mapping,
нужен отдельный явный запрос на правку именно генерирующего кода.

### Partial completion / follow-up

Rollout не обязан закрывать 100% файлов скоупа за раз: часть групп может
остаться отложенной (см. раздел 6 — как это фиксируется в памяти). Это
нормальный, ожидаемый исход, а не незавершённая работа.

### Completion / closeout

SKILL.md формализует терминальное закрытие через пару полей, а не одно:
`phase: closed` **и** `rollout.status: completed`, присваиваемые
**одновременно, одним действием на Phase 5** (Cleanup) — если повторная
проверка остатков `legacy_markers` ничего не находит и follow-up список
пуст. До этого момента, сразу после rollout, `rollout.status` всегда
`completed_partial` — Phase 4 не может знать, что follow-up окажется
пустым, это подтверждает только Cleanup. Если что-то осталось — оба поля
остаются как есть (`phase: cleanup`, `rollout.status: completed_partial`),
сессия считается открытой до отдельного повторного запуска
`/migrate_component cleanup`.

## 5. Гейты подтверждения

- **Commit отдельно от push.** Даже одобренный коммит не пушится
  автоматически — `git push` подтверждается отдельной репликой.
- **Rollout — только после явного подтверждения**, отдельного от
  одобрения pilot. Общее «ок» в начале сессии не переносится на rollout.
- **Неоднозначные паттерны не мигрируются эвристически.** Если группа
  помечена `ambiguous` и решение не подтверждено человеком — она либо
  остаётся нетронутой, либо уходит в отдельный `ds-component-audit`
  (Шаг 0.2 SKILL.md), но никогда не мигрируется «по аналогии».
- **JS-generated «похожие паттерны» не меняются без отдельного
  подтверждения.** Формализовано в SKILL.md v1.2.0 (Phase 2, «Отдельный
  gate — группы, генерируемые JS»): даже если визуальная форма совпадает
  с точным паттерном, изменение генерирующего JS-кода — отдельное
  решение, группа остаётся `deferred`, не наследует общее подтверждение
  mapping и не входит в rollout автоматически (Phase 4).

## 6. Memory log — минимальный набор полей

Файл: `memory/ds-component-migration/log.<имя>.json`, один файл на
человека (как везде в репо), список сессий по `id`.

| Поле | Назначение |
|---|---|
| `component` / `related_components` | цель миграции + связанные подкомпоненты (их спеки тоже проверяются — Порог 2, Шаг 0.1) |
| `phase` | текущая фаза сессии, закрытый enum, см. ниже |
| `discovery.groups` | закэшированные группы находок — переиспользуются, чтобы не пересканировать репозиторий (см. `scope_signature`) |
| `mapping.status` / `mapping.decisions` | подтверждён ли mapping, и что решено по каждой группе |
| `pilot.status` / `pilot.files` | какие файлы пилотировались и с каким результатом, закрытый enum, см. ниже |
| `rollout.status` | закрытый enum, см. ниже |
| `rollout.blocked_reason` | текущая причина блокировки, `null` если снята |
| `rollout.blocker_history` | что было заблокировано и чем/когда разрешилось — не затирается при снятии блокировки |
| `cleanup.follow_up` | список того, что осознанно не мигрировано в этой сессии |

**Закрытый enum статусов** (SKILL.md v1.2.0, раздел «Память»):

- `phase`: `discovery` → `mapping` → `pilot` → `rollout` → `cleanup` →
  `closed` (терминальное).
- `pilot.status`: `not_started` / `completed_pending_approval` /
  `approved`. Без `blocked`/`ready` — Pilot не блокируется Порогом 2.
  Значение `scoped_not_started`, встречавшееся раньше, объединено с
  `not_started` — выбранный scope виден по `pilot.files`/
  `discovery.pilot_candidates`, отдельный статус для этого избыточен.
- `rollout.status`: `not_started` / `blocked` / `ready` /
  `completed_partial` / `completed`. Отличается от `pilot.status`,
  потому что Rollout (в отличие от Pilot) блокируется Порогом 2.

**Partial vs полное завершение.** `completed_partial` присваивается
сразу по итогам Phase 4 — это всегда первое, что видно после rollout,
даже если по факту скоуп закрыт целиком: Phase 4 не проверяет остатки
легаси и не строит follow-up, это делает только Cleanup. `completed`
(терминальное) и `phase: closed` присваиваются **одновременно, одним
действием на Phase 5** — не раздельно и не на Phase 4. Условие:
`cleanup.follow_up` пуст и остатков `legacy_markers` не найдено.

**Как фиксировать partial completion:** `rollout.status: "completed_partial"`
+ явный список изменённых файлов (`rollout.files`) + отдельные списки
того, что осталось нетронутым по причине (`deferred_not_touched` —
similar_pattern, `out_of_scope_untouched` — ambiguous/другой компонент).

## 7. Safe vs Ambiguous

**Safe match (direct replace):** маркер legacy-паттерна встречается в
контексте, однозначно соответствующем роли canonical-компонента;
форма совпадает с описанной в спеке (например `thead` + повторяющиеся
`tbody`-строки для `Table`/`TableRow`). Такие случаи допускают перенос
без дополнительных вопросов — сначала в Pilot, затем в Rollout.

**Ambiguous case:** та же CSS-обёртка/маркер, но другая внутренняя форма
или назначение (пример: та же `.table-wrap`, но одна пара `th`+`td` на
строку без `thead` — это оказался паттерн вывода метаданных компонента,
а не табличные данные). Не мигрируется молча — задаётся вопрос (максимум
3, формат A/B/C) до любых изменений.

**Уходит в отдельный audit:** если неоднозначный случай при ближайшем
рассмотрении не относится к целевому компоненту вообще (другая роль,
другой возможный canonical-компонент) — он выводится из скоупа текущей
миграции и фиксируется как повод для отдельного запуска
`ds-component-audit`, а не решается внутри сессии миграции (Шаг 0.2
SKILL.md, раздел «Разделение ответственности»).

## 8. Примеры типичных запросов к Cursor

- «`/migrate_component Table`. Discovery. Scope: `docs/`, `storybook/`.
  Legacy-маркеры: `.table-wrap`. Ничего не менять — только найти и
  сгруппировать.»
- «Подтверждаю mapping. Запускай Phase 3: `/migrate_component pilot`
  только для `typography.html` и `colors.html`. Rollout не трогать.»
- «Проверь, что сейчас мешает full rollout для Table migration — коротко,
  без пересказа истории, ничего не меняя.»
