# Component Audit — Guide — v1.0.0

> Статус: Draft · v1.0.0

---

## 1. Назначение

Гайд объясняет процесс определения идентичности UI-компонента по
screenshot или Figma-ссылке: уже есть такой в системе (Match), нужно
завести новый (New), неясно (Ambiguous), или вход вообще не компонент
дизайн-системы (Not a DS component).

**Когда использовать `ds-component-audit`:** есть визуальный вход
(screenshot или Figma-ссылка) на UI-элемент, и неясно — уже описан ли он
в системе, нужен ли новый компонент, или это вариант/состояние
существующего. Это всегда первый шаг, до написания спеки и до любой
миграции разметки.

**Когда НЕ использовать:** для написания самой спецификации — это
`ds-component-spec` (audit вердикт не заменяет спеку, только даёт
идентичность и уровень); для переноса legacy-разметки на уже
утверждённый компонент — это `ds-component-migration`. Audit
компонент **не** трогает код и не пишет документацию.

---

## 2. Когда НЕ использовать audit, а когда нужен другой шаг

| Ситуация | Нужен |
|---|---|
| Есть визуальный вход, неясна идентичность компонента | `ds-component-audit` (этот процесс) |
| Вердикт audit согласован, нужна полная спецификация (токены, слоты, состояния, реализация на 3 платформах) | `ds-component-spec` |
| Спека уже есть (`stage`), в репозитории есть старая разметка/классы, физически реализующие роль этого компонента | `ds-component-migration` |
| Внутри миграции найден паттерн, не относящийся к целевому компоненту вообще (другая роль, другой возможный canonical-компонент) | отдельный запуск `ds-component-audit` — миграция не решает это внутри себя (`ds-component-migration-guide.md`, раздел 7) |

Audit и migration могут вызывать друг друга **в одном направлении**:
migration выводит неоднозначные вне-скоуп случаи в отдельный audit;
обратной формализованной связи (audit → migration напрямую) в
`ds-component-audit/SKILL.md` нет — audit передаёт хендофф только в
`ds-component-spec` (раздел 5 ниже). Миграция становится возможной
только после того, как по спеке компонент дошёл до `stage: final`.

## 3. Входы процесса

| Вход | Источник |
|---|---|
| **Screenshot или Figma-ссылка** (обязателен) | вложение к команде `/audit_component`; для Figma дополнительно `source_type: frame \| component_instance` |
| **Существующие компоненты** | `docs/storybook/components/*.html` — база для сравнения на Шаге 4 |
| **Существующие спеки** | `memory/ds-component-spec/log.*.json` — cross-check на Шаге 7 (открытые вопросы по тому же компоненту) |
| **Прошлые аудиты** | `memory/ds-component-audit/log.*.json` — проверка повторного входа на Шаге 8 (`proposed` / `approved` / `rejected`) |
| **Категории компонентов** | `skills/_shared/component-categories-guide.md` — только имя категории, не влияет на вердикт уровня |
| **Архитектурные уровни** | `skills/_shared/ds-component-architecture-guide.md` — 4-уровневая модель для Шага 4 |
| **Open questions / blockers** | не входной артефакт — формируются по ходу процесса (Шаг 9.5), максимум 3 за раз, до вердикта |

Без screenshot/Figma-ссылки процесс не стартует — команда без вложения
получает запрос прикрепить материал и не запускает вердикт (Шаг 1).

## 4. Как это работает — простыми словами

Скилл смотрит на картинку или Figma-фрейм и отвечает на один вопрос:
«это уже есть в системе, это новое, или непонятно». Дальше — либо
закрывает вопрос сразу (явный Match/New), либо явно спрашивает, если
не уверен, вместо того чтобы гадать.

**Важно: это не многофазная сессия, как `ds-component-migration`.**
Один запуск `/audit_component` (или один согласованный батч
скриншотов) — это один проход от входа до вердикта, зафиксированного в
памяти. Нет отдельных команд вида `pilot`/`rollout`/`status` — весь
процесс укладывается в одно взаимодействие, максимум с одним раундом
уточняющих вопросов перед финальным выводом.

**Обычный порядок использования:**

1. Прикрепить screenshot/Figma-ссылку с командой `/audit_component`.
2. Скилл определяет платформу, тип кадра, проверяет декомпозицию
   (нет ли внутри повторяющегося паттерна вроде строки таблицы) —
   без вердикта на этом этапе.
3. Если есть неоднозначность — скилл задаёт до 3 вопросов **до**
   вердикта, с вариантами ответа (a/b/c).
4. Скилл выдаёт вердикт: Match / New / Ambiguous / Not a DS component /
   Cannot analyze input / Platform scope extension — с confidence и
   обоснованием.
5. Согласовать вердикт → скилл фиксирует запись в память со статусом
   `approved` или `rejected`.
6. При необходимости — отдельно, явно запросить structured handoff в
   `ds-component-spec` (не запускается автоматически).

**Где нужны отдельные подтверждения:**
- любая неоднозначность (два близких Match-кандидата, неочевидная
  декомпозиция, State vs Variant) — вопрос **до** вердикта, не после;
- финальный выбор при конфликтующих кандидатах или дедупликации батча
  — всегда решение Principal Designer, не скилла;
- запуск `ds-component-spec` после вердикта — отдельное явное действие.

**Команды, которые обычно пишет дизайнер** — см. раздел 9.

## 5. Нормативная часть по фазам

Ниже — логические стадии внутри одного прохода `/audit_component`, не
отдельные команды (см. раздел 4). Ссылки на шаги — в
`ds-component-audit/SKILL.md` v1.3.0.

### Discovery / приём входа (Шаг 1–2)

Фиксирует `source` (screenshot/figma) и, для Figma, `source_type`
(frame/component_instance — влияет на надёжность вердикта). Нечитаемый
или недоступный вход → отдельный вердикт **Cannot analyze input**,
обработка останавливается здесь же. Затем определяется платформа(ы) по
визуальным паттернам — предположение показывается на подтверждение, не
угадывается молча при неочевидности.

### Classification (Шаг 3, 3.5)

Определяется тип кадра: единый композитный виджет (вердикт по целому)
или несколько независимых компонентов в одном кадре (разложить и
вести по каждому отдельно); неочевидность — явный вопрос, не решение
скилла. Отдельно, **до** вердикта — Decomposition Check: если внутри
входа есть повторяющийся структурный паттерн (строка таблицы, ячейка,
карточка), проверяется, встречается ли он где-то ещё отдельно от
родителя. Есть свидетельства → аргумент за выделение отдельного
компонента (пример: `Table` → выделен `TableRow`, см. `audit-002`/
`audit-003` в `memory/ds-component-audit/log.sergej.json`). Нет
свидетельств → не решается самостоятельно, уходит в открытый вопрос.
Результат всегда явный в выводе: «Decomposition needed: yes/no».

### Mapping — Match / New / Ambiguous (Шаг 4–8)

Основной вердикт сравнивает вход по роли и составу (не только по
внешнему виду) с `docs/storybook/components/*.html` и записями памяти.
Порог для **New** — высокий, при сомнении дефолт — **Ambiguous**.
Дополнительные проверки внутри этой стадии:
- **Naming collision** (Шаг 5, только при New) — конфликт имени со
  всей системой, не только смысловое совпадение.
- **State vs Variant** (Шаг 6, только при Match с дополнением) — явно
  разделяется новое состояние vs новый вариант, без общего
  «дополнить».
- **Cross-check со spec-логом** (Шаг 7) — если там уже есть
  `open_questions` по этому же компоненту, это упоминается в выводе.
- **Проверка памяти на повторный вход** (Шаг 8) — `rejected` не
  предлагается повторно без новых оснований; `approved` трактуется как
  Match с высокой confidence со ссылкой на прошлое решение; `proposed`
  — как открытый вопрос.

### Ambiguity handling / questions (Шаг 9, 9.5, визуальное подтверждение)

Дедупликация батча (Шаг 9): одинаковые по вердикту входы объединяются
в одно предложение с построчными отличиями, без усреднения; входы с
другим вердиктом не подгоняются под большинство. Уточняющие вопросы
(Шаг 9.5) задаются **до** вердикта, максимум 3, с вариантами ответа —
запрещено сначала выносить вердикт, а потом просить подтверждение.
Вердикты, требующие решения человека (Ambiguous, конфликт двух
Match-кандидатов, Platform scope extension с расхождением, неочевидный
State vs Variant), обязаны сопровождаться визуальным подтверждением
(приложенный скриншот/crop, точный HTML+CSS для repo-элементов, либо
явная пометка «визуальный рендер не получен» с текстовым описанием).

### Handoff to spec (Шаг 10 + Structured handoff)

Финальный вердикт выдаётся по фиксированному шаблону (Шаг 10) с
обязательными секциями «Уточняющие вопросы», «Вердикт», опционально
«Состав предложения» / «Визуальное подтверждение» / «Подробности» /
«Пропущенные проверки», и «Следующий шаг». После согласования вердикта
формируется structured handoff — JSON-блок, совместимый по полям с
`memory/ds-component-spec/log` (`component`, `level`, `category`,
`verdict`, `confidence`, `platforms`, `source`). Запуск
`ds-component-spec` — отдельное явное действие, не продолжение сразу
после вердикта.

**Handoff в `ds-component-migration` напрямую не описан** в
`ds-component-audit/SKILL.md` — миграция становится возможной только
после того, как компонент прошёл через `ds-component-spec` и достиг
нужной стадии (`ds-component-migration-guide.md`, раздел 1). ⚠️ open
decision: нужен ли отдельный structured handoff audit → migration для
случая, когда компонент уже recognized (Match, `approved`), но ещё не
специфицирован явно.

### Completion / closeout

⚠️ **Не формализовано отдельной фазой**, в отличие от
`ds-component-migration` (там есть явный `phase` enum с терминальным
`closed`). У audit нет понятия многошаговой сессии — «закрытие»
происходит одним действием: запись в память со статусом `approved`
или `rejected` (раздел 8). Open decision: нужен ли отдельный
`status`/`phase` для отслеживания «вердикт согласован → handoff в spec
выполнен → компонент специфицирован», или текущей модели (одна запись
= один законченный аудит, дальнейшее состояние отслеживается уже в
`memory/ds-component-spec/log`) достаточно.

## 6. Гейты

- **Не признавать новый canonical-компонент без достаточных оснований.**
  Порог для New высокий; при сомнении дефолт — Ambiguous, не New
  (Шаг 4).
- **Неоднозначные случаи не закрываются эвристически.** Любая
  неоднозначность (уровень, декомпозиция, категория, нейминг,
  конкурирующие Match-кандидаты) — явный вопрос до вердикта (Шаг 9.5),
  с обязательным визуальным подтверждением там, где решение остаётся
  за человеком.
- **Variation существующего компонента не оформляется как новый
  молча.** State vs Variant (Шаг 6) и Variant/state vs new composite
  (Шаг 4) требуют явного разделения с обоснованием, а не общего
  «дополнить компонент».
- **Недостаточно данных → вопрос, не догадка.** Неочевидная платформа,
  тип кадра или уровень архитектуры — проговариваются явно (Тон,
  Встроенные правила уровней), скилл не угадывает молча.
- **Legacy-компонент не дополняется тихо.** Match на компонент со
  статусом Legacy — явное предупреждение «предназначен на замену»,
  вместо тихого добавления в устаревшую сущность (Шаг 4).
- **`rejected` не предлагается повторно без новых оснований** (новый
  источник, другая платформа, изменённый визуальный признак) — Шаг 8.

## 7. Safe vs Ambiguous

**Safe (уверенный Match или New):**
- **Match, high confidence** — роль и состав однозначно совпадают с
  уже описанным компонентом, нет конфликта с Legacy или platform
  scope, нет второго близкого кандидата.
- **New, high confidence** — после проверки декомпозиции и обоих
  близких кандидатов (если были) явно нет подходящего Match; naming
  collision проверен, конфликтов нет.

**Ambiguous (требует подтверждения):**
- Два близких Match-кандидата с сравнимой confidence, и порог для New
  не подтверждён (пример из SKILL.md: похоже и на Badge, и на Chip).
- Decomposition Check без свидетельств использования паттерна отдельно
  от родителя — открытый вопрос, не решается самостоятельно.
- Неочевидный тип кадра (единый виджет vs несколько независимых
  компонентов в одном кадре).
- Platform scope extension с поведенческим расхождением, где под тем
  же именем может скрываться разное поведение на новой платформе.
- Неочевидный State vs Variant при частичном совпадении с Match.

**Not a DS component:** отдельный вердикт, не разновидность Ambiguous
— применяется, когда сопоставлять вход с системой не имеет смысла в
принципе (случайный скрин, сторонний сайт, нерелевантный кроп), без
предложения что-либо создать или дополнить.

## 8. Memory log

Файл: `memory/ds-component-audit/log.<имя>.json`, один файл на
человека, список записей (не сессий с фазами — раздел 5).

| Поле | Назначение |
|---|---|
| `id` | идентификатор записи (`audit-NNN`) |
| `component` | имя компонента (если применимо) |
| `verdict` | `match` / `new` / `ambiguous` / `not-a-ds-component` / `platform-scope-extension` |
| `level` | уровень архитектуры (`item` / `surface-view` / `structural-view` / `layout`), `null` если не определён |
| `category` | из `component-categories-guide.md`, `null` если не применимо |
| `confidence` | `high` / `medium` / `low` |
| `platforms` | список платформ, к которым относится вердикт |
| `source` / `source_type` | `screenshot` \| `figma`; для figma — `frame` \| `component_instance` |
| `status` | `proposed` / `approved` / `rejected` (см. ниже) |
| `date`, `notes`, `_owner` | дата, свободный текст с обоснованием и открытыми расхождениями, автор |

**Поле `status`** (не формальный closed enum, как в migration, но
используется строго по смыслу):
- `proposed` — вердикт предложен, ещё не согласован;
- `approved` — согласовано, финальное решение (защищает от повторных
  вопросов при совпадении на Шаге 8);
- `rejected` — отклонено, нужны новые основания для повторного
  предложения (Шаг 8, гейт выше).

**Открытые вопросы и расхождения**, не закрытые в моменте, фиксируются
текстом в `notes` — отдельного структурированного поля
`open_questions`, как в `ds-component-spec` (числовой счётчик), в
audit-схеме нет. ⚠️ open decision: стоит ли унифицировать оба лога
одинаковым полем `open_questions`, чтобы `ds-component-migration`
могло машинно проверять готовность так же, как оно уже делает со
спеками (`ds-component-migration-guide.md`, раздел 1, Порог 2) — на
момент этой версии гайда unresolved-моменты по audit читаются только
человеком из текста `notes` (пример — `audit-003` в
`memory/ds-component-audit/log.sergej.json`, где явно зафиксировано
расхождение в правилах нейминга без структурированного флага).

**Синхронизация** — по `skills/_shared/git-workflow.md`:

```bash
git pull --rebase
git add memory/ds-component-audit/log.<имя>.json
git commit -m "audit([ComponentName]): [match|new|ambiguous] verdict"
git push
```

## 9. Примеры типичных запросов к Cursor

- «`/audit_component` [прикреплён screenshot Badge]» — единичный вход,
  ожидается Match с высокой confidence, если компонент уже
  задокументирован.
- «`/audit_component` [4 скриншота вариантов Badge stable/draft/core/
  semantic]» — батч, ожидается дедупликация в одно предложение с
  построчными отличиями по вариантам (Шаг 9).
- «`/audit_component` [скриншот таблицы с повторяющимися строками]» —
  ожидается Decomposition Check до вердикта: возможен вердикт New по
  компоненту целиком плюс отдельный кандидат на строку, если строка
  встречается отдельно в другом месте сайта (по аналогии с
  `Table`/`TableRow`, `audit-002`/`audit-003`).
