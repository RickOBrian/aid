# Работа с библиотекой Figma

> Статус: Draft · v0.4.0 · обновлено 2026-10-22

---

## 1. Назначение

Протокол описывает, как идёт любая задача, которая меняет библиотеку Figma
продукта. Он не заменяет гейты и стандарты объектов, а задаёт порядок, в
котором их проходят, и точки, где нужно «да» PD.

**Охват.** Объект × операция:

| | Создать | Править | Переименовать | Удалить |
|---|---|---|---|---|
| Компонент | ✓ | ✓ | ✓ | ✓ |
| Токен | ✓ | ✓ | ✓ | ✓ |
| Стиль | ✓ | ✓ | ✓ | ✓ |
| Иконка | ✓ | ✓ | ✓ | ✓ |
| Экран | позже, раздел 7 | | | |

Продукт — любой из реестра продуктов (`products/<id>/product.json`). Файлы
и папки продукта в Figma — `figmaFolders` и `figmaFiles` того же файла.

**Граница.** Задача всегда заканчивается в Figma. Страница в Presentbook и
код — отдельные задачи.

**Кто работает.** Библиотеки продуктов правят и публикуют инженеры по
правилам владения библиотекой (корневой `CLAUDE.md`, «Только PD» п.4;
`docs/hub/ORCHESTRATION.md` §9; «Решения PD»). Протокол не назначает
владельца, он задаёт порядок для любого исполнителя.

---

## 2. Вход

Задачу приносит PD. Вход бывает четырёх видов, и от него зависит, сколько
согласований будет до сборки.

| Вход | Что берётся | Дополнительная точка согласования |
|---|---|---|
| Ссылка на макет | Фрейм, значения, привязки; вхождения в Handoff исполнитель находит сам | — |
| Ссылка на объект | Структура, свойства, ключ | — |
| Скрин | Только визуал; каждое значение подбирается по токенам | Анкета значений (шаг 6) |
| Текст | Описание задачи | Набросок до спецификации |

Чем слабее вход, тем раньше первое согласование.

**Объект на входе — экземпляр, не мастер** (решение PD 2026-10-21). Если
вход — компонент, в аудит приносится экземпляр того компонента, на основе
которого собирали, а не мастер-компонент. Если исходный файл не
опубликован как библиотека и экземпляр вставить нельзя, — скрин и ссылка
на node экземпляра.

**Вход — не образец.** Объект по ссылке может быть собран неверно. Его
структура и свойства проходят аудит (шаг 3) так же, как скрин.

## 3. Шаги

| # | Шаг | Итог | Согласование |
|---|---|---|---|
| 1 | Вход → задача | Продукт, объект, операция | — |
| 2 | Контекст | Файлы продукта по `product-context` | — |
| 3 | Аудит входа | Пейдж аудита в Figma (раздел 3.1) | «да» PD |
| 4 | Поиск | Вердикт: есть, аналог, нет | — |
| 5 | Влияние | Список затронутых мест | — |
| 6 | Предложение | Предложение по гейту объекта и одна анкета | «да» PD |
| 7 | Изменение | Правка в черновике или ветке файла, без публикации | — |
| 8 | Проверка | Отчёт «правило · уровень · статус» и снимок «было · стало» | — |
| 9 | Публикация | Публикация и запись «Не опубликовано» в чейнжлог | — |

**Шаг 2. Контекст.** Гейт `product-context`: продукт подтверждён до любой
работы. Объекты другого продукта не подставляются. Перенос объекта между
продуктами — только по «да» PD и через гейты целевого продукта.

**Шаг 3. Аудит входа.** Задача начинается с аудита, а не со сборки «как
есть». Аудит только читает (`audit-gate`), отчёт строится по
`ds-component-audit-guide`. В отчёте:

- что есть и как собрано;
- ошибки сборки;
- предложения по архитектуре и разбиению на компоненты
  (`ds-component-architecture-guide`);
- карта «значение → токен» с пробелами (`token-integrity`);
- вопросы, а также идеи и предложения, о которых PD не спрашивал.

Аудит — отдельная точка согласования. Без «да» PD по отчёту шаг 6 не
начинается. Отчёт оформляется в Figma по разделу 3.1. Для компонента
шаги идут этапами флоу (раздел 3.2).

### 3.1 Оформление аудита в Figma

Решение PD 2026-10-21: аудит любого компонента оформляется по одним
правилам.

**Что такое аудит.** Итог, который показывают дизайнеру перед
полноценной сборкой компонента. Промежуточные решения, принятые до
аудита, в него не входят: ни отдельным блоком или фреймом «Решения PD»,
ни пометками «решение PD». На пейдже — только факт: «Caption 2»,
«Убран».

**Пейдж.** Отдельный пейдж в целевом файле библиотеки с именем
`🚧 <Компонент> · аудит`. Слово — «аудит», не «варианты токенов» и не
другое. 🚧 означает, что аудит идёт.

**Блоки.** Колонка карточек в одном стиле. Тексты — для человека;
технические детали — строкой «Для инженера» внизу блока.

| # | Блок | Что в нём |
|---|---|---|
| — | Обложка | Как читать пейдж и содержание |
| 0 | Вход | Экземпляр исходного компонента (не мастер), скрин или иные вводные — раздел 2 |
| 1 | Что увидели в макете | Что есть и как собрано, ошибки сборки |
| 2 | Токены: варианты и рекомендация | Карта «значение → токен» с пробелами. При сомнении — варианты рядом с цветом из макета, выбор по виду. Новый визуал — хексом-допущением (раздел 3.5). Новые токены — только после «да» PD (шаг 6) |
| 3 | Состояния и интерактив | Не статикой, а прототипом: interactive components, переключение, Smart Animate |
| 4 | Сборка | Архитектура и разбиение на компоненты |
| 5 | Трудные случаи | Минимальный вьюпорт, длинные подписи, максимум элементов и другие (`component-standards.md` §10) |
| 6 | Было → Стало | Компонент в боевом макете, рядом — исходный экран |
| 7 | Что ждёт решения по аудиту | Вопросы, идеи и предложения, о которых не спрашивали |

**Две темы.** Все блоки — в светлой и тёмной теме, прототип тоже.

**Вьюпорт.** Минимальный вьюпорт аудита — 360: столько дают вендоры
Android. 320 не используется.

**Иконки.** Иконки из макета стоят рядом как кандидаты в библиотеку,
вместе с похожими из библиотеки продукта.

**Блок 7.** Каждый вопрос — с вариантами а, б, в; рекомендация отмечена;
ответ — строкой вида «1б, 2а». У каждого вопроса — ссылка-якорь
(гиперссылка на узел) на слайд, где пункт разобран. Заголовок — «Что
ждёт решения по аудиту», не «Что ждёт решения PD».

**Аудит — не сборка** (PD 2026-10-22). Аудит — место принятия решений:
посмотреть, как выглядит. Поэтому в нём допустимы рабочие компоненты,
прототипы и пример в боевом макете. Как выглядит сборка — решается на
предсборке (раздел 3.2).

**Статус пунктов.** У каждого вопроса блока 7 — бейдж статуса:

| Статус | Значит |
|---|---|
| Ждёт решения | Вопрос задан, ответа нет; указан хозяин — Standards, куратор или дизайнер |
| Согласовано куратором | Архитектура решена, визуал ждёт дизайнера |
| Ждёт дизайнера | Визуал на выборе у дизайнера |
| Принято | Решено всеми, кого касается |
| Снято | Вопрос отпал |

Набор статусов уточняется на прогонах.

### 3.2 Флоу компонента

Первая итерация (PD 2026-10-22): флоу дописывают Designer, Standards и PD
по ходу прогонов. Если практика расходится с флоу, правят флоу, а не
скрывают отклонение.

**Роли.**

| Роль | Кто | Решает |
|---|---|---|
| Исполнитель | AI-инженер Designer · Components или инженер | Готовит предаудит, аудит, предсборку, сборку; вносит правки; предлагает свои идеи без запроса |
| Куратор стандартов | Standards | Соответствие стандартам: принимает аудит и сборку по стандартам до приёмки куратором; отход от стандарта — только записью исключения (standards-11); новое правило — тоже через Standards |
| Куратор | PD или инженер-человек, который ведёт задачу | Архитектура задачи: сборка, токены, имена — в рамках стандартов |
| Дизайнер продукта | Человек | Визуал: оттенок, иконка, вид. Последнее слово по визуалу |
| Designer · <продукт> | AI-инженер, чат под задачу в папке продукта | Дизайн-задачи продукта: иллюстрации, визуал, гайды. Компонент в библиотеку — не его зона: нужен компонент — флоу компонента с Designer · Components |
| Исполнители других зон | Presentbook и другие | Подключаются, только если нужны (витрина, иконки на витрине). Чужую зону исполнитель не правит, а зовёт её исполнителя |
| Разработчик продукта | Человек | Компонент в коде по Figma и Presentbook |

Зоны не пересекаются: дизайнер решает, **какой** оттенок, куратор —
**как** токен называется и заводится, Standards — **соответствует ли**
это стандарту. Ответы дизайнера куратор передаёт
исполнителю текстом.

**Комментарии Figma — к сведению.** Слова PD 2026-10-22: «Ты можешь их
принимать к сведению, но в таких задачах никогда не вноси изменения не
согласовав со мной». Правка аудита и сборки — только после «да» в чате.

**Этапы.**

| # | Этап | Участники | Итог | Пейдж | Шаги раздела 3 |
|---|---|---|---|---|---|
| 1 | Заявка | Куратор | Задача на доске: номер, тип, предложенная версия (раздел 3.3); вход, продукт | — | 1, 2 |
| 2 | Предаудит | Исполнитель и куратор; дизайнер — по мелким вопросам | Договорились обо всём, о чём можно; в аудит не идёт | — | 4, 5 |
| 3 | Аудит | Исполнитель; другие зоны — если нужны | Итог и нерешённые вопросы, у каждого хозяин и статус | `🚧 <Компонент> · аудит` | 3 |
| 4 | Приёмка аудита | Standards, затем куратор, дизайнер, исполнитель | Все пункты — «Принято» или «Снято» (раздел 3.4) | тот же | 6 |
| 5 | Предсборка | Исполнитель и куратор | Как выглядит и из чего состоит пейдж сборки | — | — |
| 6 | Сборка | Исполнитель | Компонент, гайд с трудными случаями, итоги аудита секцией рядом | `🚧 <Компонент> · сборка` | 7 |
| 7 | Приёмка сборки | Standards, затем те же трое, те же зоны | «Принято» | тот же | 8 |
| 8 | Публикация | По «Кто работает» (раздел 1) | Библиотека опубликована; 🚧 снят | — | 9 |
| 9 | Витрина | Presentbook делает, куратор контролирует | Компонент в Presentbook | — | отдельная задача |
| 10 | Готов к разработке | Разработчик продукта | Забирает Figma и Presentbook | — | — |

Попутные объекты (раздел 3.6) проходят свой цикл до сборки. Итог флоу —
«готов к разработке»; релиз в коде продукта — вне флоу.

Публиковать ли библиотеку и писать ли в чейнжлог Figma исполнителю-AI —
не решено: пробел 8.

### 3.3 Тип задачи и версия

Задача заводится на доске до предаудита, с номером и типом. Версия
ведётся с первого дня как предложение; итоговая — только на границе
релиза (`release-gate`, `component-gate`).

| Тип | Что | Версия |
|---|---|---|
| Создание | Новый компонент | `proposedVersion: 1.0.0`, `proposedSemVerImpact: initial` |
| Развитие | Вариант, состояние, слот; правка визуала или токена; переименование, удаление | Текущая → предложенная по `semver-guide`: вариант, состояние, слот — minor; визуал или токен без смены API — patch; удаление и переименование, ломающее API, — major |

Предложение — pending-запись `changes/<продукт>/pending/component-<slug>.json`.
Импакт уточняется на приёмке аудита и сборки: решение меняет API — меняется
и предложенная версия.

### 3.4 Приёмка аудита

Сначала аудит проверяет Standards — по стандартам; замечания исполнитель
вносит до разбора с куратором. Отход от стандарта, который остаётся, —
запись исключения, а не пункт «Принято».

1. Исполнитель присылает полный список вопросов аудита — коротко, со
   ссылкой на блок в Figma.
2. Разбирают ответы по каждому; исполнитель уточняет, если нужно.
3. Куратор добавляет новые вводные, если есть.
4. Договорённости фиксируются в чате. По команде куратора исполнитель
   вносит их в аудит, куратор несёт аудит дизайнеру.
5. Есть дополнения — повторяют нужные пункты. Всё «Принято» или «Снято» —
   этап 5, предсборка.

### 3.5 Хекс как допущение

Решение PD 2026-10-22: в аудите новый визуал показывается **хексом**.
Аудит проверяет, как выглядит; токен, заведённый заранее, при отказе
пришлось бы удалять или править. Хекс в аудите помечен как допущение.

Визуал принят дизайнером → **сразу** предложение токена по
`token-change-gate`; токен заводится до сборки. В сборке хексов нет — там
действует `token-integrity` без исключений.

### 3.6 Попутные объекты

Иконки, токены и стили, нужные компоненту, проходят свой короткий цикл по
гейту объекта (раздел 4): добавление в библиотеку объекта → чейнжлог этой
библиотеки → публикация → витрина, если нужна. До сборки компонента, по
«да» куратора.

**Шаг 4. Поиск.** Точное совпадение → аналог по смыслу со сверкой по
ключу → снимок «было» → вердикт. Новый объект без поиска не создаётся
(`component-gate`, `token-integrity`).

**Шаг 5. Влияние.** Где объект используется: библиотека, Handoff, другие
компоненты. Для правки, переименования и удаления шаг обязателен.

**Шаг 6. Предложение.** По гейту объекта (раздел 4). Все пробелы — одной
анкетой. Если по токену есть сомнение, варианты показываются визуально,
рядом, и PD выбирает по виду, а не по тексту.

**Шаг 7. Изменение.** В черновике или ветке файла Figma, без публикации.

**Шаг 8. Проверка.** По стандарту объекта (раздел 4); для компонента — по
`component-standards.md` §15 и §15.1. Отчёт — правило, уровень (`must`,
`should`), статус; снимок «было · стало».

**Шаг 9. Публикация.** Публикация библиотеки и запись «Не опубликовано» в
таблицу чейнжлога Figma, без версии
(`docs/standards-alpha/WORKING-RULES.md` §5). Версия и changelog — только
на границе релиза по `release-gate`.

## 4. Объект → гейт и стандарт

| Объект | Гейт | Стандарт |
|---|---|---|
| Компонент | `component-gate` | `component-standards.md` §15, §15.1 |
| Токен | `token-change-gate`, `token-integrity` | `token-rules`, `semantic-*-tokens-guide` |
| Стиль | `token-change-gate` | Типографика — `semantic-typography-tokens-guide`; тени, стекло, градиенты — **нет** (пробел 3) |
| Иконка | **нет** (пробел 2) | **нет** (пробел 2) |
| Экран | **нет** (пробел 4) | **нет**; есть только проверка `ds-ui-review` |

### 4.1 Компонент

Сверх `component-standards` для задачи в библиотеке (решения PD
2026-10-21):

- **Две темы.** Компонент собирается и показывается в светлой и тёмной
  теме.
- **Недостающие состояния** (pressed и другие) предлагаются по
  `component-standards.md` §8.3. Новые токены для них попадают в библиотеку
  только после «да» PD, а не сразу.
- **Гайд рядом с компонентом.** Результат задачи — собранный компонент и
  гайд для человека рядом с ним: пограничные случаи (маленький экран,
  длинный текст и другие, `component-standards.md` §10) и описание
  (`component-standards.md` §13). Формат гайда в Figma — пробел 6.

### 4.2 Токен

Значение без подтверждённого источника не используется (`token-integrity`).
Правка значения токена → список зависимых компонентов (шаг 5). Канон
значений — пробел 5.

## 5. Операции

| Операция | Что добавляется к шагам |
|---|---|
| Создать | Шаги 1–9 как есть |
| Править | Шаг 5 решает, ломает ли правка использование. Правка значения токена — список зависимых компонентов |
| Переименовать | Ключ объекта сохраняется. Ломается сверка с репозиторием и кодом: в шаг 5 входят записи о токене или компоненте в репозитории |
| Удалить | Только через устаревание: пометить → заменить во всех местах из шага 5 → удалить позже. Удаление — только с согласия PD. Порядок для Figma — пробел 1 |

## 6. Пробелы

Здесь стандарта пока нет. Протокол их не додумывает: исполнитель
останавливается и пишет вопрос в анкету шага 6.

1. **Устаревание и удаление объектов Figma.** `component-standards.md` §14
   написан для кода (пропы, предупреждение в разработке).
2. **Иконки:** гейт и стандарт. Канон имён — раздел «Иконки» в
   `naming-conventions`, общий с автопроверкой стандартов в CI.
3. **Стили:** тени, стекло, градиенты.
4. **Сборка экрана** (раздел 7).
5. **Канон значений токенов:** ADR-039 называет источником правды Figma,
   описание `figmaFiles` в `product.json` — репозиторий. Ждёт решения PD;
   до него расхождение Figma и репозитория — вопрос в анкету.
6. **Формат гайда для человека в Figma:** какие пограничные случаи
   обязательны и как гайд оформлен рядом с компонентом. Для аудита
   формат задан (раздел 3.1); для гайда рядом с собранным компонентом —
   нет.
7. **Пейдж аудита после сборки:** в архив или удалить — решают после
   сборки, правила пока нет.
8. **Публикация исполнителем-AI:** может ли AI-инженер публиковать
   библиотеку и писать в чейнжлог Figma по «да» куратора. Сейчас версия и
   чейнжлог библиотек Rider и Driver — за инженером-человеком (корневой
   `CLAUDE.md`, «Только PD» п.4). Ждёт решения PD.
9. **Шаблон аудита и автопроверка.** Карточки блоков и бейджи статусов —
   компонентами шаблона; проверка аудита и сборки скриптом перед приёмкой
   (токены, ночь, вьюпорт от 360, хозяин, якорь и статус у вопросов, вход —
   экземпляр, прототип проверен). PD согласен, формы пока нет.
