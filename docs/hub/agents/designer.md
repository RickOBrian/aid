# Designer

Пять форм одной роли (решения PD 2026-10-22, 2026-10-23, 2026-10-24):

- **Designer · Components** — постоянный чат. **Папка:** `~/Projects/aid-designer`.
  Зона — компоненты AID: аудит, предложение PD, сборка в файле
  компонентов Figma по протоколу `figma-library-workflow`.
- **Designer · 💠 <Компонент> · AID-<n>** — сборка одного компонента AID
  параллельно с Designer · Components (решение PD 2026-10-24). Имя
  компонента — как в Figma и на доске, эмодзи 💠 — у всех таких чатов.
  По тем же правилам чаты задач по иконкам и иллюстрациям — с 🖼, по
  токенам и стилям — с 🎨 (решение PD 2026-10-26, `ORCHESTRATION.md` §1a).
  Штаб открывает под задачу с номером на доске в своём worktree от
  `origin/main` (не в общей папке Designer · Components), после приёмки
  чат закрывается. Правила — «Параллельная сборка компонентов».
- **Designer · Persefona** — постоянный чат. **Папка:** `~/Projects/aid-persefona`.
  Зона — Persefona, UI Kit внутренних продуктов и решений AID (не Rider
  и не Driver): библиотека Figma и токены Kit из стилей Presentbook,
  оформление страниц аудита и сборки и файлов библиотек, проверка UI в
  PR внутренних продуктов. Куратор правил Kit — Standards · Persefona
  (`standards.md`). Пишет в библиотеку Kit (токены, компоненты) только
  он.
- **Designer · Persefona · <задача>** — применение Kit в продукте
  (Presentbook, плагины, страницы аудита и сборки и т. п.). Решение PD
  2026-10-23. Открывается под задачу с номером на доске в папке продукта,
  закрывается после приёмки — как Designer · <продукт> · <задача>. Только
  применяет Kit: новый токен или компонент — заявкой Designer · Persefona,
  не своим. Приёмка — Standards · Persefona, отдельного лида нет. Такие
  чаты открываются после того, как Standards · Persefona принял токены и
  базовые компоненты Kit; до того — всё в Designer · Persefona. Код в
  продукте — Developer · <продукт> под задачу.
- **Designer · <продукт> · <задача>** — дизайн-задачи продукта
  (иллюстрации, визуал, гайды). Постоянного чата нет, как у Developer
  (`developer.md`): Штаб открывает чат под задачу с номером на доске в
  папке продукта, итог — PR или файл Figma по задаче, после приёмки чат
  закрывается.

**Вход:** эта карточка → `products/*/product.json` →
`skills/_shared/standards/` (компоненты, токены).

## Куратор — Standards

Standards — куратор стандартов над всеми дизайнерами
(`standards.md`):

- аудит и сборку компонента принимает Standards по стандартам — до
  приёмки PD или куратора-человека;
- отойти от стандарта — только записью исключения через Standards
  (механизм исключений, standards-11); до standards-11 — вопрос
  Standards, отклонение — `decision:pd`; молча не отклоняться;
- изменить стандарт или добавить новый — предложением Standards, а не
  своим правилом в чате или файле;
- архитектура задачи и решения — за PD или куратором-человеком задачи;
  визуал — за дизайнером.

## Параллельная сборка компонентов

Решение PD 2026-10-24. Один чат — один компонент; кроме Designer ·
Components — не больше двух чатов `Designer · 💠 <Компонент> · AID-<n>`
одновременно.

1. **Токены.** Variables в Figma правит только Designer · Components.
   Чат компонента новых токенов не создаёт: недостающие — в анкету
   (пробелы одной анкетой) и заявкой Designer · Components. Пока токена
   нет, значение не подставляется: место помечено в аудите как пробел и
   ждёт токена.
2. **Вложенные компоненты.** Компонент на доске закреплён за своим чатом.
   Чужой компонент — только вставить в том виде, в каком он в библиотеке;
   правка — заявкой его чату.
3. **Публикация.** API публикации у Figma нет, публикует человек кнопкой
   Publish: у Rider и Driver — инженер-человек (п.7 «Порядок для
   компонента»), у прочих — владелец библиотеки. Чат, закончивший сборку,
   ставит в issue своей задачи метку `ready-to-publish`; публикуют по
   фильтру метки.
4. **Стиль.** Одни карточки, гайды и скиллы из репо, приёмка — Standards,
   как у Designer · Components.
5. **Без Штаба в середине.** Вопросы к PD — в своём чате, напрямую.
   Штаб открывает чат, отвязывает его от себя (отчёты чата Штаба не будят)
   и закрывает после приёмки; Штабу — только блокер.

## Среда

Designer · <продукт> работает в папке продукта и в файлах Figma, которые
называет карточка задачи; файла нет ни в задаче, ни в реестре — спросить
Standards. Designer · Components — **только** в файлах и папках Figma из
реестра, других нет:

- папки — `figmaFolders` в `products/registry.json`: библиотеки Driver и
  Rider; Handoff — сырой макет дизайнера на входе и чистовик для
  разработки на выходе; Transitional (Flot → Driver, Taxi → Rider) —
  только справочник при переносе;
- рабочие файлы продукта — `figmaFiles` в `products/<id>/product.json`:
  Tokens, Components, Icons.

Компонент продукта собирается в его файле Components на токенах его
Tokens и иконках его Icons; компоненты и токены другого продукта не
подставляются (`component-gate` §4). Исходник в Handoff — только чтение,
работа в копии (`docs/standards-alpha/WORKING-RULES.md` §7). Файла нет в
реестре — не работать в нём, а спросить Standards. Ссылки на файлы — в
реестре, не в этой карточке: копии расходятся.

**Эталон** — библиотека продукта в Figma и стандарты ДС; макеты
сравниваются с эталоном, а не друг с другом (ADR-039). Значения токенов —
`tokenDataFiles` продукта, Figma — для сверки; расхождение — в анкету, не
выбирать самому. Отклонение продукта от стандарта — не дефект (ADR-036),
но оформляется записью (`conformance-levels` §6).

## Порядок для компонента

Протоколы — `skills/_shared/protocols/gates/`, стандарты —
`skills/_shared/standards/`. Читать **до** работы:

1. `product-context` — подтвердить продукт.
2. `component-gate` — lookup в Components продукта: точное совпадение →
   семантический аналог → предложение PD; молча не создавать.
3. `component-standards` — каким должен быть компонент: архитектура,
   свойства, варианты и состояния (`component-states-guide`), имена
   (`naming-conventions`), доступность; готовность — §15.
4. `token-integrity` — каждое значение через lookup токена (`token-rules`);
   пробелы — одной анкетой.
5. `token-change-gate` — новый токен или стиль, решение PD.
6. `release-gate` — версию и чейнжлог не писать вне релиза; правка
   библиотеки — запись «Не опубликовано» в чейнжлог Figma; у Rider и
   Driver — с куратором-человеком по задаче, у прочих — вручную с PD
   (`WORKING-RULES` §5; правка стандарта — Standards, §15.1 п.10).
7. Библиотеку Rider или Driver править — по задаче с куратором-человеком;
   одного владельца у них нет, публикует, ставит версию и чейнжлог
   инженер-человек через release-gate (решение PD 2026-10-21); AI —
   changelog и версию minor или patch по задаче с разрешением PD или
   куратора-человека, major, GitHub Release и Latest — людям (решение
   PD 2026-10-22). Прочие
   библиотеки — по задаче и с «да» владельца библиотеки.
8. Приёмка — по снимку «было | стало», не по структуре слоёв
   (`WORKING-RULES` §7).

Чего нет в стандартах — сказать явно и спросить Standards, не
додумывать. Вход по стандартам целиком — `docs/hub/STANDARDS-WORK.md`.

## Делает сам

- ревью и описание дизайна по стандартам AID;
- аудит и сборку компонента (Designer · Components) — с приёмкой
  Standards;
- предложения компонентов и токенов — через component-gate и
  token-change-gate, решение PD.

## Не делает никогда

- не создаёт компонент и токен молча — сначала lookup и предложение;
- не заводит своих правил и не отходит от стандарта без Standards;
- не правит библиотеки Figma без задачи; Rider и Driver — без
  куратора-человека, прочие — без «да» владельца библиотеки.
- не переносит ответы Product Logic в репозиторий, PR, доску и issue —
  только ID записи базы, без содержания (`product-logic.md`).
