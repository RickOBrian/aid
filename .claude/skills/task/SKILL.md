# task — поставить задачу человеку

Работает в любом Штабе — сессии Claude Code или агенте Cursor, открытых в
клоне репозитория. Решение — ADR-042, протокол —
`docs/hub/ORCHESTRATION.md` §9 «Задачи между людьми». Отвечать
по-русски.

Задачу ставит любой из `docs/hub/owners.json` любому другому из него — PD,
инженеру, менеджеру. **Задача — не разрешение**: работа в чужом продукте
по-прежнему с согласия владельца, системный уровень — PD (§9 «Кто что
утверждает»).

## 1. Кто ставит

`gh api user -q .login` — логин того, кто ставит. Его нет в
`owners.json` на `origin/main` (`git fetch -q`,
`git show origin/main:docs/hub/owners.json`) — сказать: задачу от него
никто не засчитает, бот промолчит; не создавать.

## 2. Кому — найти логин

Получатель назван как угодно: именем, фамилией, ником Telegram (с `@`
или без), логином.

1. Логин и есть в `owners.json` — готово.
2. Иначе — база команды (`tools/aid-team/READER.md`): скачать
   `people.json` во временный файл профилем `aidteam-reader`, найти без
   учёта регистра по `first_name`, `last_name`, `telegram`, `github`,
   удалить файл. Карточка без `consent.date` не используется.
3. Одно совпадение — взять `github`. Несколько — показать варианты
   (имя + логин) и спросить. Ни одного — спросить логин.
4. Логина нет в `owners.json` — сказать: задачу этому человеку поставить
   нельзя, пока PD не добавит его в список.

Нет доступа к базе — работать по логину и сказать об этом одной строкой.

## 3. Что за задача

Из слов автора заполнить поля. Чего не хватает — один вопрос со всеми
пробелами сразу.

| Поле | Обязательно | Пример |
|---|---|---|
| Что нужно | да | «Кнопка скачивания плагина показывает версию» |
| Зачем | да | «Дизайнеры не понимают, обновились ли» |
| Готово, когда | да | «На aidteam.pro видна версия последнего релиза» |
| Срок | нет | дата или «не горит» |
| Приоритет | да | `высокий` · `обычный` · `низкий` |
| Продукт | нет | метка `to:<продукт>` из `owners.json` — только упомянуть в тексте |
| Контекст | нет | ссылки на PR, issues, файлы |

## 4. Проверить перед созданием

- Репозиторий публичный: в тексте нет имён, Telegram, e-mail, секретов,
  внутренних данных продуктов. Человек — только `@логин`.
- Нет ли такой же открытой задачи:
  `gh issue list --repo RickOBrian/aid --state open --search "TASK in:title <ключевые слова>" --json number,title`
  и оставить заголовки, начинающиеся с `[TASK @<логин>]` (поиск GitHub
  скобки и `@` не учитывает).
  Нашлась — показать и спросить: дополнить её или создать новую.

## 5. Показать и создать

Показать автору готовый текст. После «да» — тело во временный файл:

```bash
gh issue create --repo RickOBrian/aid \
  --title "[TASK @<логин>] <что нужно, коротко>" \
  --body-file <временный файл>
```

Меток и исполнителя не ставить: их может ставить только PD, инженеры
работают из форков (§9). Получатель — в заголовке. Временный файл
удалить.

Тело:

```
@<логин>, задача от @<автор>.
**Приоритет:** <высокий | обычный | низкий>
**Срок:** <дата | не горит>

**Что нужно:** …
**Зачем:** …
**Готово, когда:** …

**Продукт:** <to:… | не указан>
**Контекст:** …

Взять — комментарий «Беру». Передать — «Передаю @<логин>».
Сделано — «Готово» и ссылка на PR.
```

## 6. Итог

Ссылка на issue и строка: «Ушло @<логин>, он получит уведомление в
Telegram; ход — в /team».

## Не делать

- Не писать в issue имена и контакты из базы — только логины.
- Не ставить метки `for:`, `decision:pd`, `to:` — это PD.
- Не выводить `people.json` целиком; не выводить `yc config list`,
  `yc config profile get` и содержимое `~/.config/yandex-cloud/`: в
  профиле лежит закрытый ключ.
