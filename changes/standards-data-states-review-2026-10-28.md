# Разбор: состояния экрана с данными в стандартах AID

Повод — статья «Designing for different UI states» (uxdesign.cc) и вопрос
sergej 2026-10-28: есть ли у нас такой тип стандарта. Статья сайтом не
открылась (403); разбор опирается на схему, которую она пересказывает, —
UI Stack: экран бывает **идеальным, пустым, загружающимся, частичным и с
ошибкой**.

Номер задачи — от Штаба. Черновик гайда —
`changes/standards-data-states-guide-draft-2026-10-28.md`.

С чем сверял: `component-states-guide` 1.3.1, `ds-component-architecture-guide`
1.6.0 (§6, §7, §8, §11), `component-standards` (§4, §8, §10),

## 1. Что у нас уже есть

| Тема статьи | Где у нас | Что там |
|---|---|---|
| Загрузка (компонент) | `component-states-guide` §1, §6.3 | `loading` — спиннер внутри компонента; `skeleton` — заглушки при первой загрузке |
| Кто решает, что рисовать | `ds-component-architecture-guide` §7, §8 | Компонент рисует по пропу (`isSkeleton`, `isLoading`), решает экран или CollectionView |
| Пустое состояние | `ds-component-architecture-guide` §6 | Компонент `EmptyState` — «Состояние пустоты», без описания |
| Пустое состояние | `component-categories-guide` §2 | `EmptyState` — категория Feedback |
| Ошибка | `component-states-guide` §6.5 | `error` — **только** ошибка поля формы |
| Частичное состояние | `component-standards` §10 | Устойчивость компонента к контенту (длинный, короткий, пустой текст) |
| Доступность загрузки | `accessibility` §6 | `aria-busy` на контейнере, объявление о конце загрузки |
| Оркестратор | `ds-component-architecture-guide` §11 | `CollectionView` — только строка в глоссарии |

Итого: у нас хорошо описан **компонент**: что он умеет показать. Нет
стандарта для **экрана**: когда и что из этого показывать.

## 2. Чего нет

| № | Пробел | Почему важно |
|---|---|---|
| П1 | Нет словаря состояний экрана. В §7 гайда архитектуры сказано «empty / loading / error», но `empty` у нас не состояние, а `loading` и `error` значат другое (см. §3) | Дизайнер и разработчик называют одно и то же разными словами |
| П2 | Не различаются причины пустоты: первый запуск, «ничего не найдено», всё удалено | Под каждую причину нужны свой текст и своё действие |
| П3 | Нет ошибки экрана: нет сети, сбой сервера, нет прав | Сейчас `error` разрешён только формам, поэтому ошибку экрана нечем назвать |
| П4 | Нет обновления при уже показанных данных: обновление, данные устарели, офлайн | Типичная ошибка — данные пропадают и снова видны заглушки |
| П5 | Нет правил переходов и времени: когда показывать индикатор и сколько его держать | Мигание скелетона на быстрой сети |
| П6 | `EmptyState` не описан: анатомия, свойства, действие | Компонент из списка ролей нельзя собрать по стандарту |
| П7 | `CollectionView` без уровня архитектуры | Правило `must` `architecture-level-declared` требует уровень |
| П8 | Нет нормы текста сообщений | Тексты «Что-то пошло не так» без действия |
| П9 | Аудит экрана не проверяет состояния данных | Макет приходит только в идеальном виде |

## 3. Главный риск противоречия — слова

Термины статьи нельзя перенести один в один: часть слов у нас уже занята
состояниями компонента, и у тех есть таблица приоритетов и запрещённых
сочетаний.

| Термин статьи | Занято у нас? | Если взять как есть | Предлагаю |
|---|---|---|---|
| Ideal | нет | — | `content` |
| Empty | нет | — | `empty` |
| Loading | **да**: `loading` — спиннер внутри компонента, 2–3 с | Экран в `loading` и кнопка в `loading` — разное, а слово одно | `pending` — данных ещё нет |
| Error | **да**: `error` — только поле формы (§6.5) | Ломает правило «error — только для форм» или заставляет его переписать | `failed` — загрузка не удалась |
| Partial | нет | — | не состояние, а **значение** (§4) |

Почему не переименовать состояния компонента: их имена — источник истины
для Figma и трёх платформ (`component-states-guide` §1). Это MAJOR
половины корпуса ради нового гайда.

Почему не «то же слово, другой уровень»: в коде экрана встретятся обе оси
сразу (`dataState === 'loading'` рядом с `isLoading` кнопки). Читатель
кода не должен угадывать, какая из двух «загрузок» имеется в виду.

## 4. Как предложение опирается на действующие правила

| Действующее правило | Как гайд им пользуется |
|---|---|
| «Состояние против значения» (`component-states-guide` §4) | Partial — значение (сколько данных), а не пятое состояние. Его закрывает §10 «Устойчивость к контенту» + правило экрана «одна запись тоже должна выглядеть задуманно» |
| Экран решает, компонент рисует по пропу (§7–8 архитектуры) | Без изменений: состояние данных живёт у экрана, компоненты получают `isSkeleton` / `isLoading` как сейчас |
| Недопустимо `skeleton + loading` | Продлевается на экран: при `pending` не показывать одновременно скелетон и общий спиннер |
| Составной `loading` по зонам (Structural View) | Продлевается: у зоны — своё состояние данных; одна зона может упасть, остальные — нет |
| `error` только для форм, `destructive` — вариант | Сохраняется. Ошибка экрана — `failed`, не `error` |
| Булевы пропы с `is` (`naming-conventions` §6) | `isRefreshing`, `isStale` |
| Перечисления — union (Web), enum (iOS, Android) | `DataState`, `DataStateReason` |
| Вариант = оформление, смысл — не вариант (`component-standards` §8.2) | Причина пустоты/сбоя — значение `reason`, а не `variant`: оформление одно, меняются текст и действие |
| Узкий список `must` (`conformance-levels` §2) | В гайде нет новых `must`: экран без описанного `failed` опознаётся и переносится; это дистанция, а не нарушение |
| Без значения без токена (три запрета) | Пороги времени в гайде — без чисел; токены — в анкету вместе с нормой motion (после Spinner) |
| Компонент не создаётся молча | Новых компонентов нет. `EmptyState` уже в списке ролей; предлагается описать и расширить на сбой (вопрос 3). `Spinner` упоминается только как будущий — после его внесения в гайд архитектуры 1.7.0 |
| Уровень правила — в машинном слое, не в прозе (`conformance-levels` §5) | В черновике уровней нет; предложение — таблица §4.1 ниже, при переносе — `data-states.json` |

### 4.1. Предлагаемые уровни правил

| Правило | Уровень |
|---|---|
| Для области с загружаемыми данными нарисованы `pending`, `empty`, `failed` | `should` |
| Имена состояний — `pending · content · empty · failed`, не `loading` / `error` | `should` |
| Обновление не возвращает область в `pending` | `should` |
| У `failed` есть действие | `should` |
| Одна запись выглядит задуманно | `should` |
| Пороги индикатора — через токены времени | `should` |
| Тексты: что случилось, что делать, без кодов | `should` |
| `isStale` с `Banner` | `may` |
| `EmptyState` меньшего размера для упавшей зоны | `may` |

`must` нет намеренно: `mustRegistry` расширяется только MAJOR и только
тем, без чего артефакт нельзя опознать или перенести.

## 6. Вопросы к PD

1. **Где жить правилам.** а★ — отдельный гайд `data-states-guide`;
   б — раздел в `component-states-guide`. За «а»: у состояний компонента
   своя матрица и свой приоритет; правила экрана в неё не ложатся и
   раздули бы гайд, который уже читают при каждой сборке.
2. **Имена.** а★ — `pending · content · empty · failed` (+ `isRefreshing`,
   `isStale`); б — слова статьи `loading · error` с пометкой «уровень
   экрана». За «а» — §3.
3. **Пусто и сбой — один компонент?** а★ — один `EmptyState` со значением
   `reason`; б — отдельный компонент для сбоя. За «а»: анатомия одна
   (иллюстрация, заголовок, текст, действие), меняются текст и кнопка, а
   кнопка приходит слотом от экрана. Похоже устроен `ContentUnavailableView`
   в SwiftUI: один вид с настраиваемым текстом и действиями для любой
   причины. Риск «а»: строка §8.2 «меняется смысл действия → новый
   компонент» — читаем её так, что смысл самого `EmptyState` не меняется
   («показать нечего»); если PD читает иначе — «б».
4. **Уровень `CollectionView`.** а★ — не компонент ДС, а паттерн экрана:
   контракт (`dataState` → что рисовать) в гайде, реализация в продукте;
   б — Structural View со слотами под каждое состояние. За «а»: логика
   в Layout — антипаттерн (§7), а Structural View с данными внутри
   нарушает «компонент не знает об источнике данных».
5. **Пороги времени** (через сколько показывать индикатор и сколько
   держать) — токены коллекции `motion`, в анкету вместе с нормой motion
   после Spinner. Согласны?
6. **Тексты.** Стандарта текстов интерфейса нет. Пока — минимум в этом
   гайде (что случилось, что делать, кнопка) или сразу отдельная задача?
