# Градиенты: как описана передача в разработку — разбор

От: Standards, 2026-10-24. Кому: PD (через Штаб).
Поручение PD (чат Штаба, 2026-10-24): «нужно, чтобы Стандарты изучили как
мы сейчас описываем гайд по разработке градиента и пока не правила, но
указала если там что-то поменять с учетом обсужденного нами (кроме
скрипта, это пока отложим)».

Это отчёт, не правило. Скрипт конвертации Figma → код не разбирался.

## 1. Коротко

- **Правила передачи градиента в разработку нет.** В стандартах и
  протоколах градиент упомянут только как пробел: «Стили: тени, стекло,
  градиенты» (`figma-library-workflow` §6, пробел 3).
- Что разработчик видит сейчас: Dev Mode Figma и страница Gradients в
  Presentbook (только Driver). Страница показывает **только линейный**
  градиент, **угол для квадрата** и точки **строго 0…100 %**. Это
  расходится со всеми тремя пунктами обсуждения.
- Цвета точек — токены (коллекция `gradients`). Тип, угол, позиции и
  поведение при изменении размера записаны только в стиле Figma. В
  репозитории они есть лишь в коде витрины, в чейнжлоге их нет.

## 3. Расхождения с обсуждением

| Пункт обсуждения | Как сейчас | Расхождение |
|---|---|---|
| 1. Точки за краем — не ошибка | Тест витрины требует 0 и 100; модель не хранит точки вне 0…100 | Градиент с точкой −20 % нельзя показать на витрине без нарушения теста; читатель витрины воспримет это как ошибку |
| 1. Центр радиального — может быть снаружи | Радиального типа в модели нет | Не описан вовсе |
| 2а. Dev Mode даёт неверный CSS при точках за краем | Ни в одном документе нет предупреждения; блок 4 сборки называет ограничения Figma только в общем виде | Разработчик берёт CSS из Dev Mode, и ему не сказано, что тот может быть неверным |
| 2б. Перекошенные ручки — наклонный эллипс | Не описано | Нет правила «только по согласованию с разработкой» |
| 2в. Тянется или фиксирован | Угол витрины — «для квадратного превью». На неквадратном объекте (карточка 343×64) тот же CSS даёт другую картинку, чем Figma: в Figma градиент тянется с объектом, в CSS линия градиента остаётся под углом в пикселях | Поведение при изменении размера не записано, а витрина неявно показывает частный случай |
| 3. Параметры передачи: тип, угол или центр с радиусами, шаги с позициями, тянется / фиксирован | Есть угол и позиции, только для линейного Driver | Нет типа, центра и радиусов, режима размера |
| 3. Повторяющийся градиент — токеном | Цвета — токены, геометрия — только стиль Figma; в чейнжлоге её нет | Токен описан наполовину: смена угла не видна ни в чейнжлоге, ни в сверке |

Ещё одно противоречие внутри стандартов. `component-standards.json`
→ `valueKinds.unclassifiedEqualsHardcode: true`. Угол и позиции градиента
не классифицированы, значит по строгому чтению они — hardcode. Сейчас это
никто не применяет. Но первая автопроверка (standards-7) пометит каждый
градиент ошибкой.

## 4. Что предлагаю поменять

Каждое предложение — «было / стало / почему». Порядок — по пользе для
разработки.

**4.1. Описание градиента для передачи**
- Было: правила нет; геометрию видно только на витрине Driver и в Dev
  Mode.
- Стало: в стандарте (новый раздел — см. 4.7) градиент передаётся
  параметрами, а не CSS из Dev Mode:
  тип (`linear`, `radial`, позже `angular`);
  для линейного — угол и две точки ручек в долях объекта;
  для радиального — центр и два радиуса в долях объекта;
  точки — `позиция` (может быть < 0 и > 100) и цвет-токен;
  режим размера — `stretch` (тянется) или `fixed` (в pt / dp).
- Почему: п.3 обсуждения. Параметры однозначно переводятся на три
  платформы; CSS из Dev Mode — нет (п.2а).

**4.2. Точки за краем — допустимы**
- Было: тест витрины требует 0 и 100; правила нет.
- Стало: в стандарте — «позиция точки вне 0…100 допустима»; для
  линейного из двух цветов — рекомендация `should` привести к 0…100
  пересчётом цветов на краях (картинка не меняется). Тест витрины снять
  или ослабить до «по возрастанию».
- Почему: п.1. Это не ошибка дизайнера. Пересчёт упрощает код, но для
  трёх и более точек не всегда возможен без потерь, поэтому `should`, а не
  `must`.

**4.3. Перекошенный радиальный — по согласованию**
- Было: не описано.
- Стало: ручки радиального не под прямым углом — запись отличия
  (после мержа #329 — вид `exception`, standards-11) с согласием разработки до сборки; без неё —
  находка аудита.
- Почему: п.2б. В CSS эллипс радиального не поворачивается; на iOS и
  Android нужен обходной путь. Решать это надо на аудите, а не в коде.

**4.4. Режим размера — обязателен в гайде компонента**
- Было: не видно ни в Figma, ни в гайде; витрина показывает угол для
  квадрата.
- Стало: в блоке 3 сборки («Анатомия и токены», `figma-library-workflow`
  §3.8, приходит с #341) у каждого градиента — режим `stretch` / `fixed`. В блоке 6
  («Трудные случаи») — градиент на двух размерах, если `stretch`.
  Витрина Presentbook подписывает, для какой пропорции дан угол, или
  хранит ручки вместо угла.
- Почему: п.2в. Один и тот же угол на квадрате и на карточке 343×64 даёт
  разную картинку.

**4.5. Dev Mode — известное ограничение**
- Было: блок 4 сборки (§3.8, #341) говорит об ограничениях Figma в общем виде.
- Стало: пример в блоке 4 — «CSS градиента из Dev Mode неверен при
  точках за краем и перекошенных ручках; брать параметры из блока 3».
- Почему: п.2а. Короче и дешевле, чем разбор форка в коде.

**4.6. Градиент-токен целиком**
- Было: токены — только цвета точек; тип, угол, позиции — в стиле Figma
  без записи в репозитории и чейнжлоге.
- Стало: повторяющийся градиент (`Gradients/*` Driver и Rider) — токен
  вместе с геометрией: параметры из 4.1 хранятся рядом с цветами;
  смена геометрии — запись в чейнжлоге по `semver-guide` (тип смены
  значения). Разовый градиент в одном компоненте — параметрами в его
  гайде, без токена.
- Почему: п.3. Без этого смена угла проходит мимо чейнжлога и сверки.
  Тот же шаг закрывает расхождение `unclassifiedEqualsHardcode` (раздел 3):
  геометрия токена становится `semantic-token`.

**4.7. Где жить правилу**
- Было: пробел 3 протокола («Стили: тени, стекло, градиенты»).
- Стало: отдельный стандарт стилей (градиенты — первым; тени и стекло —
  тем же форматом позже), ссылка из `component-standards` §9 и из
  протокола. В `valueKinds.levelByCategory` — `gradient: should`.
- Почему: в `component-standards` правило о форме значения было бы
  чужим. Отдельный стандарт закрывает пробел 3 по частям.

**4.8. Rider в витрине**
- Было: градиентов Rider в Presentbook нет; чейнжлог лежит в `pending`.
- Стало: перенос по standards-3 и страница Rider Gradients уже с
  параметрами из 4.1 (типы, режим размера). Сверка угла и позиций Rider —
  в той же задаче.
- Почему: Viewpoint, Fade Horizontal и Shimmer — те случаи, где тип и
  поведение при изменении размера важнее цвета. Какого они типа, по
  репозиторию не видно; проверить в Figma.

## 5. Вопросы к PD

1. Принять 4.1 как модель передачи? Тогда следующий шаг — стандарт
   (4.7) отдельной задачей с номером.
2. Пересчёт к 0…100 для двухцветного линейного (4.2) — `should` или
   `may`?
3. Геометрия градиента-токена (4.6) — в каком источнике: в стиле Figma с
   копией в репозитории, или канон — репозиторий? Это пересекается с
   пробелом 5 протокола (канон значений токенов, ADR-039).

## 6. Не разбиралось

- Скрипт конвертации Figma → код для трёх платформ (отложен PD).
- Градиенты в коде продуктов (Rider, Driver) — их нет в этом
  репозитории.
