## Q-02 · уточняется
**В какой репозиторий кладём код бота?**

Пока git нет, два аккаунта Claude не могут работать параллельно: нет
веток, ревью и истории, а правки расходятся между маком и сервером.

Варианты: (а) отдельный приватный репозиторий бота; (б) этот репозиторий,
отдельным продуктом.

Склоняюсь к (а). Против (б): этот репозиторий публичный, а у бота
серверная конфигурация и данные людей; другой язык (Python) и свой деплой
на VPS, не на Vercel; `CLAUDE.md` этого чата уже записал, что код бота
сюда не копируется. В (а) оба автора получают доступ к обоим
репозиториям, а `CLAUDE.md` бота ссылается на контракт отсюда.

**2026-10-02, Principal Designer:** (б), но приватным разделом.
Уточнение: видимость в GitHub задаётся на весь репозиторий, приватной
папки в публичном репозитории не бывает. Сделать `RickOBrian/aid`
приватным нельзя без потерь: постоянная ссылка на релиз Token Comparator
(кнопка Presentbook, бот) перестанет скачиваться без авторизации. Нужен
повторный выбор.

## Q-04 · answered 2026-10-02
**Как два аккаунта Claude видят общее?**

Память у них раздельная. Нужен файл, который читают оба при входе в
контекст: где лежит, кто его ведёт, как инженер узнаёт, что контракт
изменился. Зависит от Q-02.

**Ответ:** контракт лежит здесь, в `tools/aid-bot/`; `CLAUDE.md` бота
ссылается на него. Контракт меняется только через PR, инженер — ревьюер.
Инженеру выдаётся доступ к `RickOBrian/aid` (collaborator) — выдаёт
Principal Designer в настройках репозитория.

## Q-05 · answered 2026-10-02
**Где хостится бот и что у него есть для входящих событий?**

VPS, long polling. HTTP-сервера нет, вебхуки принять некуда. Фоновые
циклы asyncio внутри процесса есть — события можно получать опросом
внешних API. Для пилота этого достаточно.

## Q-07 · answered 2026-10-02
**Откуда бот берёт плагин и его версию?**

Постановка «слияния» у автора предлагает сделать Presentbook единственным
источником релизов: манифест `GET /plugin/latest.json` на сайте. Это
расходится с тем, как AID устроен сейчас: источник релизов Token
Comparator — GitHub Releases, метка Latest и постоянная ссылка
`releases/latest/download/token-comparator.zip` принадлежат Token
Comparator, Presentbook сам ссылается на неё.

Предлагаю: бот скачивает по той же постоянной ссылке, версию читает из
GitHub API (`/repos/RickOBrian/aid/releases/latest` → `tag_name`), с
локальной копией на случай недоступности. Манифест на Presentbook не
нужен — второй источник релизов разойдётся с первым.

Это новый стык (бот читает ссылку Latest) — заносится в корневой
`CLAUDE.md` через Principal Designer и сообщается чату Token Comparator:
проверка ссылки после релиза теперь касается и бота.

**Ответ:** согласовано. Требование Principal Designer — полная
автоматизация: в боте всегда актуальная версия, без ручных шагов после
релиза, как кнопка Presentbook. Схема — `PLAN.md`, «Пилот».

## Q-08 · уточняется
**Где хранить описание бота?**

Этот репозиторий публичный. В описании — имена и Telegram-ники команды,
устройство сервера и его слабые места. Варианты: (а) в репозитории бота
после Q-02, здесь — только ссылка; (б) здесь, в сокращённой версии без
людей и инфраструктуры.

**2026-10-02, Principal Designer:** в репозитории и в Presentbook,
раздел Tools/Bots. Уточнение: оба места публичны. Предлагаю две версии —
полную во внутреннем месте (зависит от Q-02) и публичную для Presentbook:
что бот умеет, команды, как начать, без людей и сервера. Раздел Tools/Bots
— работа чата Presentbook.

## Q-09 · отложен 2026-10-02
**Хранить поля заявки отдельно от HTML поста?**

Сейчас тип заявки, компонент и ссылка на Figma живут только в тексте
поста. Превью из Figma, поиск, выгрузка в трекер, связь с компонентом
Presentbook — всё это требует структурных полей. Работа инженера; её
стоит согласовать с его архивом и поиском, которые трогают то же
хранилище.
