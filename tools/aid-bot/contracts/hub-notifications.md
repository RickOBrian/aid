# Контракт: уведомления о задачах между Штабами

> Статус: Draft · v0.2.0 · 2026-10-08
> Основание: ADR-042, `docs/hub/ORCHESTRATION.md` §9 «Задачи между
> людьми» и «Уведомления в Telegram». Задача владельцу бота — issue #136.
> Владелец — инженер бота (ADR-041): он утверждает этот контракт и
> выбирает реализацию. Меняется только через PR в `RickOBrian/aid`.

Когда в `RickOBrian/aid` человеку ставят задачу или пишут ему, он за минуту
получает в Telegram короткое сообщение со ссылкой на issue.

---

## 1. Транспорт: webhook или опрос

**Решение владельца (#136, 2026-10-08): опрос GitHub раз в 30 секунд.**
Webhook не нужен, в настройках репозитория ничего не ставится. ADR-042
предлагал webhook, #136 оставлял выбор владельцу. Сравнение — для
истории и на случай перехода.

| | Webhook | Опрос GitHub API |
|---|---|---|
| Задержка | секунды | период опроса, 30–60 с |
| Что нужно на сервере бота | публичный HTTPS-адрес: домен, TLS, обратный прокси, открытый порт | ничего входящего |
| Секреты | секрет подписи webhook | токен GitHub только на чтение (fine-grained, один публичный репозиторий) |
| Что ставит PD | webhook в настройках репозитория | ничего |
| Пропуск событий | при простое бота GitHub повторяет доставку ограниченно; потерянное надо добирать опросом | нет: бот продолжает с последней метки |
| Общая инфраструктура | та же, что нужна Library Updater (#98): HTTPS-адрес у сервера бота | — |

Почему опрос: у бота нет HTTP-сервера, опрос укладывается в существующий
шаблон фоновых циклов и не теряет события при перезапуске. Переход на
webhook — если у сервера бота появится HTTPS-адрес по другой причине;
правила разделов 2–6 от транспорта не зависят.

### Опрос

- Раз в `HUB_POLL_SECONDS` (по умолчанию 30):
  - `GET /repos/RickOBrian/aid/issues?state=all&since=<метка>&sort=updated&direction=asc&per_page=100`
    — новые и изменённые issues: открытие, метки, заголовок;
  - `GET /repos/RickOBrian/aid/issues/comments?since=<метка>&sort=created&direction=asc&per_page=100`
    — новые комментарии;
  - для меток — `GET /repos/RickOBrian/aid/issues/<n>/events` только у
    issues из первого запроса, чтобы знать, **кто** и **когда** поставил
    метку.
- Заголовок `Authorization: Bearer <GITHUB_TOKEN>`, `User-Agent`,
  `If-None-Match` с ETag прошлого ответа. Лимит с токеном — 5000 в час,
  опрос тратит ~240.
- Метка `<метка>` — `updated_at` последнего обработанного объекта минус
  2 минуты (перекрытие на часы GitHub); повторы отсекает журнал из
  раздела 5.
- Pull requests в `/issues` пропускаются (`pull_request` в ответе).

### Webhook

- События `issues` (`opened`, `labeled`, `edited`) и `issue_comment`
  (`created`), `content-type: application/json`.
- Подпись `X-Hub-Signature-256` проверяется секретом
  `HUB_WEBHOOK_SECRET` сравнением за постоянное время. Нет подписи или не
  совпала — `401`, ничего не делать.
- Ответ `200` — сразу после проверки подписи и записи события в очередь;
  отправка в Telegram — после ответа. GitHub ждёт ответ 10 секунд.
- `X-GitHub-Delivery` — ключ для журнала из раздела 5.
- Раз в сутки — дозапрос опросом за последние 24 часа: закрывает доставки,
  пропущенные при простое.

## 2. Кто автор события

Репозиторий публичный: писать issues и комментарии может кто угодно.
Поэтому:

- **автор события** — `sender.login` (webhook) или `user.login`
  комментария, `actor.login` события метки, `user.login` issue;
- автор должен быть в `docs/hub/owners.json` → `people[].github`
  (формат `aid-hub-owners/2` на `main` 2026-10-08; другой `format` —
  ошибка в лог и пауза уведомлений, а не догадка о структуре). Файл
  читается с `main` (`raw.githubusercontent.com/RickOBrian/aid/main/docs/hub/owners.json`),
  кэш — 10 минут;
- автор не из списка — событие записывается в журнал как
  `ignored:author`, **уведомлений нет**;
- боты GitHub (`*[bot]`) — то же.

Права в `owners.json` при этом не проверяются: уведомление — не
разрешение (ORCHESTRATION.md §9 «Задача — не разрешение»).

## 3. Кому слать

Таблица из ORCHESTRATION.md §9 в виде правил разбора. Один объект может
сработать по нескольким правилам — получатели объединяются, каждый
получает **одно** сообщение на событие.

| # | Событие | Как распознать | Получатели |
|---|---|---|---|
| R1 | Открыт issue-задача | `issues.opened`, заголовок по `^\[TASK @([A-Za-z0-9-]+)\]` | логин из заголовка |
| R2 | Передача | комментарий, строка по `^Передаю @([A-Za-z0-9-]+)\b` (первая такая строка); автор — текущий исполнитель (раздел 3.1) или PD | новый логин и автор issue |
| R3 | Взял / сделал | комментарий, первая непустая строка — `Беру` или `Готово` (без учёта регистра, точка в конце допустима); автор — текущий исполнитель | автор issue |
| R4 | Метка `for:<логин>` | `issues.labeled`, `label.name` по `^for:([A-Za-z0-9-]+)$` | этот логин |
| R5 | Метка `decision:pd` | `issues.labeled`, `label.name == "decision:pd"` | все из `owners.json` с `"system"` в `decides` |
| R6 | Запрос в продукт | `issues.opened` или `issues.labeled` с меткой `to:<продукт>` | все из `owners.json`, у кого `<продукт>` в `owns` |
| R7 | Упоминание | комментарий в issue с меткой `hub`, `@логин` вне блоков кода и цитат | каждый упомянутый логин |

Общие правила:

- **Себе не пишем:** автор события исключается из получателей.
- **Только известные:** получатель — логин из `owners.json`; остальные
  отбрасываются молча.
- **Метки при открытии:** issue, открытый сразу с метками, — одно событие
  `opened`: R1, R4, R5, R6 считаются по меткам из этого же события, а
  последующие `labeled` для тех же меток в течение 60 секунд не
  повторяют уведомление.
- **Правка заголовка** (`issues.edited`) получателя не меняет и
  уведомлений не шлёт: текущий исполнитель меняется только через R2.
- **Закрытые issues** — R1–R7 не срабатывают.

### 3.1. Текущий исполнитель

Логин из заголовка `[TASK @x]`, затем — из последнего комментария R2,
автор которого был текущим исполнителем или PD. Бот вычисляет его из
комментариев issue при каждом событии R2/R3, а не хранит.

## 4. Логин → Telegram

Решение PD 2026-10-07 (`docs/hub/BOARD.md` → «Решения PD», «Ключ бота»;
`tools/aid-team/STORAGE.md`): бот видит **не базу Team**, а отдельный
файл только с парами «логин → Telegram».

| Что | Где |
|---|---|
| Файл | `telegram.json` в бакете `aidteam-team-bot` (Яндекс Облако) |
| Формат | `{"format": 1, "source": "people.json format N", "people": [{"github": "<логин>", "telegram": "<ник без @>"}]}` |
| Доступ бота | ключ сервисного аккаунта, только чтение этого бакета |
| Кто пишет | только Team (PD), пересобирает после любой правки базы; в файл попадают люди с согласием и заполненным Telegram |

`people.json` бот не читает и ключа к нему не имеет.

1. Логин → ник: поиск в `telegram.json` → `people[]` по `github`, без
   учёта регистра. Кэш файла — 10 минут. Неизвестный `format` — ошибка
   в лог, уведомления по Team не отправляются до исправления.
2. Ник → `chat_id` — из базы бота: связь заводится, когда человек пишет
   боту `/start` (ADR-042 «2а»). Бот ищет его Telegram-ник в
   `telegram.json` и запоминает пару `telegram user_id ↔ github логин`;
   дальше ведёт по `user_id` — он не меняется при смене ника.
3. **Связка только по `telegram.json`.** `/start <логин>` или ввод
   логина руками не принимается: иначе любой подпишется на уведомления
   чужого логина. Файл пишет только Team — это и есть проверка.
4. Ника нет в `telegram.json` — бот отвечает на `/start`: «Не нашёл тебя
   в базе команды AID — попроси PD добавить твой Telegram». Событие для
   такого логина — журнал `skipped:no-telegram`.
5. Человек не писал `/start` — журнал `skipped:no-chat`, без повторов.
6. Человека убрали из `telegram.json` — при следующем обновлении кэша
   связь `user_id ↔ логин` удаляется, уведомления прекращаются.

Существующий `/start` бота (меню заявок) остаётся; связка — дополнительный
шаг в нём, без нового экрана, если ник найден.

## 5. Журнал и повторы

- Ключ события: `X-GitHub-Delivery` (webhook) или
  `<тип>:<id объекта>[:<label>]` (опрос). Повтор ключа — пропуск.
- Журнал хранит ключ, время, правило, получателей и итог (`sent`,
  `ignored:author`, `skipped:no-telegram`, `skipped:no-chat`, `error`) —
  30 дней. Только логины, без текстов issues.
- Ошибка отправки в Telegram — 3 попытки с паузой 1, 5, 30 секунд, потом
  `error` в журнал. Тихих потерь нет: `error` пишется в лог уровня
  `WARNING`.

## 6. Текст сообщения

HTML, как остальные сообщения бота. Без текста issue — только заголовок и
ссылка: в issue могут быть подробности, которым не место в Telegram.

| Правило | Текст |
|---|---|
| R1 | `📌 Задача от <автор>: <заголовок без [TASK …]>` |
| R2 | `↪️ <автор> передаёт задачу <кому>: <заголовок>` |
| R3 | `✅ <исполнитель> взял задачу: <заголовок>` / `🏁 <исполнитель>: готово — <заголовок>` |
| R4 | `🔖 Для тебя (for): <заголовок>` |
| R5 | `⚖️ Нужно решение PD: <заголовок>` |
| R6 | `📨 Запрос в <продукт>: <заголовок>` |
| R7 | `💬 <автор> упомянул тебя: <заголовок>` |

Вторая строка всегда — ссылка: `<html_url>` issue или комментария.
`<автор>` — GitHub-логин. Заголовок экранируется под HTML и обрезается до
200 символов.

Тихие часы бота не действуют: это событие, а не напоминание.

## 7. Переменные окружения

Описать в `.env.example` бота без значений.

| Переменная | Назначение | Секрет |
|---|---|---|
| `HUB_TRANSPORT` | `poll` или `webhook` | нет |
| `HUB_REPO` | `RickOBrian/aid` | нет |
| `HUB_POLL_SECONDS` | период опроса | нет |
| `GITHUB_TOKEN` | fine-grained, только чтение issues одного публичного репозитория; нужен для опроса | да |
| `HUB_WEBHOOK_SECRET` | секрет подписи webhook | да |
| `TEAM_BOT_KEY_FILE` | путь к ключу сервисного аккаунта, читающего `aidteam-team-bot/telegram.json` | да (файл) |

Секреты передаются лично или через менеджер паролей — не в issues, не в
Telegram-канал, не в репозитории.

## 8. Готово, когда

1. Issue `[TASK @<логин>] …` от логина из `owners.json` → сообщение
   получателю в Telegram за минуту.
2. Тот же issue от логина не из списка → тишина, `ignored:author` в
   журнале.
3. «Передаю @y» от текущего исполнителя → сообщение `y` и автору; от
   постороннего логина из `owners.json` — сообщения нет.
4. Повторная доставка того же события → второго сообщения нет.
5. Человек без `/start` → `skipped:no-chat`, бот не падает.

Проверка — на тестовых issues в `RickOBrian/aid` с заголовком
`[TASK @<свой логин>] test`, после — закрыть их.

---

## 9. Чего бот не делает

- Не пишет в `RickOBrian/aid`: не комментирует, не ставит метки, не
  закрывает issues.
- Не решает, кто что утверждает, — только уведомляет.
- Не пересылает текст issues и комментариев.
- Не читает базу Team (`people.json`) и не хранит её — только `telegram.json` в кэше и связь `user_id ↔ логин`.
