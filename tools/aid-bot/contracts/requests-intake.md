# Контракт: приём запросов дизайнеров

> Статус: Draft · v0.1.0 · 2026-10-14
> Задача: AID-22 (решение PD «заводи пока все», `docs/hub/BOARD.md`).
> Основание: ADR-047, `docs/hub/ORCHESTRATION.md` §10–11, карточка
> `docs/hub/agents/requests.md`.
> Владелец — инженер бота (ADR-041): утверждает контракт и реализацию.
> Входящие и ключи сервиса задач — AI Ops · Team. Меняется только через PR
> в `RickOBrian/aid`.

Дизайнер отправляет запрос в бота, как сейчас. Бот кладёт его во входящие
AI-инженера «AID · AI Ops · Requests». Requests разбирает запрос, отвечает
автору или заводит задачу. Вся переписка с автором идёт через бота:
Requests к человеку напрямую не ходит.

```
дизайнер ──Telegram──▶ бот ──входящие ai-requests──▶ Requests
    ▲                   │                                │
    └────── Telegram ───┴──── входящие bot ◀─────────────┘
                                                         │
                                       задача ──▶ сервис задач (Tasks)
```

---

## 1. Что такое запрос

То, что дизайнер сейчас заполняет в боте: направление, тип, ответы на
вопросы визарда, ссылка на Figma, скрин. Новых шагов для дизайнера нет.

### Поля

| Поле | Тип | Откуда | Обязательно |
|---|---|---|---|
| `id` | строка `req-<n>` | бот, свой счётчик | да |
| `source` | `bot` | бот | да |
| `sourceRef` | строка | бот: ключ заявки в его хранилище | да |
| `kind` | `question` · `bug` · `edit` · `new` | тип в визарде: 💬 · 🐞 · ✏️ · ✨ | да |
| `kit` | `rider` · `driver` | направление в визарде | да |
| `component` | строка | поле «Компонент» / «Что за компонент»; у `question` — «Что собираю» | нет |
| `text` | объект «вопрос визарда → ответ» | остальные поля визарда (`problem`, `change`, `usage`, `why`, `question`) | да |
| `figmaUrl` | строка | поле «Фигма»; только `https://www.figma.com/…` | нет |
| `attachments` | список `{kind: "image", ref}` | скрин; `ref` — непрозрачный id файла у бота | нет |
| `author` | объект, раздел 1.1 | бот | да |
| `createdAt` | ISO 8601, UTC | бот | да |

`kit` — продукт дизайн-системы (UI Kit), не код продукта сервиса задач:
коды `rider`/`driver` в `products/registry.json`, коды сервиса —
`token-comparator`, `bot-request` и т. п. В какой продукт сервиса пойдёт
задача, решает Requests.

### Q-09: поля хранятся отдельно

Сейчас тип, компонент и ссылка на Figma у бота живут только в HTML поста
(`OPEN-QUESTIONS.md`, Q-09, отложен). Этот контракт его **открывает**:
бот хранит поля заявки отдельно и из них собирает и пост в канале, и
запрос. Разбор HTML поста как источник — не допускается: формат поста
меняется, а запрос — контракт.

### 1.1. Автор

| Поле | Что |
|---|---|
| `author.ref` | непрозрачный id автора у бота, например `tg-7f3a…` — хэш Telegram `user_id` с секретом бота. По нему бот находит чат; Requests видит только его |
| `author.login` | GitHub-логин, если автор есть в `telegram.json` (раздел 4 `hub-notifications.md`); иначе нет поля |
| `author.name` | «Имя Ф.» из Telegram-профиля — только во входящих, никуда дальше |

Telegram `user_id`, ник и номер телефона во входящие не попадают.

## 2. Куда бот кладёт запрос

Во входящие AI-инженера `ai-requests` в сервисе задач
(`team.aidteam.pro`), сервисным ключом бота (вид `bot`, делает AI Ops ·
Team — решение PD 2026-10-14 «любой, включая ботов»).

### Что нужно от сервиса — запрос в AI Ops · Team

Входящих в API v1 сейчас нет (`tools/aid-team/SERVICE.md`). Боту нужно:

| Запрос | Ключ | Что |
|---|---|---|
| `POST /v1/inbox/ai-requests` | сервисный `bot` | новое сообщение: `{type: "request", request: {…раздел 1}}` или `{type: "reply", requestId, text}` → `{messageId}`; повтор с тем же `Idempotency-Key` не создаёт второе |
| `GET /v1/inbox/bot?after=<messageId>` | сервисный `bot` | сообщения боту от Requests, по порядку |
| `POST /v1/inbox/bot/ack` | сервисный `bot` | `{ids: […]}` — доставлено; неподтверждённое придёт снова |

Читать входящие — **только по ключу**: в них текст запросов и имена, а
`GET /v1/tasks` читается открыто. Хранение — 90 дней после закрытия
запроса, затем удаление (предложение, решает Team и PD).

Конкретные пути и формат — за Team; этот раздел — требования бота. Пока
API нет, бот запросы не отправляет, а работает как сейчас.

### Когда бот отправляет

Сразу после «✅ Отправить» в визарде, параллельно с постом в канал.
`Idempotency-Key` — `bot:<sourceRef>`. Сервис недоступен — повтор с
паузой 1, 5, 30 минут, потом алерт лиду; заявка в канале и у лида при
этом идёт как сейчас (раздел 6).

## 3. Переписка с автором

### Requests → автор

Requests пишет во входящие `bot`:

```json
{ "type": "to-author", "requestId": "req-42", "text": "…", "expectsReply": true }
```

Бот отправляет автору в ЛС:

```
🤖 AID Requests (AI-инженер) · по запросу «<title>»

<text>

[↩️ Ответить]   — если expectsReply
```

- Подпись «AI-инженер» обязательна: человек должен видеть, что отвечает
  не живой инженер.
- `text` — простой текст, бот экранирует его под HTML; ссылки только
  `https:`. До 3000 символов, длиннее — бот обрезает с `…`.
- Тихие часы не действуют.
- Автор заблокировал бота или не писал `/start` — бот подтверждает
  сообщение и пишет обратно `{type: "delivery-failed", requestId}`:
  Requests должен знать, что ответ не дошёл.

### Автор → Requests

- Кнопка «↩️ Ответить» или ответ (reply) на сообщение Requests в ЛС.
- Бот кладёт во входящие `ai-requests`:
  `{type: "reply", requestId, text, attachments}`.
- Обычные сообщения боту вне этого — меню, как сейчас; в Requests не
  уходят.
- Ответ на закрытый запрос — бот предлагает «Создать новый запрос».

## 4. Статусы запроса

Статус живёт во входящих (у запроса), бот показывает его автору в
`/tasks` и строкой на посте в канале.

| Статус | Что значит | Кто ставит |
|---|---|---|
| `new` | пришёл, никто не взял | бот |
| `taken` | Requests взял (экземпляр отметил «взял», §11) | Requests |
| `waiting-author` | Requests задал вопрос, ждёт автора | Requests (`expectsReply: true`) |
| `answered` | вопрос закрыт ответом | Requests |
| `in-task` | заведена задача, `taskId` — `<продукт>-<n>` | Requests |
| `declined` | не к команде AID или дубль; причина автору обязательна | Requests |
| `withdrawn` | автор отозвал | бот, по кнопке автора |

- `waiting-author` → `taken` — автоматически, когда бот положил ответ
  автора.
- Без ответа автора 7 дней — Requests решает: закрыть (`declined` с
  причиной «нет ответа») или подождать.
- `in-task` — не финал для автора: когда задача в сервисе становится
  «готово», Requests пишет автору итог (раздел 3) и ставит `answered`.
- Каждая смена статуса — сообщение боту `{type: "status", requestId,
  status, taskId?}`; бот обновляет строку на посте и пишет автору только
  при `answered`, `in-task`, `declined`.

## 5. Запрос → задача

Сервис задач **читается открыто** (`GET /v1/tasks` без ключа), поэтому в
задачу из запроса идёт только то, что можно показать всем:

| В задачу | Не в задачу |
|---|---|
| название и описание, **переписанные Requests** своими словами | исходный текст автора как есть |
| `kind`, `kit`, `component` | имя, Telegram, `author.ref` |
| ссылка на запрос: `requestId` (без содержимого) | скрины |
| `author.login`, если он есть и автор согласен быть в задаче | ссылка на Figma — до решения PD (раздел 7) |

Задачу заводит Requests своим ключом AI-инженера, куратор — по §11.
Requests не обещает автору срок и решение (карточка Requests).

В этот публичный репозиторий ничего из запросов не попадает: ни тексты,
ни имена, ни ссылки на файлы.

## 6. Что не меняется в боте

Решение за владельцем бота и PD — до него контракт ничего не отключает:

- пост в канале «AID Judgment», согласование лидом, «Взять в работу»
  исполнителями — работают как сейчас;
- Requests видит запрос **параллельно** и отвечает на вопросы (`question`)
  и уточнения; задачи по `bug` / `edit` / `new` заводит, только если лид
  согласовал заявку в боте (статус бота `handed_off`).

Как совместить два потока окончательно — открытый вопрос (раздел 7).

## 8. Готово, когда

1. Запрос из визарда за минуту появляется во входящих `ai-requests` со
   всеми полями раздела 1; повторная отправка того же — без дубля.
2. Сообщение Requests с `expectsReply` доходит автору с подписью
   «AI-инженер» и кнопкой; ответ автора возвращается в `ai-requests` с
   тем же `requestId`.
3. Смена статуса видна автору в `/tasks` и на посте в канале.
4. Автор без `/start` — Requests получает `delivery-failed`.
5. В задаче, заведённой из запроса, нет ни имени, ни Telegram, ни
   исходного текста автора.
