# Контракт: приём запросов дизайнеров

> Статус: Draft · v0.3.0 · 2026-10-14
> Задача: AID-22 (решение PD «заводи пока все», `docs/hub/BOARD.md`).
> Основание: ADR-047, `docs/hub/ORCHESTRATION.md` §10–11, карточка
> `docs/hub/agents/requests.md`.
> Владелец — инженер бота (ADR-041): утверждает контракт и реализацию.
> Входящие и ключи сервиса задач — AI Ops · Team. Меняется только через PR
> в `RickOBrian/aid`.

Дизайнер отправляет запрос в бота, как сейчас. Бот кладёт его во входящие
AI-инженера «AID · AI Ops · Requests». Requests разбирает запрос, отвечает
автору или заводит задачу. Вся переписка с автором идёт через бота:
Requests к человеку напрямую не ходит.

```
дизайнер ──Telegram──▶ бот ──входящие ai-requests──▶ Requests
    ▲                   │                                │
    └────── Telegram ───┴──── входящие bot ◀─────────────┘
                                                         │
                                       задача ──▶ сервис задач (Tasks)
```

---

## 1. Что такое запрос

То, что дизайнер сейчас заполняет в боте: направление, тип, ответы на
вопросы визарда, ссылка на Figma, скрин. Новых шагов для дизайнера нет.

### Поля

| Поле | Тип | Откуда | Обязательно |
|---|---|---|---|
| `source` | `bot` | бот | да |
| `sourceRef` | строка | бот: ключ заявки в его хранилище | да |
| `kind` | `question` · `bug` · `edit` · `new` | тип в визарде: 💬 · 🐞 · ✏️ · ✨ | да |
| `kit` | `rider` · `driver` | направление в визарде | да |
| `component` | строка | поле «Компонент» / «Что за компонент»; у `question` — «Что собираю» | нет |
| `text` | объект «вопрос визарда → ответ» | остальные поля визарда (`problem`, `change`, `usage`, `why`, `question`) | да |
| `figmaUrl` | строка | поле «Фигма»; только `https://www.figma.com/…` | нет |
| `attachments` | список `{kind: "image", ref}` | скрин; `ref` — раздел 2.2 | нет |
| `author` | объект, раздел 1.1 | бот | да |
| `createdAt` | ISO 8601, UTC | бот | да |

`kit` — продукт дизайн-системы (UI Kit), не код продукта сервиса задач:
коды `rider`/`driver` в `products/registry.json`, коды сервиса —
`token-comparator`, `bot-request` и т. п. В какой продукт сервиса пойдёт
задача, решает Requests.

### Q-09: поля хранятся отдельно — нужно решение PD

Сейчас тип, компонент и ссылка на Figma у бота живут только в HTML поста
(`OPEN-QUESTIONS.md`, Q-09, отложен PD 2026-10-02). Без структурных полей
этот контракт не работает — так же считает Requests (пожелание b).
Предложение: **переоткрыть Q-09** — бот хранит поля заявки отдельно и из
них собирает и пост в канале, и запрос. Разбор HTML поста как источник
не допускается: формат поста меняется, а запрос — контракт.
Переоткрыть Q-09 — решение PD; реализация — владелец бота.

### 1.1. Автор

| Поле | Что |
|---|---|
| `author.ref` | непрозрачный id автора у бота, например `tg-7f3a…` — хэш Telegram `user_id` с секретом бота. По нему бот находит чат; Requests видит только его |
| `author.login` | GitHub-логин, если автор есть в `telegram.json` (раздел 4 `hub-notifications.md`); иначе нет поля |
| `author.name` | «Имя Ф.» из Telegram-профиля — только во входящих, никуда дальше |

Telegram `user_id`, ник и номер телефона во входящие не попадают.

### 1.2. Id запроса

Своего счётчика у бота нет. **Id запроса — `thread`**, который сервис
вернул на сообщение `request` (`m-<n>`, раздел 2). Бот хранит связь
`thread → sourceRef, author.ref`; всё дальнейшее в цепочке — `replyTo`
на сообщения этой цепочки. Ниже `requestId` = этот `thread`.

## 2. Куда бот кладёт запрос

Во входящие AI-инженера `ai-requests` в сервисе задач
(`team.aidteam.pro`), сервисным ключом бота (вид `bot`, делает AI Ops ·
Team — решение PD 2026-10-14 «любой, включая ботов»).

### 2.1. API входящих

Общая схема для всех входящих сервиса — ответ AI Ops · Team на этот
контракт, 2026-10-14. `{addr}` — id AI-инженера (`ai-requests`,
`ai-tasks`, …) или `bot`.

| Запрос | Кто может | Что |
|---|---|---|
| `POST /v1/inbox/{addr}` | любой ключ | тело `{type, …, replyTo?}` → `{messageId, thread}`. Повтор с тем же `Idempotency-Key` от того же автора в тот же адрес в течение 7 дней возвращает тот же `messageId` |
| `GET /v1/inbox/{addr}?after=<messageId>&state=open\|all` | владелец адреса или PD | по умолчанию — только неподтверждённые |
| `POST /v1/inbox/{addr}/ack` | владелец адреса | `{ids: […]}`; всё неподтверждённое придёт снова |
| `POST /v1/inbox/{addr}/{messageId}/claim` | владелец адреса | «взял» — один экземпляр AI-инженера; второй получает `409 taken`. Боту не нужен |

- `messageId` — `m-<n>`; `thread` — id первого сообщения цепочки.
- **Автора и его вид** (`human` / `ai` / `bot`) ставит сервис по ключу,
  из тела не берёт.
- Входящие читаются **только по ключу**.

**Права ключа `bot`:** писать в любые входящие; читать и подтверждать —
только `bot`; читать ленту событий. Задачи не пишет.

**Хранение** (удаляет TTL сервиса, руками не чистится):

| Что | Срок |
|---|---|
| сообщение | 90 дней после `ack` или закрытия цепочки |
| неподтверждённое | 180 дней |
| журнал AI-инженеров | 1 год |
| `Idempotency-Key` | 7 дней |

### 2.2. Скрины

Два варианта, **выбирает владелец бота**:

| | Бакет сервиса задач (предложение Team) | Файл остаётся у бота |
|---|---|---|
| Как | бот загружает `POST /v1/files` → `ref`, кладёт в `attachments` | `ref` — id файла у бота; Requests скачивает через API бота |
| Ограничения | png, jpeg, webp до 10 МБ; удаление через 30 дней | — |
| Кто скачивает | владелец адреса, где файл упомянут, или PD | тот, кому бот даст доступ |
| В задачи | никогда | никогда |
| Минус | копия скрина до 30 дней и у бота, и в сервисе | **у бота нет HTTP-сервера**: нужен публичный адрес, домен и TLS — то, от чего бот отказался в #136 |

Рекомендация чата — бакет сервиса: второй вариант требует открыть сервер
бота в интернет ради одной функции.

### 2.3. Когда бот отправляет

Сразу после «✅ Отправить» в визарде, параллельно с постом в канал:
`POST /v1/inbox/ai-requests` с `{type: "request", request: {…раздел 1}}`,
`Idempotency-Key` — `bot:<sourceRef>`. Скрин — сначала `POST /v1/files`
(если выбран бакет сервиса).

Сервис недоступен — повтор с паузой 1, 5, 30 минут (тот же
`Idempotency-Key` — без дублей), потом алерт лиду; заявка в канале и у
лида при этом идёт как сейчас (раздел 6). Пока API входящих не выложено,
бот запросы не отправляет.

### 2.4. Что бот читает

Свой адрес `bot`: `GET /v1/inbox/bot?after=<последний>` раз в 30 секунд,
после обработки — `ack`. Обработка сообщения идемпотентна: повтор того
же `messageId` автору второй раз не отправляется.

## 3. Переписка с автором

### Requests → автор

Requests пишет во входящие `bot`:

```json
{ "type": "to-author", "replyTo": "m-41", "text": "…", "expectsReply": true }
```

`replyTo` — сообщение цепочки запроса; бот находит запрос по `thread` из
ответа сервиса.

Бот отправляет автору в ЛС:

```
🤖 AID Requests (AI-инженер) · по запросу «<title>»

<text>

[↩️ Ответить]   — если expectsReply
```

- Подпись «AI-инженер» обязательна: человек должен видеть, что отвечает
  не живой инженер.
- `text` — простой текст, бот экранирует его под HTML; ссылки только
  `https:`. До 3000 символов, длиннее — бот обрезает с `…`.
- Тихие часы не действуют.
- Автор заблокировал бота или не писал `/start` — бот подтверждает
  сообщение и пишет в `ai-requests` `{type: "delivery-failed", replyTo}`:
  Requests должен знать, что ответ не дошёл.

### Автор → Requests

- Кнопка «↩️ Ответить» или ответ (reply) на сообщение Requests в ЛС.
- Бот кладёт во входящие `ai-requests`:
  `{type: "reply", replyTo: <сообщение Requests>, onBehalfOf: "human", text, attachments}`.
  `onBehalfOf: "human"` сервис принимает только у `type: "reply"` и
  только от ключа `bot` — так ответ автора считается сообщением человека
  (раздел 4, защита от зацикливания).
- Обычные сообщения боту вне этого — меню, как сейчас; в Requests не
  уходят.
- Ответ на закрытый запрос — бот предлагает «Создать новый запрос».

## 4. Статусы запроса

Два уровня: подробный — во входящих, для Requests; простой — у автора в
боте (пожелание Requests d).

| Во входящих | Что значит | Кто ставит | Автор видит в боте |
|---|---|---|---|
| `new` | пришёл, никто не взял | бот | **принят** |
| `taken` | Requests взял (экземпляр отметил «взял», §11) | Requests | **в работе** |
| `waiting-author` | Requests задал вопрос, ждёт автора | Requests (`expectsReply: true`) | **в работе** · «ждёт твоего ответа» |
| `in-task` | заведена задача `<продукт>-<n>` | Requests | **в работе** · номер задачи |
| `answered` | ответ дан или задача готова | Requests | **отвечен** |
| `closed` | закрыт: автор подтвердил, или 7 дней после `answered` без ответа автора | Requests; бот — по кнопке автора «Вопрос решён» | **закрыт** |
| `declined` | не к команде AID или дубль; причина автору обязательна | Requests | **закрыт** · причина |
| `withdrawn` | автор отозвал | бот, по кнопке автора | **закрыт** |

Правила:

- Статус — сообщение `{type: "status", replyTo, status, taskId?}` в
  цепочке запроса; текущий статус — последнее такое сообщение.
- **Бот сам ставит только `new`, `withdrawn` и `closed` по кнопке
  автора** — пишет `status` в `ai-requests`. `new` — само сообщение
  `request`. Остальное — по сообщению от Requests в `bot`: бот статусы не
  выводит сам из переписки.
- `waiting-author` → `taken` — когда бот положил ответ автора; ставит
  Requests, прочитав ответ.
- Без ответа автора на вопрос 7 дней — Requests решает: `declined` с
  причиной «нет ответа» или подождать.
- `in-task` → `answered`: задача в сервисе стала «готово» — Requests
  пишет автору итог (раздел 3).
- Каждая смена статуса — сообщение боту `{type: "status", replyTo,
  status, taskId?}`; бот обновляет строку на посте и в `/tasks`, а ЛС
  автору пишет только при `in-task`, `answered`, `declined`.

### Защита от зацикливания

Решение Team: 3 сообщения подряд в одной цепочке без человека — сервис
отвечает `409`, переписка уходит куратору задачи.

- Сообщения автора, которые бот кладёт в `ai-requests` (`type: "reply"`,
  `onBehalfOf: "human"`), считаются сообщениями человека и сбрасывают
  счётчик.
- Служебные сообщения бота (`delivery-failed`) — не человек.
- На `409` бот **не повторяет** отправку: пишет `WARNING` в лог и больше
  ничего не делает — дальше ведёт куратор.

## 5. Запрос → задача

Сервис задач **читается открыто** (`GET /v1/tasks` без ключа), поэтому в
задачу из запроса идёт только то, что можно показать всем:

| В задачу | Не в задачу |
|---|---|
| название и описание, **переписанные Requests** своими словами | исходный текст автора как есть |
| `kind`, `kit`, `component` | имя, Telegram, `author.ref` |
| ссылка на запрос: `requestId` (без содержимого) | скрины |
| `author.login`, если он есть и автор согласен быть в задаче | ссылка на Figma — до решения PD (раздел 7) |

Задачу заводит Requests своим ключом AI-инженера, куратор — по §11. У
задачи — ссылка типа `message` на запрос (`requestId`), её делает
сервис (Team); содержимое запроса по ссылке без ключа не читается.
Изменения своих задач Requests берёт из ленты событий с фильтром
`source=ai-requests`.

Что ещё допустимо хранить в сервисе задач о запросе — решает Team
(пожелание Requests e); этот контракт задаёт нижнюю границу: ничего
личного.
Requests не обещает автору срок и решение (карточка Requests).

В этот публичный репозиторий ничего из запросов не попадает: ни тексты,
ни имена, ни ссылки на файлы.

## 6. Что не меняется в боте

Решение за владельцем бота и PD — до него контракт ничего не отключает:

- пост в канале «AID Judgment», согласование лидом, «Взять в работу»
  исполнителями — работают как сейчас;
- Requests видит запрос **параллельно** и отвечает на вопросы (`question`)
  и уточнения; задачи по `bug` / `edit` / `new` заводит, только если лид
  согласовал заявку в боте (статус бота `handed_off`).

Как совместить два потока окончательно — открытый вопрос (раздел 7).

## 8. Готово, когда

1. Запрос из визарда за минуту появляется во входящих `ai-requests` со
   всеми полями раздела 1; повторная отправка того же — без дубля.
2. Сообщение Requests с `expectsReply` доходит автору с подписью
   «AI-инженер» и кнопкой; ответ автора возвращается в `ai-requests` с
   тем же `requestId`.
3. Смена статуса видна автору в `/tasks` и на посте в канале простым
   статусом: принят → в работе → отвечен → закрыт.
4. Автор без `/start` — Requests получает `delivery-failed`.
5. В задаче, заведённой из запроса, нет ни имени, ни Telegram, ни
   исходного текста автора.
