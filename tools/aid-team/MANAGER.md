# AID Team — менеджер команды

Как устроена роль менеджера инженеров в оркестрации AID. Решение PD
2026-10-06 («1в, но ставит мне, а я сам решаю — мне или другому
делегирую; 2 он сам решит; 3 да; 4 да»), расширено ADR-042
(2026-10-07): задачи ставит любой любому. Людей здесь нет — только логины
и роли; кто есть кто — база `team-data` (`STORAGE.md`).

## Что может менеджер

С ADR-042 (2026-10-07) задачи ставит **любой** человек из
`docs/hub/owners.json` любому другому, и менеджер в том числе. Поток
«менеджер → только PD» из решения 2026-10-06 стал частным случаем:
менеджер может по-прежнему ставить задачи PD, а может — сразу инженеру.

| Действие | Как | Скилл |
|---|---|---|
| Видеть, что у кого в работе, что застряло, что ждёт PD | сводка по людям из досок, PR и задач | `/team` |
| Ставить задачу любому, в том числе PD | issue `[TASK @<логин>] …`, получатель — по имени, фамилии, Telegram или логину | `/task` |
| Передать задачу, если он её исполнитель | комментарий «Передаю @<логин>» | `/delegate` |
| Найти человека по имени, фамилии, Telegram, логину | личный ключ на чтение базы | `READER.md` |
| Видеть расходы Облака | роль просмотра платёжного аккаунта | см. ниже |

Менеджер **не** утверждает работу продуктов и системный уровень — это
по-прежнему владельцы и PD (`ORCHESTRATION.md` §9). Задача — не
разрешение: она говорит «сделай», а не «можно».

## Поток задачи (ADR-042)

```
любой ──/task──▶ issue «[TASK @x] …»        (без меток: метки ставит только PD)
                     │  бот → Telegram x
                     ▼
        x: «Беру»  ──или──  «Передаю @y» (/delegate) ──▶ бот → Telegram y и автору
                     │
                     ▼
        «Готово: <PR>» ──▶ бот → Telegram автору; issue закрыт ссылкой на PR
                     │
        /team показывает статус на каждом шаге; /plan каждого Штаба —
        задачи, где он текущий исполнитель
```

- **Текущий исполнитель** — логин из заголовка, затем последний
  «Передаю @логин» от тогдашнего исполнителя или PD.
- **Автор** задачи и комментариев сверяется с `docs/hub/owners.json`
  (§9 «Проверка авторов»): от логина не из списка — не задача, бот молчит.
- **Уведомление** — бот «AID · Bot · Request» в Telegram (§9 «Уведомления
  в Telegram»); пока бот не готов — письмо GitHub по упоминанию `@логин` и
  `/plan`.
- **Репозиторий публичный:** в issue — суть задачи, без имён, контактов
  и закрытых данных. Человек обозначается логином.

## Метки

Метки может ставить только PD (единственный collaborator), поэтому
получатель — в заголовке, а метки не обязательны.

| Метка | Что значит | Ставит |
|---|---|---|
| `for:<логин>` | PD явно назначил исполнителя | PD, по желанию (`/delegate`) |
| `task`, `hub`, `to:hub` | задачи 2026-10-06 по старой схеме `[TASK]` → PD | PD при приёме |

## Сводка `/team`

По запросу в чате менеджера. Расписание — на выбор менеджера (решение PD:
«он сам решит»); в Cursor — см. «Менеджер в Cursor».

## Расходы Облака

Роль на платёжном аккаунте `aidteam` — только просмотр: расходы, бюджеты,
оповещения. Делает PD, один раз:

1. Менеджер сообщает PD свой Яндекс ID — лично, не в репозиторий.
2. Консоль Облака → **Организация** → **Пользователи** → **Добавить
   пользователя** → его Яндекс ID.
3. **Биллинг** → платёжный аккаунт → **Управление доступом** →
   **Назначить роли** → пользователь → роль `billing.accounts.viewer`.
4. По желанию — добавить его получателем оповещений бюджета 500 ₽.

## Где скиллы

Подключены Штабом 2026-10-06 (решение PD «да» в Штабе): скиллы лежат в
`.claude/skills/` репозитория и доступны в любой сессии, открытой в его
рабочей копии. Содержание ведёт «AID · Ops · Team» — PR в эти файлы.

| Скилл | Где вызывать |
|---|---|
| `.claude/skills/team/SKILL.md` — `/team` | любой Штаб, прежде всего менеджера |
| `.claude/skills/task/SKILL.md` — `/task` | любой Штаб |
| `.claude/skills/delegate/SKILL.md` — `/delegate` | любой Штаб: исполнитель задачи или PD |

`/plan` каждого Штаба собирает задачи, где он текущий исполнитель;
менеджер отмечен в `docs/hub/owners.json` (`"manager": true`); роль и
поток — `docs/hub/ORCHESTRATION.md` §9 «Менеджер команды» и «Задачи между
людьми».

## Менеджер в Cursor

Менеджер работает не в Claude Code, а в Cursor (PD 2026-10-06; в карточке
`tool: cursor`). Всё выше остаётся в силе; отличия:

| Что | Claude Code | Cursor |
|---|---|---|
| Штаб | сессия «AID · Hub · Штаб» по набору `docs/hub/kit` | чат агента Cursor в клоне репозитория; набор `kit` не нужен — менеджер не ведёт продуктов, досок и PR |
| Скиллы `/team`, `/task` | `.claude/skills/` | Cursor читает `.claude/skills/` сам; вызов — `/team`, `/task` или словами («кто что делает», «поставь задачу PD») |
| Сообщения между чатами | `SendMessage` | нет; связь с людьми — только задачи `[TASK @логин]`, `/team` и уведомления бота в Telegram |
| Расписание сводки | расписание задач Claude | вручную `/team`; при желании — Cursor CLI по расписанию macOS (ниже) |
| Правила | `CLAUDE.md` | правила в самих скиллах и `READER.md`; корневой `CLAUDE.md` и `AGENTS.md` Cursor тоже читает |

**Подготовка в Cursor — один раз:**

1. `brew install gh`, `gh auth login` — свой GitHub-логин.
2. `git clone https://github.com/RickOBrian/aid ~/Projects/aid` и открыть
   папку в Cursor. Обновлять перед работой: `git pull`.
3. Ключ на чтение базы — `READER.md`.
4. **Privacy Mode в Cursor — включить** (Settings → General → Privacy
   Mode). База команды — личные данные; с выключенным режимом то, что
   агент прочитал из `people.json`, может храниться у Cursor.

**Сводка по расписанию (по желанию).** Cursor CLI (`cursor-agent`) умеет
выполнить запрос без окна; macOS запускает его по расписанию через
`launchd` или `cron`, например каждый будний день в 9:00:
`cd ~/Projects/aid && git pull -q && cursor-agent -p "Выполни скилл .claude/skills/team/SKILL.md" > ~/aid-team-$(date +%F).md`.
Команда — пример: имя и флаги CLI проверить на машине менеджера
(`cursor-agent --help`). Настраивать — в самом Cursor по просьбе
менеджера, с его согласия.
