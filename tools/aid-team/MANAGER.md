# AID Team — менеджер команды

Как устроена роль менеджера инженеров в оркестрации AID. Решение PD
2026-10-06 («1в, но ставит мне, а я сам решаю — мне или другому
делегирую; 2 он сам решит; 3 да; 4 да»). Людей здесь нет — только логины
и роли; кто есть кто — база `team-data` (`STORAGE.md`).

## Что может менеджер

| Действие | Как | Скилл |
|---|---|---|
| Видеть, что у кого в работе, что застряло, что ждёт PD | сводка по людям из досок, PR и issues | `/team` |
| Ставить задачи | **только на PD**: issue с меткой `task`; PD делает сам или делегирует | `/task` |
| Найти человека по имени, фамилии, Telegram, логину | личный ключ на чтение базы | `READER.md` |
| Видеть расходы Облака | роль просмотра платёжного аккаунта | см. ниже |

Менеджер **не** утверждает работу продуктов и системный уровень — это
по-прежнему владельцы и PD (`ORCHESTRATION.md` §9). Ставить задачи
инженерам напрямую он не может: всё идёт через PD.

## Поток задачи

```
менеджер ──/task──▶ issue «[TASK] …» (без меток: менеджер не collaborator)
                        │
               /plan PD │ находит по заголовку и автору, ставит hub, to:hub, task
                        ▼
         PD: делаю сам  ──или──  /delegate «передай Артуру»
                                     │ метка for:<логин>, комментарий @логин
                                     ▼
                     /plan инженера видит for:<свой логин>
                     → берёт, отвечает комментарием, PR
                                     │
                         закрыто ссылкой на PR
                                     ▼
               /team менеджера показывает статус на каждом шаге
```

- **Автор** задачи и комментариев сверяется с `docs/hub/owners.json`
  (§9 «Проверка авторов»): задача засчитывается, только если автор —
  менеджер или PD; делегирование — только от PD.
- **Уведомление** исполнителя: упоминание `@логин` в комментарии
  делегирования — GitHub пришлёт письмо; `/plan` его Штаба подберёт issue.
- **Репозиторий публичный:** в issue — суть задачи, без имён, контактов
  и закрытых данных. Человек обозначается логином.

## Метки

| Метка | Что значит | Ставит |
|---|---|---|
| `hub`, `to:hub` | запрос в Штаб PD (есть) | `/plan` PD при приёме |
| `task` | задача от менеджера принята PD | `/plan` PD при приёме |
| `for:<логин>` | PD делегировал исполнителю | `/delegate` |

Ставить метки может только collaborator, а он в репозитории один — PD.
Поэтому менеджер создаёт issue без меток, с заголовком `[TASK]`, а метки
ставит Штаб PD. Метку `task` заводит Штаб; `for:<логин>` создаёт
`/delegate` при первом делегировании.

## Сводка `/team`

По запросу в чате менеджера. Расписание — на выбор менеджера (решение PD:
«он сам решит»): ежедневная сводка заводится в его Claude через
расписание задач, текст запуска — `/team`.

## Расходы Облака

Роль на платёжном аккаунте `aidteam` — только просмотр: расходы, бюджеты,
оповещения. Делает PD, один раз:

1. Менеджер сообщает PD свой Яндекс ID — лично, не в репозиторий.
2. Консоль Облака → **Организация** → **Пользователи** → **Добавить
   пользователя** → его Яндекс ID.
3. **Биллинг** → платёжный аккаунт → **Управление доступом** →
   **Назначить роли** → пользователь → роль `billing.accounts.viewer`.
4. По желанию — добавить его получателем оповещений бюджета 500 ₽.

## Что подключает Штаб

Скиллы лежат здесь, в `skills/`; устанавливает их Штаб
(`.claude/skills/`, набор `docs/hub/kit/`), протокол и метки — тоже он:

- `skills/team/SKILL.md` → Штаб менеджера;
- `skills/task/SKILL.md` → Штаб менеджера;
- `skills/delegate/SKILL.md` → Штаб PD;
- в `/plan` всех Штабов: собирать issues `for:<свой логин>`; в `/plan` PD
  — раздел «Задачи от менеджера»: открытые issues `[TASK] in:title` от
  автора с пометкой менеджера в `owners.json`, при приёме — метки `hub`,
  `to:hub`, `task`;
- в `ORCHESTRATION.md` §9 — роль менеджера и поток выше;
- в `owners.json` — пометка менеджера у его логина.
