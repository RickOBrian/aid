# AID Style Migration — чат плагина

Figma-плагин для Presentbook. Отдельный продукт: с Token Comparator общих
кода, сборки и релизов нет. Корневой `CLAUDE.md` действует тоже — особенно
разделы «Три продукта — три чата», «Стыки между продуктами» и
«Git-полномочия».

## Программа AID — читать первым

Сейчас главная работа — **программа AID**: учимся работе дизайнера
(разборы экранов), накапливаем знание о продуктах, потом делаем
инструменты. Плагин заморожен до экзамена (D-1). Учат модель главный
инженер (Principal Designer) и инженеры из `teachers.json`, с любых
аккаунтов. Между сессиями модель помнит только то, что записано в
репозитории.

В начале каждой сессии, до любой работы, прочитать:
1. `docs/program.md` → «Где остановились» — состояние и следующий шаг;
2. `docs/decisions.md` — решения (D-n); в переписке решения не живут;
3. `docs/method.md` — метод разбора (M…, MR…);
4. `docs/mistakes.md` — мои прошлые ошибки, не повторять;
5. для работы с продуктом — `products/<id>/knowledge/` (`rules.json`, `README.md`);
6. `docs/teaching.md` — как устроены уроки, кто что решает;
7. запустить `node tools/aid-style-migration/scripts/knowledge/check.cjs driver` —
   он покажет очередь главного инженера (уроки и споры, ждущие решения).

Потом коротко сказать, где мы и что в очереди, и ждать решения человека.

**Три слоя знания — не смешивать** (D-15):
- стандарты ДС — `skills/_shared/standards/`, общий эталон, к которому
  стремится любой продукт; только читаем;
- знание о продукте — `products/<id>/knowledge/`, как продукт устроен
  сейчас;
- метод — `docs/method.md`.

**Кто решает.** Правила продукта, метод и споры утверждает только главный
инженер. Инженеры — вайбкодеры, не дизайнеры: им задаю вопросы о фактах,
дизайнерские вопросы складываю в очередь главного инженера (MR2). Урок
инженера — файл в `inbox/`, а не правка канона.

**Как работаем:** сначала план и «да», потом шаг; после шага — остановка
и показ результата. Предлагать на равных: идеи, возражения, риски.
Вопросы главному инженеру — с визуалом (MR1).

## Правило закрытия шага

Шаг не закрыт, пока не пройдено всё:
1. Новое знание записано **уроком** в `inbox/` (дата-автор-тема.json).
   Канон (`rules.json`, `method.md`, `findings/`) меняется только по
   уроку, который принял главный инженер.
2. Решение главного инженера — в `docs/decisions.md` (D-n), урок →
   `accepted` с `appliedIn`.
3. Моя ошибка — в `docs/mistakes.md` с защитой: правилом, решением или
   эталонным случаем.
4. `check.cjs` проходит без ошибок.
5. «Где остановились» в `docs/program.md` обновлено.
6. Коммит и пуш в рабочую ветку (слияние в `main` — только с
   разрешения).
7. Локальная память модели — только ссылки на эти файлы, без знания.

## Задача

Есть файл макетов с плохой системой стилей и компонентов: он не тянет ни
одну из наших библиотек. Плагин переводит такие макеты на токены и
компоненты выбранного продукта (Driver, Rider или будущего) так, чтобы
**структура макетов не менялась**, а визуально они стали макетами этого
продукта. Чего в библиотеке продукта не хватает — плагин предлагает
добавить или изменить.

Для кого — дизайнеры команды, как у Token Comparator. Плагин не только
чинит, но и предлагает решения уровня Principal Designer — с основанием
из образцов продукта или стандартов ДС. Гайд пользователя — `GUIDE.md`.

Как работает, по шагам:

1. **Область** — выделение, страница или набор страниц (выпадающий список с
   чекбоксами).
2. **Сборка** — макеты разбросаны по страницам и канвасам; плагин собирает
   их, дублирует на страницу `AID Migration` (создаёт, если её нет) и
   аккуратно расставляет парами «было → стало». Исходные макеты не трогаются.
3. **Материалы продукта** — на что опираемся. По умолчанию пять видов:
   токены и стили, компоненты, иконки, образцовые макеты (как продукт
   выглядит и какие токены и компоненты для каких ролей использует),
   стандарты ДС. Список расширяемый — см. трекер, «Материалы продукта».
   Выбор — через плагин, по образцу выбора библиотек в Token Comparator;
   доступ — и через PAT + REST API, и через индексацию открытого файла.
4. **Перевод** — сырые значения и чужие стили/переменные → токены продукта;
   чужие инстансы, локальные компоненты и ручные фреймы → компоненты
   продукта. Исходник может визуально совсем не походить на продукт
   (другие цвета, шрифты, радиусы), поэтому перевод идёт **по роли, а не по
   значению**: акцент исходника становится акцентом продукта, иерархия
   текста — иерархией продукта. Пользователь решает на уровне карты стиля,
   а не каждого цвета.
5. **Ревью** — «было → стало» рядом, визуально и текстом: что переехало
   хорошо, что спорно, что нужно добавить или изменить в библиотеке.

Плагин не привязан к продукту: библиотеки и образцы выбирает пользователь.
Решения и план — `docs/audit-2026-09-29.md`.

## Решения, которые действуют всегда

- **Без сервера** — всё локально, как у Token Comparator до бэкенда.
  Появится сервер — это новый контур, см. «Когда появится код».
- **Профиль маппинга** хранится в плагине (`clientStorage`) с экспортом и
  импортом JSON. Общий реестр профилей — позже.
- **Код Token Comparator не импортируется** — нужное копируется сюда и
  развивается независимо. Общий пакет — после готовности обоих плагинов,
  решение Principal Designer.
- **Визуальный стиль интерфейса — общий с Token Comparator**, интерфейс
  компактный. Плагины одной компании, но функционально не связаны.
- **Продукт — это данные, а не код.** Один запуск — один целевой продукт.
  Всё продуктовое (библиотеки, образцы, коллекция темы и её режимы) — в
  профиле продукта; имён продуктов и режимов (`Day`, `Night`, `Light`…) в
  `src/` нет. Новый продукт подключается профилем, без правки кода.
- **Тёмная тема обязательна**, даже если в исходнике её нет: «Стало»
  показывается во всех режимах темы продукта. Колонка тёмного режима —
  производная от светлой, руками не правится.
- **Предложения в библиотеку** — отдельная страница в том же файле;
  оформление — токенами целевого продукта, без захардкоженных цветов.
- **Правила рекомендаций — пакетами.** Сейчас пакет один — «продукт»
  (библиотека и образцы). Стандарты ДС подключатся позже вторым пакетом
  без переделки движка; у каждой находки с первого дня есть `source` и
  `level`, режим стандартов (`off` / `reference` / `enforced`) — в профиле
  продукта. Подробно — трекер, «Уровень Principal Designer».
- **Знание о продукте — общее, не в плагине** (2026-09-30, уточнено
  D-1, D-14, D-15): данные в `products/<id>/knowledge/`, формат —
  `docs/knowledge-format.md`, источник правды — репозиторий; эталон —
  библиотека и стандарты, а не статистика макетов. Плагин читает,
  изменения предлагает уроком. Проект ADR `docs/adr-draft-product-language.md`
  принят в редакции «Знание о продукте» как ADR-039; `style-language.json`
  не заводится.
  База знаний общая с Token Comparator, код раздельный.
- **Под капотом — модули, в интерфейсе — одно окно:** движок (роли,
  сопоставление) без Figma API, адаптеры Plugin API и REST; изучение
  образцов и в плагине, и позже пакетно по REST; ревью языка продукта —
  в плагине, позже в Presentbook.
- **Интерфейс — маленькое понятное окно** (Principal Designer,
  2026-09-30): не перенасыщать; вести по шагам (Собрать → Перевести →
  Проверить → Подача), редкое — в настройки, второстепенное — свёрнуто,
  по умолчанию показывать то, что требует решения. Смотреть результат —
  на канвасе, окно — для решений.
- **Чисто, а не грубо:** неуверенные решения карты не привязываются —
  остаются как в исходнике с пометкой «нужно решение». Плагин —
  консультант: находит недочёты библиотеки и предлагает улучшения по
  стандартам ДС; решение — за дизайнером и главным по AID.
- **Никогда не отвязываем инстансы.** Цвета и текст внутри инстансов —
  оверрайды; отступы и радиусы внутри инстансов — замена компонента или
  предложение библиотеке (агент и джун оба отвязывали — `docs/`).
- **Подача — на канвасе, как в эталоне Test-2** (`docs/reference-test2-2026-09-30.md`):
  зеркальные секции ДО · X | ПОСЛЕ · X | ПОСЛЕ NIGHT · X, библиотека «как
  станет», маппинг апгрейда, примеры До/После на элементах, сравнение
  экранов, гайд. Всё генерируется из данных плагина.
- **AI в плагине нет.** Ядро детерминированное; подсказки от модели —
  возможность на будущее.
- **Наработки Figma Agent** (скилл wb-aid-core/rules/steps) — референс и
  идеи, не источник правды. Разбор — в `docs/audit-2026-09-29.md`.

## Проверки перед тем, как считать работу готовой

```bash
npm run typecheck && npm test && npm run build
```

`dist/` — результат сборки, в git не хранится и руками не правится.
Зависимости — те же, что у Token Comparator, `package-lock.json` взят у
него: свежий `npm install` падает на удалённом `std-env@4.3.0` (трекер,
«Замечено попутно»). Новая зависимость — вопрос к Principal Designer.

Проверка в Figma: Plugins → Development → Import plugin from manifest →
`tools/aid-style-migration/manifest.json` (после `npm run build`).
