**Почему без сервера (№10).** Все этапы до ревью включительно работают
внутри Figma: чтение библиотек — напрямую из плагина через REST API, профиль
и индекс — в `clientStorage`, предложения в библиотеку — экспорт файлом.
Сервер понадобится только для общего реестра профилей или отправки
предложений на согласование; тогда он заводится как новый контур по
правилам корневого `CLAUDE.md`.

## Разбор наработок Figma Agent

Источник: скилл wb-aid-core / wb-aid-rules / wb-aid-steps и три документа к
нему (Guide, Risks, Recommendations). Статус — референс уровня junior:
направление верное, реализация и часть фактов — нет.

### Что берём

- Работа на копиях, оригиналы не трогаются.
- Последовательность «инвентарь → маппинг → валидация → замена → проверка →
  отчёт».
- Поиск ручных фреймов, которые должны быть компонентами (шаг 02b), и
  признак «фрейм с заливкой + вложенные инстансы = кандидат в составной
  компонент» (правило 32).
- Пробелы библиотеки фиксируются и превращаются в предложения (правила 13,
  17, 26).
- Правила 1–32 — как список регрессий, которые Verifier должен ловить
  автоматически.
- Пары «было / стало» на одной странице. Для нас это не избыточность, а
  требование ревью (решение №4, №6).

### Что не берём и почему

1. **Визуальное совпадение как условие замены** (правила 19, 27, 31). При
   смене стиля размеры, радиусы и цвета *должны* меняться, и проверка
   заблокирует каждую правильную замену. Разделяем: *эквивалентность
   назначения* (роль, оси, свойства, слоты) и *регрессия вёрстки*
   (геометрия: сдвиги, обрезанный текст, выход за родителя).
2. **Маппинг по ключам old → new.** Наш исходный файл не тянет ни одну
   библиотеку — ключей-пар нет. Нужна классификация по роли и значению:
   цвет заливки текста ≠ цвет фона при одинаковом HEX. Правило «не маппить
   только по HEX» верное, но для нас это ядро, а не примечание.
3. **Маппинг на уровне сета.** Нужен уровень варианта и свойств: оси и
   значения, TEXT / BOOLEAN / INSTANCE_SWAP. Правила 1, 2, 9, 12, 15 —
   симптомы отсутствия маппинга свойств.
4. **Checkpoint в `pluginData`** — хранит метаданные без оверрайдов, откатить
   по нему нельзя. Вместо него — журнал операций с откатом по ноде.
5. **Батчи по 5 и Gate Check** — ограничение контекста агента. В плагине —
   dry run по всей области, ревью, затем применение.
6. **`safeTraverse` с `maxDepth`** — глотает ошибки, молча режет глубину,
   медленный. Вместо него — `findAllWithCriteria`,
   `skipInvisibleInstanceChildren`, `getMainComponentAsync`.
7. **Таблица отчёта на канвасе с HEX и Google Sans** — нарушает
   `no-hardcode-color-protocol`. Ревью живёт в интерфейсе плагина, экспорт —
   файлом; на канвасе — только пары «было / стало» с метками.

### Качество документов

- Заявлено 32 правила — фактически 31 (нет 23); в гайде упомянуто «28».
- Дубли: 19 = 25; 1 ≈ 2 ≈ 9; 6 ≈ 7 ≈ 12.
- Противоречие: 5 (не перекрашивать инстанс) vs 12 (восстановить цвет) vs
  17 (не делать молчаливых оверрайдов).
- «95%+ покрытия» ничем не подтверждено.

### Факты API — проверить на этапе 0

| Утверждение наработок | Наше ожидание |
|---|---|
| Виртуальные инстансы бросают исключения | Бросает синхронный `mainComponent` при `documentAccess: dynamic-page`; нужен `getMainComponentAsync()` |

## Этап 1 — что сделано

- **Область:** выделение или страницы с галочками и фильтром по тексту
  («✅» — фильтр, а не правило в коде). Страница «AID Migration» в список
  не попадает.
- **Экраны:** фрейм, инстанс, компонент или группа размером с устройство
  (телефон 280–480, планшет 560–1100, десктоп 1180–2000 по ширине, высота
  от 120 — модалки проходят), в том числе внутри секций. Картинки размером
  с экран — отдельно, по умолчанию не собираются. Остальное — «не экраны»
  с причиной.
- **Тёмные пары:** тёмный экран — по слову в имени (night / dark /
  тёмная — синонимы) или по яркости фона корня ниже 0,2; пара — то же имя
  без слов темы и та же структура, иначе та же структура и ближайший.
  Разъединить — в списке; связать — выделить два экрана на канвасе.
- **Сборка:** секция «Сборка · <страница>» на «AID Migration», **плитка на
  экран** по сетке с переносом (секция ≈ 1,6 : 1). В плитке — «Было» и
  «Было · тёмная» рядом; копий «Стало» на этапе 1 нет — появятся с
  переводом. Имя плитки — ссылка на исходник. «Было · тёмная» без
  тёмного макета — копия с тёмным режимом коллекции темы исходника. У копий
  чистится pluginData, ставятся метки роли и источника.
- **Повтор:** секция уже есть — вопрос «заменить / добавить версию рядом /
  отмена». «Разобрать сборку» убирает только секции плагина.
- **Тесты:** экраны, словарь темы, пары, раскладка, план строк; страж
  «движок не знает продуктов» (словарь темы — законное исключение для
  имён режимов).

Что проверить в Figma:

1. Страницы «✅» → «Найти экраны»: не пропущены ли экраны и не попал ли
   мусор; причины в «Не экраны».
2. Тёмные пары: нашлись ли; верно ли «разъединить» и «связать».
3. «Собрать»: ровная ли сетка, читаются ли подписи, работает ли ссылка на
   исходник, как выглядит «Было · тёмная» из темы исходника.
4. Повторная сборка → вопрос; «Разобрать» → чисто.
5. Время сборки на всех «✅» страницах.

## Этап 2a — что сделано

- **Вкладка «Продукт»:** выбрать, создать, удалить (в два шага), экспорт и
  импорт профиля файлом `<id>.aid-profile.json` вместе с индексами.
- **Материалы из открытого файла:** «Изучить открытый файл» → плагин
  считает переменные, стили, компоненты и предлагает, чем файл служит
  (токены; иконки, если ≥ 70 % компонентов не больше 48×48; иначе
  компоненты) → пользователь подтверждает → индекс в `clientStorage`
  (ключ на материал). Компоненты с `_` и `.` в начале имени не
  индексируются — Figma их не публикует.
- **Тема:** после индекса токенов плагин предлагает коллекцию с тёмным
  режимом (роль по словарю темы; второй режим пары — светлый);
  пользователь меняет коллекцию и роли режимов.
- **Чего не хватает:** список недостающих материалов с последствиями.
- **Подключена ли библиотека токенов в текущем файле** — по имени
  библиотеки у `teamLibrary`; для компонентов и иконок проверки нет — API
  не перечисляет их библиотеки.
- **Стражи:** роли темы — константы в словаре, без строковых литералов в
  движке (страж поймал это при написании).

**Первая проверка (2026-09-29):** индекс токенов показал 7 коллекций и 351
переменную, а подключённая библиотека на этапе 0 — 6 и 161. Разница —
скрытые от публикации переменные (примитивы Core): файлам с макетами они
недоступны, переводить на них нельзя. Исправлено: у коллекций,
переменных и стилей есть признак `published`, в карточке — опубликованные
и отдельно «скрытых от публикации»; тема выбирается только из
опубликованных. Заодно индекс хранит итоговые значения по режимам
(ссылки семантика → примитив пройдены) — для перевода и контраста.
Индекс токенов нужно пересобрать.

Что проверить в Figma:

1. «Продукт» → создать «Driver».
2. Открыть файл «WB AID Driver Tokens & Styles», запустить плагин →
   «Изучить открытый файл» → «Токены и стили» → «Проиндексировать».
   Ожидаем: 6 коллекций, ~161 переменная, стили текста и эффектов; тема
   `color-sem` day → светлая, night → тёмная.
3. То же в «WB AID Driver Components» (компоненты) и «Driver Icons»
   (иконки: ~315).
4. В файле Flot Tasks — у токенов бейдж «подключена в этом файле».
5. Экспорт → импорт: профиль восстанавливается.

## Этап 2b — что сделано

- **Образцы — ещё один вид материала.** «Изучить открытый файл» в файле
  образцов считает экраны текущей страницы и предлагает «Образцовые
  макеты»; область — текущая страница или выделение.
- **Только экраны, не обвязка:** тот же распознаватель, что в сборке —
  стрелки, ромбы, заметки не читаются. Не больше 80 экранов, равномерная
  выборка: файл большой (спайк).
- **Что собирается (агрегаты, не ноды):**
  - токен → где встречается: фон экрана, поверхность, текст, иконка,
    обводка, эффект, радиус, отступ, промежуток, размер — **отдельно в
    светлых и тёмных экранах**;
  - стиль текста → сколько раз, кегль, **регистр как видит
    пользователь** (капс от `textCase` стиля тоже капс);
  - компонент → сколько раз и **регистр подписей внутри** (кнопки);
  - значения без токена и текст без стиля — насколько образец сам
    следует библиотеке.
- **Внутрь инстансов не идём** (там устройство компонента, а не решения
  автора образца) — кроме регистра подписей.
- **Доверие к образцам:** сколько использованных токенов нашлось в
  опубликованных токенах продукта.

Что проверить в Figma:

1. Открыть «✅ Driver App • Order», страницу с «✅ Order MERGED»,
   запустить плагин → «Продукт» → «Изучить открытый файл». Ожидаем:
   предложены «Образцовые макеты», экранов на странице — десятки.
2. «Проиндексировать» (текущая страница). Ожидаем: до 80 экранов, есть
   тёмные; «токенов в ходу» и «из них из токенов продукта» — второе
   близко к первому, если образцы собраны на библиотеке.
3. Время индексации.

## Решения по открытым вопросам (2026-09-29, Principal Designer)

| Вопрос | Решение |
|---|---|
| Режимы | Тёмную тему делать нужно, даже если в исходнике её нет; показывать, как выглядит результат. Учесть: тёмной темы нет / есть отдельными макетами / есть, но токены применены неправильно |
| Продукт за запуск | Один. Новые продукты (третий, четвёртый…) должны подхватываться быстро и безболезненно |
| Куда предложения | Сейчас — на отдельную страницу в том же файле (похоже на печать таблицы в Token Comparator). Дальше разовьём |
| Тёмные дубликаты исходника | Сводятся в один «Стало» с колонками режимов, а не переводятся двумя макетами |
| Метки проблем | Рядом с экраном (номер → описание), не поверх элементов |
| Анализ и применение | Анализ и карта стиля — по всей области; применение — целиком или выборочно |
| Night, Dark, тёмная | Синонимы — одна роль «тёмная тема». Плагин узнаёт их в именах экранов и режимов, в профиле хранится роль, а не имя |
| «Было · тёмная» | Строится и из собственной тёмной темы исходника (режим его коллекции темы), если тёмного макета нет |
| Картинки-скриншоты экранов | На этапе 1 — в списке с пометкой «картинка», по умолчанию не собираются; можно включить — попадут в «Было» как есть. **Будущее:** собирать интерфейс по скриншоту из библиотек продукта и стандартов |
| Повторная сборка | Если секция уже есть — спросить: заменить, добавить версию рядом или отменить. Исходники всегда на своих местах — откат и «было / стало». **Будущее:** режим «поверх исходников» для уверенного пользователя (с журналом отката) |
| Колонка Night | Строит только плагин, руками не правится; нужна правка — чинится «Стало · Day» |

## Материалы продукта (2026-09-29, решение Principal Designer)

Профиль продукта — это **набор материалов**, на которые плагин опирается.
Пять видов по умолчанию, но список расширяемый — «не только их».

| Вид | Что плагин из него берёт | Для чего | Доступ | Без него |
|---|---|---|---|---|
| **Токены и стили** | Переменные с режимами, стили текста и эффектов, описания | Во что переводить; что вообще существует | REST или открытый файл (стили текста/эффектов иначе не перечислить — спайк) | Перевод невозможен — единственный обязательный |
| **Компоненты** | Компоненты и наборы, варианты, свойства, анатомия | Замена инстансов и ручных фреймов | REST или открытый файл | Только токены; компоненты — в предложения |
| **Иконки** | Иконки, их формы и имена | Замена иконок | REST или открытый файл | Иконки не трогаются |
| **Образцовые макеты** | Статистика: какой токен и компонент для какой роли, сколько уровней текста, как выглядят карточки, кнопки, регистр текста | Определение ролей, спорное, рекомендации | REST или открытый файл | Роли — только по именам и описаниям токенов, уверенность ниже, рекомендаций меньше |
| **Стандарты ДС** | Пакет правил `must` / `should` / `may` | Группа «На будущее», позже — проверка | Файл-пакет | Группы нет |

**Старшинство при противоречии:** токены и компоненты решают, *что
существует*; образцы — *как это принято использовать*; стандарты — *как
должно быть в идеале* (не ломают текущее). Образец использует токен
вопреки его описанию — это находка «образец расходится с библиотекой», а
не новое правило.

**Расширяемость.** Каждый вид материала — адаптер одного формата: откуда
читать, что извлекать, как кэшировать, что даёт движку. Новый вид —
новый адаптер, без переделки движка (как пакеты правил). Кандидаты:

- **внешние компоненты** — системные киты (клавиатура, статус-бар,
  android): не переводятся, не входят в статистику (спайк, п. 5);
- **гайд по текстам** — регистр кнопок и заголовков и т. п. (спайк, п. 2);
- **ассеты и иллюстрации** продукта, в том числе тёмные версии;
- **платформенные гайдлайны** (iOS / Android).

Профиль показывает, каких материалов не хватает и что из-за этого
работает хуже, — а не молча снижает качество.

Примеры на сегодня (Driver): все четыре файла — в `spike-2026-09-29.md`;
стандарты — `skills/_shared/standards/`.

## Продукт — это данные, а не код

Движок не знает ни одного продукта по имени. Всё продуктовое — в
**профиле продукта**:

- id и название;
- библиотеки: компоненты, иконки, токены (file key; доступ по REST или
  индексацией открытого файла);
- файлы-образцы;
- **тема**: какая коллекция отвечает за тему и какой её режим — светлый,
  какой — тёмный, какие ещё есть. Имена режимов у продуктов разные: у
  Driver это `Day` / `Night` (`products/driver/product.json`,
  `colorModeMapping`), поэтому `Light` / `Dark` в коде не хардкодим;
- подсказки ролей, выученные из образцов (какой токен для какой роли).

Новый продукт = новый профиль, созданный в плагине мастером, без правки
кода. Профиль экспортируется и импортируется JSON (решение №9). Позже
профиль можно заполнять из `products/<id>/product.json` — это связь с
репозиторием, отдельное решение.

**Страховка.** Тест в CI: в `src/` нет имён продуктов (`driver`, `rider` и
т. д.). Появилось — значит, продуктовое протекло в движок.

## Тёмная тема

### Как показываем

Страница миграции — строка на экран, колонка на режим темы продукта:

```
Было · Day  │ [Было · Night] │ Стало · Day │ Стало · Night │ [ещё режимы]
```

- «Было · Night» есть, только если в исходнике нашлась тёмная пара экрана.
- «Стало · Night» — **производная** от «Стало · Day»: копия с явным режимом
  темы на корневом фрейме (`setExplicitVariableModeForCollection`). Она
  пересоздаётся после каждого применения и руками не правится — иначе две
  колонки разъедутся.
- Режимов у продукта больше двух — колонок больше. Тёмного режима нет —
  колонка одна и заметка в ревью.

Тёмная тема получается «бесплатно» ровно настолько, насколько «Стало»
привязано к семантическим токенам. Поэтому проверка тёмной темы — это в
первую очередь проверка полноты привязки.

### Три сценария исходника

**А. Тёмной темы нет.** Переводим светлый макет; «Стало · Night»
генерируется. Всё, что не привязалось к токену, в Night остаётся светлым —
это находка, а не мелочь.

**Б. Тёмная тема отдельными макетами.** Ищем пары «светлый — тёмный»: имя
(`dark`, `night`, `тёмн`, `ночь`…), одинаковая структура дерева,
инвертированная яркость фона корня. Пару **сводим в один «Стало»** с двумя
колонками режима, а не переводим два макета отдельно. Тёмный исходник
работает дважды:

1. **как улика для выбора токена** — у ноды есть пара значений (светлое,
   тёмное), и токен должен совпасть с обоими в своих режимах. Это
   различает токены с одинаковым светлым значением намного надёжнее, чем
   один HEX;
2. **как эталон для ревью** — «Было · Night» против «Стало · Night».

Пары, которые не нашлись автоматически, пользователь сводит руками или
переводит тёмный макет как самостоятельный (токены подбираются по
значениям в тёмном режиме).

**В. Тёмная тема есть, но токены применены неправильно.** Чужим привязкам
не доверяем: они — улика, а не ответ. Берём разрешённые значения ноды в
обоих режимах и подбираем токен продукта по роли и паре значений. Светлая
и тёмная улики противоречат друг другу — «спорно», с обоими кандидатами.
Явные режимы **коллекции темы**, выставленные в исходнике на фреймах и
инстансах, в «Стало» снимаются и попадают в отчёт; режимы других осей
(платформа, язык, устройство) сохраняются — см. спайк.

### Риски и проверки

| Риск | Как ловим | Что в ревью |
|---|---|---|
| Цвет не привязан к токену (сырой HEX, пропущенная нода, оверрайд внутри инстанса) | Любая заливка, обводка, эффект в «Стало» без привязки к переменной | Блокер: «в Night останется светлым» |
| Привязан примитив (Core) вместо семантики | Переменная разрешается одинаково во всех режимах, а роль ноды — тематическая | Спорно: подобрать семантический токен |
| Токен не той роли (текстовый на фоне и т. п.) | Контраст текста к ближайшему фону в **каждом** режиме (WCAG 4.5 / 3) | Спорно или блокер по порогу |
| Растровые картинки и иллюстрации с запечённым светлым фоном, логотипы | Image fill, векторы с множеством сырых цветов | Предложение: нужен тёмный ассет |
| Тени и эффекты | Эффекты без стиля/переменной | Спорно: эффект продукта |
| Прозрачность слоя поверх цветных заливок | `opacity < 1` у ноды с заливкой | Предупреждение — в Night выглядит иначе |
| Явный режим, навязанный в исходнике | `explicitVariableModes` на нодах исходника | Снят в «Стало», в отчёт |
| Имена режимов разные у продуктов | Профиль продукта, не код | — |

## Перевод стиля, а не значений (2026-09-29, уточнение Principal Designer)

Исходные макеты могут **визуально** отличаться от продукта: другие цвета,
шрифты, радиусы, визуальный язык. Перевод — это не только починка
архитектуры, но и визуальная работа с умом. Следствия:

- **Подбор по ближайшему значению бесполезен.** Фиолетовый акцент
  исходника не «ближе всего» ни к одному токену Driver — он *роль*
  «акцент», и становится акцентом Driver.
- **Ядро — определение роли**, а не сравнение значений. Для каждой ноды:
  фон страницы / карточка / приподнятая поверхность / акцент /
  статус (ошибка, успех, предупреждение, инфо) / основной, второстепенный,
  третичный текст / разделитель / иконка. Сигналы: место в дереве, размер,
  соседи, частота, ранг размера шрифта на экране, насыщенность цвета,
  контраст к фону.
- **Сохраняем отношения, а не числа.** Темнее остаётся темнее, заголовок
  крупнее подзаголовка, отступ больше остаётся больше. Палитра исходника
  раскладывается по порядку светлоты на нейтральную шкалу продукта;
  стили текста — по рангу иерархии на типографическую шкалу продукта, а не
  по ближайшему кеглю; отступы и радиусы — на шкалу продукта с сохранением
  порядка.
- **Решения — на уровне карты стиля.** Пользователь сопоставляет не 64
  цвета по одному, а роли: «этот фиолетовый — акцент», «эти пять серых —
  нейтральная шкала», «эти 23 стиля текста — 6 уровней иерархии». Мало
  решений — большой эффект.
- **Образцы дают визуальные правила**, которых нет в токенах: как у
  продукта выглядят карточки (радиус, обводка или тень), высоты кнопок,
  стиль иконок, сколько уровней текста на экране. Плагин предлагает
  применять их к опознанным ручным элементам — с подтверждением.
- **Не трогаем автоматически:** фото и иллюстрации — только предложение
  «нужен ассет в стиле продукта».

Новые риски — в Verifier:

| Риск | Проверка |
|---|---|
| Другой шрифт и кегль → текст не влезает, переносится, наезжает | Обрезка и переполнение текста, пересечения соседей после применения |
| Шрифт продукта недоступен в файле | Проверка загрузки шрифта до применения; стоп с объяснением |
| Статусный цвет принят за акцент (синий бренд vs синее «инфо») | Такие случаи всегда «спорно» |
| Экран не похож на продукт, хотя всё привязано (9 уровней текста при 5 у образцов, лишние тени) | Сравнение со статистикой образцов — «не в стиле продукта» |
| Смысл цвета потерян (красная ошибка стала акцентом) | Статусные роли не переназначаются без подтверждения |

## Уровень Principal Designer (2026-09-29, уточнение Principal Designer)

Плагин не только чинит, но и предлагает решения — как на дизайн-ревью.
Пользовательское описание — `../GUIDE.md`, шаг 7.

- **Три слоя вывода:** исправления (привязки — применяются), решения
  (карта стиля — пользователь выбирает), рекомендации (дизайн-уровень —
  только предлагаются; структура макета — решение автора).
- **Формат рекомендации:** что вижу · почему это проблема · что предлагаю ·
  альтернатива · сколько мест · уверенность.
- **Не на вкус.** У каждой рекомендации — основание: статистика образцов
  продукта или правило стандарта. Нет основания — нет рекомендации. Это
  защита от шума.
- **Темы:** иерархия (главные действия, уровни текста, акценты),
  единообразие между экранами, доступность (контраст по режимам, зоны
  нажатия), ритм отступов, паттерны продукта, тёмная тема.
- **Источник правды для рекомендаций — продукт как он есть сейчас:**
  библиотека и образцы. Стандарты ДС (`skills/_shared/standards/`) — идеал,
  к которому Driver и Rider приведут отдельной задачей; плагин его
  учитывает, но не ломает текущее (решение Principal Designer,
  2026-09-29):
  - продукт и стандарт расходятся — перевод идёт **по продукту**;
  - расхождения со стандартом — отдельная группа «На будущее: стандарты
    ДС», свёрнута, **не влияет** на светофор, блокеры и статус «готово»;
  - предложения в библиотеку не противоречат стандарту без нужды: если
    нужен новый токен, имя — по `naming-conventions`, но если продукт уже
    живёт иначе — по соседям в продукте, с пометкой о расхождении.
- **Стандарты подключаются позже, но место под них — с первого кода**
  (решение Principal Designer, 2026-09-29). Архитектура:
  - **пакеты правил.** Движок рекомендаций не знает правил — он получает
    пакеты одного формата: `id`, `source`, `version`, правила с `id`,
    `level` (`must` / `should` / `may`), областью и текстом. Сейчас пакет
    один — «продукт», собирается из библиотеки и образцов. Стандарты станут
    вторым пакетом, без переделки движка;
  - **у каждой находки с первого дня** есть `source` и `level`. Группа «На
    будущее: стандарты ДС» — это просто фильтр `source = ds-standard`;
  - **режим стандартов — в профиле продукта:** `off` → `reference`
    (видно, не влияет на статус) → `enforced` (влияет, `must` = блокер, как
    в `audit-gate`). Когда Driver приведут к стандарту, переключается одна
    настройка в его профиле, а не плагин;
  - **пакет стандартов — файл,** который импортируется в плагин (или
    собирается из `skills/_shared/standards/*.json`). В отчёт пишется версия
    пакета — по `standards-registry.json`, чтобы было видно, по какой
    редакции стандартов шла проверка;
  - **контрактный тест:** движок работает с тестовым пакетом, которого нет
    в коде, — значит, подключение нового пакета не требует правки движка.

- **Предложения в библиотеку** — с обоснованием, почему существующий
  токен или компонент не подошёл, и с именем по `naming-conventions`.

## Страница предложений

Сейчас — отдельная страница в том же файле, похоже на печать таблицы в
Token Comparator.

- Группы: новый токен · изменить токен · новый компонент · новый вариант
  или свойство · нужен тёмный ассет.
- В строке: пример (кусок макета), сколько раз встречается, ссылка на
  экран, причина, кандидаты.
- Повторный запуск обновляет свою страницу (опознаётся по `pluginData`), а
  не плодит новые.
- Оформление страницы — токенами целевого продукта там, где роль найдена в
  индексе: страница сама переключается Day / Night и не нарушает
  `no-hardcode-color-protocol`. Таблица Token Comparator красит
  захардкоженными цветами — это не копируем.
