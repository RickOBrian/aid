## Разбор наработок Figma Agent

Источник: скилл wb-aid-core / wb-aid-rules / wb-aid-steps и три документа к
нему (Guide, Risks, Recommendations). Статус — референс уровня junior:
направление верное, реализация и часть фактов — нет.

### Что берём

- Работа на копиях, оригиналы не трогаются.
- Последовательность «инвентарь → маппинг → валидация → замена → проверка →
  отчёт».
- Поиск ручных фреймов, которые должны быть компонентами (шаг 02b), и
  признак «фрейм с заливкой + вложенные инстансы = кандидат в составной
  компонент» (правило 32).
- Пробелы библиотеки фиксируются и превращаются в предложения (правила 13,
  17, 26).
- Правила 1–32 — как список регрессий, которые Verifier должен ловить
  автоматически.
- Пары «было / стало» на одной странице. Для нас это не избыточность, а
  требование ревью (решение №4, №6).

### Что не берём и почему

1. **Визуальное совпадение как условие замены** (правила 19, 27, 31). При
   смене стиля размеры, радиусы и цвета *должны* меняться, и проверка
   заблокирует каждую правильную замену. Разделяем: *эквивалентность
   назначения* (роль, оси, свойства, слоты) и *регрессия вёрстки*
   (геометрия: сдвиги, обрезанный текст, выход за родителя).
2. **Маппинг по ключам old → new.** Наш исходный файл не тянет ни одну
   библиотеку — ключей-пар нет. Нужна классификация по роли и значению:
   цвет заливки текста ≠ цвет фона при одинаковом HEX. Правило «не маппить
   только по HEX» верное, но для нас это ядро, а не примечание.
3. **Маппинг на уровне сета.** Нужен уровень варианта и свойств: оси и
   значения, TEXT / BOOLEAN / INSTANCE_SWAP. Правила 1, 2, 9, 12, 15 —
   симптомы отсутствия маппинга свойств.
4. **Checkpoint в `pluginData`** — хранит метаданные без оверрайдов, откатить
   по нему нельзя. Вместо него — журнал операций с откатом по ноде.
5. **Батчи по 5 и Gate Check** — ограничение контекста агента. В плагине —
   dry run по всей области, ревью, затем применение.
6. **`safeTraverse` с `maxDepth`** — глотает ошибки, молча режет глубину,
   медленный. Вместо него — `findAllWithCriteria`,
   `skipInvisibleInstanceChildren`, `getMainComponentAsync`.
7. **Таблица отчёта на канвасе с HEX и Google Sans** — нарушает
   `no-hardcode-color-protocol`. Ревью живёт в интерфейсе плагина, экспорт —
   файлом; на канвасе — только пары «было / стало» с метками.

### Качество документов

- Заявлено 32 правила — фактически 31 (нет 23); в гайде упомянуто «28».
- Дубли: 19 = 25; 1 ≈ 2 ≈ 9; 6 ≈ 7 ≈ 12.
- Противоречие: 5 (не перекрашивать инстанс) vs 12 (восстановить цвет) vs
  17 (не делать молчаливых оверрайдов).
- «95%+ покрытия» ничем не подтверждено.

## Продукт — это данные, а не код

Движок не знает ни одного продукта по имени. Всё продуктовое — в
**профиле продукта**:

- id и название;
- библиотеки: компоненты, иконки, токены (file key; доступ по REST или
  индексацией открытого файла);
- файлы-образцы;
- **тема**: какая коллекция отвечает за тему и какой её режим — светлый,
  какой — тёмный, какие ещё есть. Имена режимов у продуктов разные: у
  Driver это `Day` / `Night` (`products/driver/product.json`,
  `colorModeMapping`), поэтому `Light` / `Dark` в коде не хардкодим;
- подсказки ролей, выученные из образцов (какой токен для какой роли).

Новый продукт = новый профиль, созданный в плагине мастером, без правки
кода. Профиль экспортируется и импортируется JSON (решение №9). Позже
профиль можно заполнять из `products/<id>/product.json` — это связь с
репозиторием, отдельное решение.

**Страховка.** Тест в CI: в `src/` нет имён продуктов (`driver`, `rider` и
т. д.). Появилось — значит, продуктовое протекло в движок.

## Тёмная тема

### Как показываем

Страница миграции — строка на экран, колонка на режим темы продукта:

```
Было · Day  │ [Было · Night] │ Стало · Day │ Стало · Night │ [ещё режимы]
```

- «Было · Night» есть, только если в исходнике нашлась тёмная пара экрана.
- «Стало · Night» — **производная** от «Стало · Day»: копия с явным режимом
  темы на корневом фрейме (`setExplicitVariableModeForCollection`). Она
  пересоздаётся после каждого применения и руками не правится — иначе две
  колонки разъедутся.
- Режимов у продукта больше двух — колонок больше. Тёмного режима нет —
  колонка одна и заметка в ревью.

Тёмная тема получается «бесплатно» ровно настолько, насколько «Стало»
привязано к семантическим токенам. Поэтому проверка тёмной темы — это в
первую очередь проверка полноты привязки.

### Три сценария исходника

**А. Тёмной темы нет.** Переводим светлый макет; «Стало · Night»
генерируется. Всё, что не привязалось к токену, в Night остаётся светлым —
это находка, а не мелочь.

**Б. Тёмная тема отдельными макетами.** Ищем пары «светлый — тёмный»: имя
(`dark`, `night`, `тёмн`, `ночь`…), одинаковая структура дерева,
инвертированная яркость фона корня. Пару **сводим в один «Стало»** с двумя
колонками режима, а не переводим два макета отдельно. Тёмный исходник
работает дважды:

1. **как улика для выбора токена** — у ноды есть пара значений (светлое,
   тёмное), и токен должен совпасть с обоими в своих режимах. Это
   различает токены с одинаковым светлым значением намного надёжнее, чем
   один HEX;
2. **как эталон для ревью** — «Было · Night» против «Стало · Night».

Пары, которые не нашлись автоматически, пользователь сводит руками или
переводит тёмный макет как самостоятельный (токены подбираются по
значениям в тёмном режиме).

**В. Тёмная тема есть, но токены применены неправильно.** Чужим привязкам
не доверяем: они — улика, а не ответ. Берём разрешённые значения ноды в
обоих режимах и подбираем токен продукта по роли и паре значений. Светлая
и тёмная улики противоречат друг другу — «спорно», с обоими кандидатами.
Явные режимы, выставленные в исходнике на фреймах и инстансах, в «Стало»
снимаются и попадают в отчёт.

### Риски и проверки

| Риск | Как ловим | Что в ревью |
|---|---|---|
| Цвет не привязан к токену (сырой HEX, пропущенная нода, оверрайд внутри инстанса) | Любая заливка, обводка, эффект в «Стало» без привязки к переменной | Блокер: «в Night останется светлым» |
| Привязан примитив (Core) вместо семантики | Переменная разрешается одинаково во всех режимах, а роль ноды — тематическая | Спорно: подобрать семантический токен |
| Токен не той роли (текстовый на фоне и т. п.) | Контраст текста к ближайшему фону в **каждом** режиме (WCAG 4.5 / 3) | Спорно или блокер по порогу |
| Растровые картинки и иллюстрации с запечённым светлым фоном, логотипы | Image fill, векторы с множеством сырых цветов | Предложение: нужен тёмный ассет |
| Тени и эффекты | Эффекты без стиля/переменной | Спорно: эффект продукта |
| Прозрачность слоя поверх цветных заливок | `opacity < 1` у ноды с заливкой | Предупреждение — в Night выглядит иначе |
| Явный режим, навязанный в исходнике | `explicitVariableModes` на нодах исходника | Снят в «Стало», в отчёт |
| Имена режимов разные у продуктов | Профиль продукта, не код | — |

## Страница предложений

Сейчас — отдельная страница в том же файле, похоже на печать таблицы в
Token Comparator.

- Группы: новый токен · изменить токен · новый компонент · новый вариант
  или свойство · нужен тёмный ассет.
- В строке: пример (кусок макета), сколько раз встречается, ссылка на
  экран, причина, кандидаты.
- Повторный запуск обновляет свою страницу (опознаётся по `pluginData`), а
  не плодит новые.
- Оформление страницы — токенами целевого продукта там, где роль найдена в
  индексе: страница сама переключается Day / Night и не нарушает
  `no-hardcode-color-protocol`. Таблица Token Comparator красит
  захардкоженными цветами — это не копируем.
