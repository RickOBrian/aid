| 12 | Общий код | Копируем нужное к себе; общий пакет — после готовности обоих плагинов |
| 13 | Интерфейс | Стиль и компактность Token Comparator |

**Почему без сервера (№10).** Все этапы до ревью включительно работают
внутри Figma: чтение библиотек — напрямую из плагина через REST API, профиль
и индекс — в `clientStorage`, предложения в библиотеку — экспорт файлом.
Сервер понадобится только для общего реестра профилей или отправки
предложений на согласование; тогда он заводится как новый контур по
правилам корневого `CLAUDE.md`.

## Разбор наработок Figma Agent

Источник: скилл wb-aid-core / wb-aid-rules / wb-aid-steps и три документа к
нему (Guide, Risks, Recommendations). Статус — референс уровня junior:
направление верное, реализация и часть фактов — нет.

### Что берём

- Работа на копиях, оригиналы не трогаются.
- Последовательность «инвентарь → маппинг → валидация → замена → проверка →
  отчёт».
- Поиск ручных фреймов, которые должны быть компонентами (шаг 02b), и
  признак «фрейм с заливкой + вложенные инстансы = кандидат в составной
  компонент» (правило 32).
- Пробелы библиотеки фиксируются и превращаются в предложения (правила 13,
  17, 26).
- Правила 1–32 — как список регрессий, которые Verifier должен ловить
  автоматически.
- Пары «было / стало» на одной странице. Для нас это не избыточность, а
  требование ревью (решение №4, №6).

### Что не берём и почему

1. **Визуальное совпадение как условие замены** (правила 19, 27, 31). При
   смене стиля размеры, радиусы и цвета *должны* меняться, и проверка
   заблокирует каждую правильную замену. Разделяем: *эквивалентность
   назначения* (роль, оси, свойства, слоты) и *регрессия вёрстки*
   (геометрия: сдвиги, обрезанный текст, выход за родителя).
2. **Маппинг по ключам old → new.** Наш исходный файл не тянет ни одну
   библиотеку — ключей-пар нет. Нужна классификация по роли и значению:
   цвет заливки текста ≠ цвет фона при одинаковом HEX. Правило «не маппить
   только по HEX» верное, но для нас это ядро, а не примечание.
3. **Маппинг на уровне сета.** Нужен уровень варианта и свойств: оси и
   значения, TEXT / BOOLEAN / INSTANCE_SWAP. Правила 1, 2, 9, 12, 15 —
   симптомы отсутствия маппинга свойств.
4. **Checkpoint в `pluginData`** — хранит метаданные без оверрайдов, откатить
   по нему нельзя. Вместо него — журнал операций с откатом по ноде.
5. **Батчи по 5 и Gate Check** — ограничение контекста агента. В плагине —
   dry run по всей области, ревью, затем применение.
6. **`safeTraverse` с `maxDepth`** — глотает ошибки, молча режет глубину,
   медленный. Вместо него — `findAllWithCriteria`,
   `skipInvisibleInstanceChildren`, `getMainComponentAsync`.
7. **Таблица отчёта на канвасе с HEX и Google Sans** — нарушает
   `no-hardcode-color-protocol`. Ревью живёт в интерфейсе плагина, экспорт —
   файлом; на канвасе — только пары «было / стало» с метками.

### Качество документов

- Заявлено 32 правила — фактически 31 (нет 23); в гайде упомянуто «28».
- Дубли: 19 = 25; 1 ≈ 2 ≈ 9; 6 ≈ 7 ≈ 12.
- Противоречие: 5 (не перекрашивать инстанс) vs 12 (восстановить цвет) vs
  17 (не делать молчаливых оверрайдов).
- «95%+ покрытия» ничем не подтверждено.

### Факты API — проверить на этапе 0

| Утверждение наработок | Наше ожидание |
|---|---|
| Виртуальные инстансы бросают исключения | Бросает синхронный `mainComponent` при `documentAccess: dynamic-page`; нужен `getMainComponentAsync()` |
| `pluginData` ~1 МБ на ноду | В заметках Token Comparator — 100 kB |
| `pluginData` теряется при дублировании | Копируется вместе с нодой — клоны унаследуют служебные данные |
| `swapComponent` не сохраняет вложенные instance swap | По документации сохраняет по логике интерфейса Figma |
| «Загрузить GLOSSARY библиотеки» | Plugin API не перечисляет компоненты библиотеки; только REST или индексация открытого файла |

## План

Каждый этап — отдельная ветка и PR; этап закрыт, когда проверен в живой
Figma на реальном файле.

| Этап | Что | Готово, когда | Статус |
|---|---|---|---|
| 0 | Каркас плагина (manifest, сборка, typecheck, тесты, UI в стиле Token Comparator). Спайк: факты API из таблицы выше, скорость дублирования и импорта на реальном файле | Плагин открывается в Figma, факты записаны сюда | todo |
| 1 | **Сборка.** Выбор области (выделение / страницы с чекбоксами), поиск экранов, дублирование на страницу миграции, раскладка парами «было → стало», ссылка на исходник | Разбросанные макеты собраны ровной сеткой, оригиналы не тронуты | todo |
| 2 | **Индекс образцов.** Выбор библиотек и файлов-образцов (REST и открытый файл). Индекс: переменные с режимами, стили, компоненты со схемой свойств. Из файлов-образцов — какие токены и компоненты используются для каких ролей | Индекс строится и кэшируется, виден в плагине | todo |
| 3 | **Токены.** Сырые значения и чужие стили/переменные → токены продукта с учётом роли (текст, фон, обводка, отступ, радиус, типографика), уверенность, dry run, применение, журнал с откатом | Экран переведён на токены, спорное помечено | todo |
| 4 | **Компоненты.** Чужие инстансы, локальные компоненты и ручные фреймы → компоненты продукта: маппинг вариантов и свойств, составные кандидаты | Экран переведён на компоненты без изменения структуры | todo |
| 5 | **Ревью и предложения.** «Было → стало» в плагине и на канвасе: хорошо / спорно / предложение; текстовый отчёт; экспорт предложений в библиотеку и профиля маппинга | Выполнен критерий готовности из `../CLAUDE.md` | todo |
| 6 | **Обвязка.** Задача в CI (через Principal Designer), релиз `style-migration-vX.Y.Z` без Latest, кнопка в Presentbook — через чат Presentbook | Первый релиз у дизайнеров | todo |

Порядок 3 → 4 не догма: если спайк покажет, что компоненты тянут за собой
большую часть токенов, поменяем местами.

## Открытые вопросы

- **Режимы.** В целевой библиотеке есть светлый и тёмный режимы, а
  исходные макеты, скорее всего, в одном. Какой режим выставлять странице
  миграции — определять по образцам или спрашивать?
- **Один продукт за запуск?** Предполагаю: одна миграция — один целевой
  продукт; сравнить Driver и Rider — это два запуска.
- **Куда уходят предложения в библиотеку** после экспорта — в чат
  стандартов, в реестр Token Comparator или новый процесс? До этапа 5
  достаточно файла.
