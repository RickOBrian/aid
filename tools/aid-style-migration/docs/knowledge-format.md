# Формат знания о продукте — черновик v0

Статус: **черновик**, 2026-10-01. Ждёт проверки Principal Designer (PD). После
его «да» формат согласуем с чатом Presentbook (D-6). До этого Presentbook
формат не получает.

Один формат для всех эталонных продуктов. Данные лежат в
`products/<id>/knowledge/`. Читают их два потребителя: Presentbook
показывает знание людям, плагин применяет его к макетам (D-1, D-6).

Пробное заполнение для Driver:

| Что | Файл |
|---|---|
| паттерн «Предложение заказа» | `products/driver/knowledge/patterns/order-offer.json` |
| паттерн «Активный заказ» | `products/driver/knowledge/patterns/active-order.json` |
| компонент `slider` | `products/driver/knowledge/components/Buttons.slider.json` |
| компонент `small` (бейдж) | `products/driver/knowledge/components/Badges.small.json` |
| компонент `Right` (сообщение чата) | `products/driver/knowledge/components/Chat.Right.json` |
| находки разборов 01–03 | `products/driver/knowledge/findings/01.json`, `02.json`, `03.json` |

Проверка ссылок и словарей: `node tools/aid-style-migration/scripts/knowledge/check.cjs driver`.

## 1. Общие правила

- **JSON.** Значения из словарей пишутся латиницей, чтобы их одинаково читали
  код и Presentbook. Текст для людей пишется по-русски. Русские подписи для
  словарных значений даны в §6.
- В каждом файле есть поле `format: "aid-knowledge/0"`. Если меняется
  контракт, меняется и номер.
- **Ссылка на компонент** имеет вид `"<страница библиотеки>/<имя набора>"`,
  например `Buttons/slider`, `Badges/small`, `Chat/Right`. Имена наборов в
  библиотеке не уникальны: `small` есть и в Badges, и в Headers. А ключи
  компонентов не совпадают со старыми копиями библиотеки (M2.8).
  Поэтому ссылка — по странице и имени набора.
- **Уверенность** (`confidence`) есть у каждого утверждения, которое не
  очевидно:
  - `reference` (эталон) — так в библиотеке, в стандарте или по решению PD;
  - `inferred` (вывод) — объясняет все найденные случаи;
  - `verify` (проверить) — гипотеза.

  Вывод становится правилом только после «да» PD. Тогда он получает
  `decision` и переходит в `reference`.
- **Основание** (`basis`) — откуда известно: `library`, `standard`,
  `review`, `decision` и ссылка (`ref`).
- **Решение** (`decision`) — `{ by, date, ref, text }`. Здесь `ref` — номер
  записи в `decisions.md` (D-n) или ответ в разборе (П1, В3…).
- Неизвестное не придумываем: оставляем `null` и пишем, что проверить.

## 2. Пять уровней знания и где каждый лежит

| Уровень | `level` | Где в данных |
|---|---|---|
| 1 Паттерн | `pattern` | `patterns/*.json` |
| 2 Выбор компонента | `component` | `components/*.json` → `purpose`, `parts`, `notThis` |
| 3 Вариант и состояние | `variant` | `components/*.json` → `variants`, `states` |
| 4 Содержимое | `content` | `components/*.json` → `content`; в паттерне — `blocks[].content` |
| 5 Оформление | `style` | `components/*.json` → `style` (часть → токен по вариантам, правило) |

Уровни 2–5 одного компонента хранятся в одной записи. Дизайнер читает
компонент целиком, а находки ссылаются на уровень через поле `level`.

## 3. Паттерн

```jsonc
{
  "format": "aid-knowledge/0", "kind": "pattern",
  "id": "order-offer",
  "name": "Предложение заказа",
  "purpose": "зачем экран: какое решение принимает пользователь",
  "confidence": "inferred",
  "evidence": [ { "file": "…", "node": "4102:3276", "name": "Order offer / Basic", "review": "01" } ],
  "layers": [            // снизу вверх (R8)
    { "order": 1, "role": "карта", "contains": ["…"], "required": null, "confidence": "inferred" }
  ],
  "container": {         // шторка (R10)
    "role": "…", "component": null, "source": "should-be-component", "scroll": false,
    "blocks": [ { "order": 1, "role": "…", "component": "Rows/time-distance", "required": null, "content": "…" } ]
  },
  "primaryAction": { "placement": "in-container-last | pinned-over-container", "component": "Buttons/full" },
  "distinguishedFrom": [ { "pattern": "active-order", "by": "чем отличается (R9)" } ],
  "notErrors": [ "что выглядит как ошибка, но нормально для паттерна (бар под шторкой)" ],
  "findings": [ "F01-03" ]
}
```

В поле `required` стоит `null`, пока у паттерна один экран: по одному
экрану не понять, какой блок обязателен.

## 4. Компонент (уровни 2–5)

```jsonc
{
  "format": "aid-knowledge/0", "kind": "component",
  "id": "Buttons/slider",
  "library": { "file": "o0IUYIS7vadbmXPXd81ql9", "page": "Buttons", "set": "slider", "node": "89:6142" },
  "purpose": { "interaction": "action", "meaning": "смысл — роль взаимодействия, не содержимое (M2.1a)" },
  "notThis": [ { "looksLike": "…", "is": "другой компонент", "why": "другая роль или структура" } ],
  "parts": [ { "path": "button/content/На месте", "slot": "label", "optional": false } ],
  "variants": [ { "props": { "Active": "True" }, "meaning": "…", "confidence": "reference" } ],
  "states": {
    "library": [ "default", "disabled" ],     // имена состояний по стандарту
    "missing": [ { "name": "…", "finding": "F03-01", "decision": { … } } ]
  },
  "content": [ { "rule": "…", "confidence": "…" } ],
  "style": [ { "part": "…", "layer": "text|fill|stroke", "tokens": { "Active=True": "Texts/Primary Light Ind" }, "rule": "R1", "confidence": "reference" } ],
  "usedIn": [ "active-order" ],
  "deviations": [ { "finding": "F02-12", "summary": "частое отступление в макетах" } ]
}
```

- `interaction`: `action` (действие), `input` (ввод), `display`
  (отображение), `container` (вмещает другие компоненты). Значение
  `container` — моё предложение, см. вопрос Ф4.
- `slot` — имя слота по стандарту (`component-architecture.json`):
  leading, content, trailing, badge, header, footer, title, subtitle,
  action. Если слот нельзя назвать, ставим `null`. Необязательная часть
  получает `optional: true` (M2.2).
- В `style` значение токена задаётся по вариантам. Если токен одинаков во
  всех вариантах, ключ `"*"`. Данные — из `components/*.anatomy.txt`.

## 4а. Правило продукта (`rules.json`)

Правила продукта лежат в одном реестре. Компоненты, паттерны и находки
ссылаются на них по номеру (`R1`…). Правила метода разбора — это не
знание о продукте, они в `tools/aid-style-migration/docs/method.md`
(`M…`, `MR…`).

```jsonc
{ "id": "R1", "level": "style", "text": "…", "table": [ … ],
  "standard": { "ref": "semantic-color-tokens.json §7, §9", "relation": "matches", "note": "…" },
  "confidence": "inferred", "basis": [ … ], "decision": null,
  "author": "кто научил: Principal Designer / инженер / Claude (вывод)" }
```

Поле `standard.relation` показывает, как правило продукта относится к
стандарту ДС:
- `matches` — совпадает;
- `deviates` — отступает (это находка, а не ошибка, MR6);
- `product-only` — в стандарте такого нет;
- `unknown` — не сверено.

Стандарт — общий эталон, к которому продукт стремится. Продукт — не
стандарт.

## 5. Находка ревью

```jsonc
{
  "id": "F02-12",
  "review": "02",
  "screen": { "file": "TLVVI8O6J0FGUcHzxxLq8H", "node": "4102:4467", "name": "Order Page / Full info" },
  "marker": "⑭",
  "fragment": { "node": null, "board": "6781:22262" },   // узел элемента; доска с визуалом
  "element": {
    "purpose": "подтвердить прибытие смахиванием",
    "interaction": "action",
    "source": "library",                 // А/Б/В/Г/отвязан
    "component": "Buttons/slider",
    "variant": { "Active": "True" }
  },
  "level": "style",
  "kind": "designer-error",
  "addressee": "author",               // обязательное поле (D-14)
  "what": "что не так — одним предложением",
  "expected": "как правильно",
  "rule": [ "R1" ],                    // правило продукта (rules.json) или метода (method.md: M…, MR…)
  "confidence": "reference",
  "status": "open",
  "decision": null,
  "proposal": null,                    // для владельца AID: что изменить в библиотеке
  "sameAs": null,                      // та же находка, уже записанная в другом разборе
  "related": [],                       // связанные находки (например, вопрос автору + решение владельца)
  "priority": "normal"                 // low — контекст под затемнением и т. п.
}
```

В файле `findings/<разбор>.json` поля `screen`, `boards` (доски с
визуалом) и `pattern` задаются один раз на весь разбор. У находки уровня
файла стоит `scope: "file"`, а `element` равен `null`.

Порядок полей повторяет порядок разбора: назначение → источник →
компонент и вариант → уровень → вид и адресат.

**Одна находка — один адресат.** Если вопрос есть и к автору, и к
владельцу AID (красная мотивация в 01: автору — «зачем», владельцу —
«пока добавить красный стиль»), это **две находки**, связанные через
`related`.

**Адресат по умолчанию** вытекает из вида находки. Поле всё равно
заполняется явно:

| `kind` | Вид | Адресат по умолчанию |
|---|---|---|
| `designer-error` | ошибка дизайнера | `author` |
| `author-question` | вопрос автору | `author` |
| `build-debris` | мусор сборки | `author` |
| `library-gap` | пробел библиотеки | `aid-owner` |
| `component-architecture` | архитектура компонента | `aid-owner` |
| `library-error` | ошибка библиотеки — **кандидат**, см. Ф1 | `aid-owner` |
| `library-source` | файл собран на копии библиотеки — **кандидат**, см. Ф2 | `aid-owner` |

**Статус** (`status`):
- `open` — ждёт ответа;
- `answered` — есть решение;
- `deferred` — отложено;
- `ask-only` — задать автору, решение не нужно (MR3).

**Не находка — компенсация.** Если дизайнер вручную ставит токен, который в
текущей библиотеке уже стоит (файл на старой копии), это не находка (M5.2). Такие случаи идут числом в сводку экрана, а не отдельными записями.

## 6. Словари и русские подписи

| Поле | Значение | Подпись |
|---|---|---|
| `confidence` | reference / inferred / verify | эталон / вывод / проверить |
| `source` | library | А — компонент библиотеки |
| | local | Б — компонент создан в файле или другом файле |
| | should-be-component | В — не компонент, но должен быть |
| | wrong-architecture | Г — компонент, но архитектурно неверный |
| | detached | отвязан — связь с компонентом разорвана (сигнал пробела, M2.4) |
| | none | не компонент и не должен им быть (линия маршрута, затемнение) |
| `level` | pattern / component / variant / content / style | паттерн / выбор компонента / вариант и состояние / содержимое / оформление |
| `addressee` | aid-owner / author | владелец AID / автор макета |
| `interaction` | action / input / display / container | действие / ввод / отображение / контейнер |

Источник `none` — тоже моё предложение. Без него линию маршрута (R11)
и затемнение не к чему отнести.

## 7. Проверка: отвечает ли формат на вопросы разборов

Каждый вопрос трёх разборов я разложила в поля формата. Ниже показано,
куда попал вопрос и что получилось.

| Вопрос | Куда ложится | Итог |
|---|---|---|
| 01 · источник компонентов (старая копия) | находка уровня файла | **не ложится**: экрана и элемента нет, ни один вид не подходит → Ф2 |
| 01 · бар под шторкой | паттерн → `notErrors` | ложится |
| 01 В1 шторка — компонент? | находка, `source: should-be-component`; паттерн → `container` | ложится |
| 01 В2 точка ≠ `adresses/offer` | компонент → `notThis` | ложится |
| 01 В3 тариф + опции | находка `library-gap`, `proposal`; компонент → `parts[].optional` | ложится |
| 01 В4 `address` Order/Offer | находка `component-architecture`, `source: wrong-architecture` | ложится |
| 01 В5 красная мотивация | две находки: `author-question` + `library-gap`, `related` | ложится через правило «один адресат» |
| 01 В6 спрятанная рамка | `author-question`, `status: deferred` | ложится |
| 01 · шеврон `Dark Ind` | `designer-error`, `rule: R1` | ложится |
| 01 · `bar/button` Main `Inverted` в библиотеке | ошибка в самой библиотеке | **не ложится** ни в пробел, ни в архитектуру → Ф1 |
| 02 П1 объекты карты | находка автору + находка владельцу; `source: none` для линии | ложится; нужен `none` |
| 02 П2 кнопка чата кругом | `designer-error` + `library-gap` (Counter в `fab`) | ложится |
| 02 П3 отвязанные инстансы | `source: detached`, `library-gap`, `proposal` | ложится |
| 02 П4 чип подъезда | `author-question`, `status: ask-only` | ложится |
| 02 П5 два стиля комментария | компонент → `variants` (два стиля одного компонента) | ложится; какой случай какой — `verify` |
| 02 А1 время спрятано перекраской | `designer-error`, `level: content` | ложится |
| 02 · чужой токен, распорки, `Inverted` на слайдере | `designer-error`, `level: style` | ложится |
| 02 · тариф вручную (повтор 01) | `sameAs: F01-07` | ложится |
| 03 П1 ошибка отправки | компонент → `states.missing`, `library-gap` | ложится, но есть вопрос к стандарту → Ф3 |
| 03 П2 быстрые ответы | `library-gap` (вариант `default`) | ложится |
| 03 П3 слот в шапке | `library-gap`, компонент → `parts` (слот `action`) | ложится |
| 03 П4 поле сообщения | `library-gap` (вариант поля) | ложится |
| 03 А1 вторая шторка | `build-debris` | ложится |
| 03 А2 две ручки | `build-debris` | ложится |
| 03 · контекст под затемнением | `priority: low` | ложится |

Итог: из 26 вопросов 23 ложатся (один из них — с вопросом к стандарту,
Ф3), 1 ложится частично (Ф5), 2 не ложатся без нового вида (Ф1, Ф2). По
ходу заполнения я добавила `container` и `none` (Ф4).

Пробное заполнение: 2 паттерна, 3 компонента, 33 находки. По адресату:
владельцу AID — 14, автору — 19. По виду: ошибка дизайнера — 13, пробел
библиотеки — 11, вопрос автору — 4, мусор сборки — 2, по одной —
архитектура компонента, ошибка библиотеки и источник файла.

## 8. Вопросы PD по формату

- **Ф1 · Ошибка библиотеки — отдельный вид?** `bar/button` `Type=Main`
  (тёмная плашка, текст `Inverted`, ночью не читается) — это не пробел
  (компонент есть) и не архитектура (состав верный). Ошибка в токене.
  Предлагаю шестой вид `library-error`.
- **Ф2 · Находка уровня файла.** «Весь файл собран на старой копии
  библиотеки» — у такой находки нет экрана и элемента. Предлагаю вид
  `library-source` и необязательные `screen` и `element` для находок уровня
  файла.
- **Ф3 · Ошибка отправки — состояние или значение?** В стандарте
  (`component-states.json`, ADR-021) состояние — режим взаимодействия, а
  данные компонента — значение. Состояние `error` разрешено только
  контролам форм. Статус доставки («отправлено / печатает / не
  отправлено») — это данные сообщения. В библиотеке у `Left` в свойстве
  `State` уже лежат значения `Sent` и `Printing`, у `Right` — только
  `Default`. Ваше решение «отдельное состояние» я понимаю так: в свойство
  `State` у `Right` добавить значение «не отправлено» рядом с `Sent`. В
  знании о продукте я бы записала это как **значение статуса доставки**, а
  не состояние `error`. Так Driver не разойдётся со стандартом. Согласны?
- **Ф4 · `container` и `none`.** Шторке не подходит ни действие, ни ввод,
  ни отображение. Линия маршрута и затемнение — не компоненты и не должны
  ими быть. Добавляем эти два значения?
- **Ф5 · Узлы фрагментов.** Сейчас находка указывает на элемент только
  маркером. Предлагаю при следующем разборе записывать `fragment.node`
  сразу: скрипт доски его знает. Старые разборы дозаполнить по запросу.
