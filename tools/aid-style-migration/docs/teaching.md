# Как учить модель — для инженеров программы AID

Модель (Claude) между сессиями ничего не помнит. Всё, чему её научили,
живёт только в репозитории. Урок, не записанный в репозиторий, потерян.
Учить может любой инженер из `tools/aid-style-migration/teachers.json`,
с любого аккаунта, в своей ветке и своём worktree.

## Как начать сессию

Открывать Claude Code в папке `tools/aid-style-migration` своего worktree
(не в корне репозитория и не в другой папке). Тогда модель сама загрузит
`tools/aid-style-migration/CLAUDE.md` с разделом «Программа AID — читать
первым»: прочитает состояние, решения, метод, свои прошлые ошибки и
покажет очередь главного инженера. Особая команда не нужна.

## Кто что решает

- **Главный инженер** (Principal Designer):
  - утверждает правила продукта и любые изменения метода;
  - решает споры;
  - добавляет инженеров в список.
- **Инженер** (вайбкодер, не дизайнер):
  - приносит экраны и запускает разборы;
  - замечает, где модель ошиблась или ответила по-разному;
  - предлагает эталонные случаи;
  - развивает инструменты.

  Дизайнерские вопросы модель инженеру не задаёт (MR2). Урок инженера о
  дизайне остаётся предложением, пока главный инженер не скажет «да».
- **Модель** записывает свои выводы и ошибки тоже уроком, а не правкой
  канона.

## Что сказать модели

- «Запиши урок: …» — модель создаёт файл урока и ничего не меняет в
  каноне.
- «Ты ошиблась: …» — урок вида `mistake`. Модель предлагает, какая защита
  не даст ошибке повториться.
- «Это спорно с правилом R… / M…» — урок вида `dispute`, в нём обе
  позиции.
- В конце сессии: «закрой шаг» — модель проходит правило закрытия шага
  (`tools/aid-style-migration/CLAUDE.md`).

## Урок

Один урок — один файл: `tools/aid-style-migration/inbox/<дата>-<автор>-<тема>.json`.
Каждый урок лежит в отдельном файле, поэтому параллельные уроки разных
инженеров не конфликтуют при слиянии.

```jsonc
{
  "format": "aid-lesson/0",
  "id": "<имя файла без .json>",
  "date": "2026-10-01",
  "author": "<id из teachers.json>",
  "target": "method | product | standard",   // standard — только запись; само предложение уходит в очередь чата стандартов
  "product": "driver | null",
  "type": "new-rule | change-rule | mistake | case | dispute",
  "ruleRef": "R1 | M2.1 | null",               // для change-rule и dispute — обязательно
  "proposal": "что предлагается, одним абзацем",
  "basis": [ { "type": "screen | finding | standard | decision | library", "ref": "…" } ],
  "case": null,          // эталонный случай: находка в формате findings (knowledge-format.md §5)
  "mistake": null,       // { "what": "что модель сделала", "correct": "как правильно" }
  "status": "proposed | accepted | rejected | dispute",
  "positions": [],       // для dispute: [{ "author", "text", "basis" }], минимум две
  "decision": null,      // { "by": "principal", "date", "ref": "D-n", "text" } — для accepted и rejected
  "appliedIn": []        // куда урок перенесён в канон
}
```

## Жизнь урока

1. **proposed** — урок подан, канон не меняется.
2. **Автопроверка:** `node tools/aid-style-migration/scripts/knowledge/check.cjs driver`.
   Она проверяет формат, авторов, ссылки и все эталонные случаи. В конце
   печатает **очередь главного инженера** — уроки, ждущие решения.
3. **Решение главного инженера:**
   - «да» → `accepted`. Модель переносит урок в канон (`rules.json`,
     `method.md`, `mistakes.md`, `findings/`), заполняет `appliedIn`,
     решение записывает в `decisions.md`;
   - «нет» → `rejected` с причиной;
   - не согласен с правилом, но ещё не решил → `dispute`. У правила
     ставится `status: "dispute"` и ссылка на урок. Модель не применяет
     такое правило молча, а показывает обе позиции.
4. Урок остаётся в `inbox/` навсегда — это история того, кто чему научил.

## Авторство в каноне

У правила продукта есть `author` и `lessons` — уроки, из которых оно
выросло. Ошибка в журнале `mistakes.md` указывает, кто её поправил.
