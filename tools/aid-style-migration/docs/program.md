## 1. Цели

1. **Плагин переводит макеты произвольного («левого») продукта на язык
   эталонного продукта** — Driver, Rider или будущего. Не Driver → Rider:
   исходник — любой продукт, часто без системы; цель — эталонный продукт, о котором есть знание.
2. **Стандарты ДС — учебник**: по ним читаем любой продукт и предлагаем
   решения, не ломая продукт.
3. **Знание о продукте** — что известно о каждом эталонном продукте; люди его
   изучают, а инструменты применяют. Figma + Presentbook (общий для всех
   эталонных продуктов).
4. **Проверка на практике до инструментов**: сами делаем работу дизайнера
   (ревью, сборка компонента, перевод экрана) и добиваемся понимания его
   логики настолько, чтобы обучать стандартам, подсказывать и приносить
   нужное.

Из цели 1 следует **два умения**, их учим отдельно:
- **читать чужое** — опознать элемент в продукте, о котором знания нет, опираясь на
  стандарты (что это: кнопка, чип, шторка; какая роль у цвета);
- **писать на своём** — собрать это в эталонном продукте по знанию о нём.

## 2. Архитектура знания

| Слой | Что | Где | Владелец |
|---|---|---|---|
| Стандарты ДС | как должно быть в любом продукте | `skills/_shared/standards` | чат стандартов |
| Знание о продукте | как устроено в продукте и как соотносится со стандартом | данные — `products/<id>/knowledge/` (репозиторий), показ — Presentbook | знание готовит этот чат; показ — чат Presentbook |
| Свидетельства | макеты и что в них нашлось | Figma, отчёты аудита | — |

- **Figma — источник истины** для токенов, стилей, компонентов. Знание о продукте
  хранит производное знание (что значит, по какому правилу применяется) и
  выводится из источников, а не придумывается.
- **Один машинный формат знания о продукте** (JSON-схема) с двумя читателями:
  Presentbook показывает, инструменты применяют. Формат согласуем с чатом
  Presentbook с самого начала.
- **Компоненты** остаются в Figma, в Presentbook не переносятся.
  **Токены и стили** Presentbook синхронно ведёт с Figma (задача чата
  Presentbook; наш вклад — снимки, сверка, постановка).

### Уровни знания о продукте (решение 2026-09-30, пробуем)

Как думает дизайнер, сверху вниз:

1. **Паттерн** — задача экрана и типовая сборка (шторка заказа, список,
   диалог, карта с плавающими кнопками).
2. **Выбор компонента** — какой компонент библиотеки для этой задачи и
   когда нельзя рисовать вручную.
3. **Вариант и состояние** — какой вариант и какие состояния
   (component-states).
4. **Содержимое** — тексты, иконки, их роли.
5. **Оформление** — цвет по плашке (R1), типографика, отступы, радиусы,
   тени.

Знание о продукте заполняется по уровням; ошибка дизайнера и подсказка тоже
формулируются на своём уровне («здесь диалог нарисован вручную — есть
`alert`» важнее, чем «иконка перекрашена»).

## 3. Правила знания (против потери контекста и выдумок)

1. **Источник и уверенность у каждого утверждения**: `эталон` (есть в
   библиотеке, ссылка на узел) / `вывод` (объясняет все найденные случаи,
   список случаев) / `проверить` (гипотеза). `Вывод` становится правилом
   только после «да» Principal Designer.
2. **Одно состояние** — этот документ; **решения** — `decisions.md`; в
   переписке решения не живут.
3. **Проверяемость**: всё о продукте перепроверяется скриптом по Figma
   (только чтение) — `scripts/knowledge/`, `scripts/audit/`.
4. **Мелкие шаги с остановкой на ревью**; сначала план, потом выполнение.
5. **Я предлагаю на равных**: идеи, возражения, риски — не только
   исполняю.

### Учебные задания (фаза 3)

1. **Ревью макета** Driver, который Principal Designer не показывал: всё,
   что не по знанию о продукте, с уровнем, объяснением, уверенностью и предложением.
2. **Сборка компонента** по стандарту компонентов и знанию о продукте (кандидат —
   плитка «Мотивация / Рейтинг», которой нет в библиотеке).
3. **Перевод «левого» экрана** в Driver вручную с объяснением каждого
   решения — проверяет оба умения (читать чужое, писать на своём).

Где ошибаюсь — дыра в знании о продукте: закрываем правилом, только потом учим
плагин.
