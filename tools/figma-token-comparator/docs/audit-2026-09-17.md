## v1.5.0 — иконки (план)

Новая категория сканирования по заданию Principal Designer: иконки должны
быть экземплярами компонентов из иконочной библиотеки; если иконка не
оттуда — подобрать библиотечную по форме (приоритетнее) или по имени.
Выпускается в **v1.5.0**, после v1.4.0. Реализация не начата — план
зафиксирован заранее, чтобы ничего не потерять.

**Что известно.** Каталог иконок Driver — отдельный файл Figma, имена
`категория/имя` (`action/camera`), размер по умолчанию 24×24, векторный слой
внутри — «🎨 Color»; 443 экспортированных SVG лежат в
`pages/driver-color-tokens/public/icons`. REST: `/v1/files/:key/components`
и `/component_sets` — опубликованные компоненты, `/nodes?ids=…&geometry=paths`
— их геометрия. Plugin API: `getMainComponentAsync`, `fillGeometry` /
`strokeGeometry`, `absoluteTransform`, `swapComponent`. Путь Figma — только
команды M, L, Q, C, Z.

### Решения Principal Designer (2026-09-18)

| Вопрос | Решение |
|---|---|
| Как отличить иконки от прочих компонентов | Иконки — **отдельная библиотека**, выбирается в сканировании |
| Приоритет при подборе | **Форма важнее имени**; имя тоже учитывается — тай-брейк и подсказка |
| Нестандартный размер | Учитываем, **не блокируем**. Если в библиотеке есть та же иконка другого размера — это может быть и баг, и осознанное решение |
| Отвязанная иконка | Учитываем |
| Устаревшие (deprecated) | **Не делаем** — в библиотеке пока не помечаются |
| Неразличимые иконки в библиотеке | Учитываем как **«спорные варианты»** |
| Варианты в наборах компонентов | Учитываем: сначала форма, потом имя |
| Цвет при подстановке | Иконка красится в **токен, который был в макете**, а не в цвет библиотечного компонента |
| Иконка из нескольких слоёв | Определять как **одну иконку** и сравнивать целиком; подсвечивать как вероятный баг |

### Как сравнивать форму

Отпечаток формы — растр 32×32 из геометрии иконки (заливка и обводка всех
её слоёв, нормализованные в квадрат с сохранением пропорций). Похожесть —
доля совпадения масок (IoU). Растеризация — своя, чистым кодом (разбор пути,
аппроксимация кривых, заливка строками по правилу nonzero/evenodd): так она
одинаково работает в песочнице плагина, где нет canvas, и в тестах.
Отпечатки библиотеки считаются при загрузке и хранятся в данных библиотеки
(~200 байт на иконку). Цвет и размер на отпечаток не влияют.

Пороги (уточнить на шаге 0): ≥ 0.90 — «Совпала форма», 0.75–0.90 —
«Похожая форма».

### Иконка из нескольких слоёв

Иконка в макете может быть не одним шейпом, а набором (стрелка: хвостик и
указатель — разные слои). Такое сравнивается как **одна иконка**: отпечаток
строится по объединению всех слоёв.

Как находить:
- контейнер размером с иконку (фрейм / группа до ~64 px), внутри которого
  только векторы, — одна иконка, сколько бы слоёв ни было;
- векторы, лежащие вразброс без общего контейнера, — объединяются в одну
  иконку, если их общая рамка укладывается в размер иконки и они касаются
  или перекрываются.

Если иконка собрана из нескольких слоёв, а библиотечная — из одного, строка
получает пометку **«Из нескольких слоёв»** с подсказкой «скорее всего это
ошибка сборки, но бывает и намеренно». Пометка не блокирует — как
«Переопределён» у типографики.

Риск: ложные склейки соседних мелких векторов (например, две иконки
вплотную). Проверить на шаге 0 и в Figma на реальных макетах.

### Статусы

| Случай | Статус |
|---|---|
| Экземпляр компонента этой библиотеки, нормального размера | скрыт (как `exact`) |
| Экземпляр чужого или локального компонента, форма совпала | «Совпала форма» |
| Не компонент (вектор, группа векторов), форма совпала | «Иконка без компонента» + предложение |
| Точная копия библиотечной иконки, но не экземпляр | «Отвязанная иконка» — вернуть привязку одним действием |
| Имя совпало, форма заметно другая | «Конфликт» |
| Форма похожа, не совпала | «Похожая форма» |
| Ничего похожего | «Нет в библиотеке» |

Пометки рядом со статусом (не блокируют):
- **«Нестандартный размер»** — экземпляр растянут не по размеру компонента,
  либо размер не из сетки библиотеки. Если в библиотеке есть та же форма
  нужного размера — предлагается она; в подсказке — «может быть осознанно».
- **«Спорный вариант»** — у лучшего совпадения есть неразличимые по форме
  двойники в библиотеке; в подсказке перечислены все, выбор за дизайнером.
- **«Из нескольких слоёв»** — см. выше.

Из формы и имени, которые указывают на разные иконки, побеждает форма; имя
— в подсказке. Среди равных по форме (варианты одного набора, одна иконка
разных размеров) выбирается по имени и по ближайшему размеру.

### «Применить в макет» и цвет

- Экземпляр чужого компонента — `swapComponent` на библиотечный.
- **Цвет сохраняется из макета.** До подстановки читается заливка иконки
  (привязанная переменная или стиль — в первую очередь, иначе значение), после
  — применяется к цветовому слою нового экземпляра («🎨 Color»). У
  многоцветных иконок — по соответствию слоёв; если соответствие не найти,
  цвет не трогается и это пишется в итоге применения.
- **Вектор без компонента — открытый вопрос.** Варианты: (а) заменить
  экземпляром на том же месте и в том же размере — локальные правки вектора
  теряются; (б) вставить экземпляр, а исходный вектор скрыть рядом; (в) для
  таких строк применение не делать, только предложение. Решить до этапа 6.

### Этап 2 — поиск иконок в макете, 2026-09-19

`lib/iconScanner.ts` (логика, тесты без Figma) + `scanIcons(scope)` в
`lib/scanner.ts` (связь с Figma, `getMainComponentAsync`). В интерфейс ещё
не выведено — это этап 4.

- Экземпляр размером с иконку (до 64 px), внутри только векторы, — иконка;
  в него не спускаемся. В экземпляры крупнее (кнопки) спускаемся, но ищем
  там только вложенные экземпляры-иконки: остальное содержимое задано
  компонентом, а не автором макета.
- Фрейм или группа размером с иконку из одних векторов, среди которых есть
  хотя бы один настоящий вектор, — иконка без компонента. Одни
  прямоугольники и круги иконкой не считаются.
- Разбросанные векторы одного родителя, которые касаются (зазор ≤ 1 px) и
  вместе не больше 64 px, — одна иконка; число слоёв сохраняется для пометки
  «Из нескольких слоёв».
- Определение компонента-иконки в макете пропускается: находкой будут его
  экземпляры. Растянутый экземпляр помечается (`scaled`).
- Группировка: экземпляры — по ключу компонента и размеру, иконки без
  компонента — по отпечатку, размеру рисунка и прозрачностям. У группы —
  слои каждого вхождения (для выделения и «Применить в макет»).
- Геометрия из REST (`path`) и из Plugin API (`data`) дают один отпечаток —
  проверено тестом: отвязанная копия узнаётся.

### Этап 3 — сравнение с библиотекой, 2026-09-19

`lib/iconComparator.ts` — чистая логика, в интерфейс — на этапе 4.

| В макете | Похожесть с лучшей иконкой | Статус |
|---|---|---|
| экземпляр этой библиотеки, нормальный размер | — | `exact`, скрыт |
| экземпляр этой библиотеки, растянут | — | `exact` + «Нестандартный размер», цель — та же форма нужного размера, если есть |
| экземпляр чужого или локального компонента | ≥ 0.97 | `value` — «Совпала форма» |
| без компонента | ≥ 0.97 | `detached` — «Отвязанная иконка» |
| любой | 0.85–0.97 | `approximate` — «Похожая форма»; другая форма ближе 0.05 — «Спорный вариант» |
| имя совпало, форма нет | < 0.85 | `conflict`, цель — по имени |
| ничего | < 0.85 | `layout-only` |

- Среди двойников (похожесть в пределах 0.01 от лучшей) — ближе по размеру
  рисунка → совпадают прозрачности → совпало имя; не разрешилось —
  `disputed` со списком `alternatives`.
- Имя нормализуется: последний сегмент пути, без `ic_` и суффикса размера
  (`controls/close_24` → `close`); у варианта — имя набора; у слоя без
  компонента — его имя, если оно не служебное («Vector», «Group»…).
- «Из нескольких слоёв» — слоёв больше, чем у цели.
- Решения: `mapped` с `targetComponentKey` из библиотеки — «Решение
  принято», строка скрыта; «Игнорировать» скрывает, «Кандидат» — нет; цель
  решения, которой нет в библиотеке, строку не закрывает.

Тесты: `test/iconComparator.test.ts` (15); мутации — без тай-брейка по
прозрачности, порог 0.8 вместо 0.97, без «Спорного варианта» — каждая

## Как работаем

1. **Один батч — одна сессия — один коммит.** За пределы своего батча не
   выходим: замеченное попутно записываем сюда в «Замечено попутно», а не
   чиним на месте.
2. **Сначала тест, который падает,** потом правка, потом тест зелёный. Для
   известных дефектов уже стоят заглушки `it.todo` с номером находки —
   батч начинается с превращения `todo` в настоящий тест.
3. **Ворота перед коммитом:** `npm run typecheck`, `npm run build`,
   `npm test` в плагине, `npm test` в `server/`. Для UI-батчей — ещё прогон
   в браузере.

```bash
cd tools/figma-token-comparator
npm run typecheck && npm run build && npm test
cd server && npm test
```

Сделано 2026-09-18, два этапа.

Первый — аварийный: ключ отозван и заменён, бэкенд передеплоен, опубликован
релиз `v0.1.1`, ассеты `v0.1.0` удалены. Это закрыло утёкший ключ, но не
причину: новый точно так же лежал в новом архиве.

Второй — по существу: **ключ вынесен из сборки в настройки плагина**, туда же,
где уже живут токен Figma и токен GitHub. `build.js` больше не подставляет

`.env.local` нет.

Что это меняет и чего не меняет: ключ больше не читается любым, кто скачал
архив, — его знают только те, кому его выдали. Но это по-прежнему **общий**
секрет: отзыв означает смену у всех, и любой, кому его дали, может слать
запросы от чужого имени. Настоящее решение — авторизация каждого дизайнера
своей учётной записью GitHub (вариант В); оно требует OAuth-приложения и
остаётся целью, а не сделано.

Без ключа плагин работает: сканирование, сравнение, решения и экспорт
доступны. Недоступен только реестр — статус на вкладке «Настройки» и отправка
на согласование.

| № | Находка | Где | Статус |

Сделано 2026-09-18. Решение по открытому вопросу: **новое решение заменяет
старое**. Реестр хранит текущее решение по каждой подписи, история правок
остаётся в git — она видна в диффе pull request'а.

- Слияние вынесено в `mergeRegistryEntries.ts` и покрыто тестами: замена по
  подписи с сохранением места записи в файле (чтобы дифф читался как правка

- Повторная отправка уже записанного решения не заводит pull request:
  сравнение идёт по содержанию решения, без `proposedAt` / `proposedBy`.
  Бэкенд отвечает `{ success: true, unchanged: true }`, плагин показывает
  «Эти решения уже записаны в реестре» вместо «ждёт согласования».

Дозакрыто 2026-09-18: перед созданием pull request бэкенд смотрит открытые
ветки `registry/propose-*` и читает реестр на каждой. Если ровно эти решения
там уже лежат — новый PR не заводится, ответ приходит с
`reason: "already_proposed"`, и плагин пишет «уже отправлены и ждут
согласования» вместо «отправлено».

Решение с **другим** содержанием по той же подписи дубликатом не считается —
оно уезжает новым PR, иначе изменение потерялось бы. Сбой самой проверки не
блокирует отправку: если GitHub не ответил, PR создаётся. Лишний pull request
— меньшее зло, чем потерянное решение.

**Счётчик `registryVersion` остаётся неточным.** Два предложения, созданные
от одного состояния `main`, получают одинаковый номер; git сольёт обе правки
без конфликта, и номер окажется занижен. Ни одна ветка логики на нём не
завязана — он только показывается в статусной строке плагина, поэтому
оставлено как есть с комментарием в коде.

**Изменение не в проде.** Бэкенд деплоится из `main`, а правка лежит в ветке
`feat/token-comparator-typography` — она заработает после мержа.

**Находка №22, найдена 2026-09-18.** Проверено: репозиторий `RickOBrian/aid`
**публичный**, и `decisions-registry.json` читается кем угодно без всякой
авторизации:

```
raw.githubusercontent.com/RickOBrian/aid/main/decisions-registry.json → HTTP 200
```

Значит ключ на пути **чтения** не защищает ничего — он лишь мешает. Защищать
надо только отправку: там бэкенд создаёт pull request серверным токеном
GitHub.

Как должно быть:

| Что делает дизайнер | Что нужно |
|---|---|
| Сканирует, сравнивает, экспортирует, видит принятые решения | только токен Figma |
| Отправляет решения на согласование | ещё и ключ реестра |

Технически: читать реестр напрямую из репозитория, а ключ спрашивать только
для отправки.

**Решено 2026-09-18: репозиторий остаётся публичным, ключ из чтения убран.**

- `githubApi.fetchPublicRegistry` читает реестр через
  **`raw.githubusercontent.com`** без авторизации; домен добавлен в
  `networkAccess` манифеста.
- Читающий клиент бэкенда и `REGISTRY_GET_URL` удалены — у них не осталось
  вызывающих.
- Ключ спрашивается только для отправки. Поле переименовано в «Ключ для
  отправки решений», при попытке отправить без него приходит внятное
  сообщение вместо общего «не удалось».
- **Почему не `api.github.com`.** Первая версия правки читала через него, и
  это было ошибкой: у неавторизованных запросов там лимит 60 в час **на IP**,
  общий для всех за одним NAT. Поймано сразу после мержа при проверке в
  проде — `HTTP 403, x-ratelimit-remaining: 0`; квота выжигается за одну
  активную сессию, а плагин показал бы «реестр недоступен» без объяснения.
  Исправлено отдельным PR (#21): `raw` раздаётся через CDN и такого лимита не
  имеет. Цена — кэш до 5 минут, для реестра это неважно.
- `sha` у raw нет, его роль играет `ETag` — непрозрачная метка версии, по
  наличию которой отличают настоящий реестр от локального пустого.

Побочный эффект, за которым стоит следить: путь чтения теперь завязан на
публичность репозитория. Если `aid` когда-нибудь закроют, чтение сломается и
придётся возвращать бэкенд — это записано здесь, чтобы связь не потерялась.

**Находка №23, найдена 2026-09-18** при работе над превью типографики. В
манифесте `documentAccess: "dynamic-page"`, а в этом режиме
`TextNode.textStyleId` только для чтения: по документации Figma стиль
привязывается через `setTextStyleIdAsync`. `applyImportedTextStyleToNode`
присваивал свойство напрямую. Типы Figma сеттер не запрещают, поэтому
typecheck молчал, а юнит-тестов на модуль не было. В живой Figma
«Применить в макет» для типографики должен был пропускать каждый слой с
ошибкой — это следует из документации, но **в Figma не воспроизведено**:
проверка применения типографики в список сценариев аудита не входила.

Исправлено заменой на `setTextStyleIdAsync`. Для цветов та же ловушка уже
была обойдена — `setStrokeStyleIdAsync` в `handleApplyToLayout`.

Тест: `test/typographyApply.test.ts` — нода, у которой сеттер `textStyleId`
бросает, как в `dynamic-page`. Проверено: до правки тест падал.

### Батч 7 — идентификаторы (отложено)

| № | Находка | Где | Статус |

**Решение 2026-09-18: не делать, риск принят.** Обе правки меняют
`LayoutRecord.id`, то есть обнуляют все накопленные решения и подписи в
реестре — у всех сразу. Сегодняшний вред несопоставим с ценой: при сотнях и
тысячах подписей вероятность коллизии 32-битного хеша — доли процента, а
склейка одноимённых стилей из разных папок встречается редко и видна глазом
по пути слоя.

Условие пересмотра — любое из двух:

- в реестре набралось порядка **10 000** записей (тогда коллизии становятся
  ожидаемыми, а не гипотетическими);
- кто-то реально столкнулся со склейкой двух разных стилей в одну строку.

Делать тогда одной миграцией: новая схема идентификатора с версией и
таблицей соответствия старых подписей новым, иначе история потеряется.
