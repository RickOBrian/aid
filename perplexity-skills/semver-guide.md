# SemVer для дизайн-системы — v1.1.0

Единые правила версионирования артефактов дизайн-системы.
Версия — это контракт между дизайном, разработкой и QA.
Она фиксирует что именно реализуется, что тестируется и
что ожидают потребители артефакта.

---

## Артефакты с версионностью

Версионируются четыре категории артефактов. Каждый артефакт
получает собственную версию независимо от других.

| Артефакт | Примеры единиц версионирования |
|---|---|
| **Токены и стили** | Colors/Core, Colors/Semantic, Spacing/Core, Spacing/Semantic, Radius/Core, Radius/Semantic, Typography/Core, Typography/Semantic |
| **Компоненты** | ButtonText, BadgeStatus, FieldCheckbox |
| **Графика** | Icons, Pictograms, Logos, Avatars |
| **Гайды** | Архитектурный гайд, SemVer-гайд, Component Spec |

Паттерны и виджеты версионируются как компоненты — отдельной
категории не образуют. Моды отображения (Light Mode, Dark Mode,
System Mode) не являются самостоятельным артефактом: добавление
поддержки Dark Mode — это изменение версии `Colors/Semantic`.

---

## Формат версии

```
MAJOR.MINOR.PATCH
```

Все три цифры обязательны для всех артефактов, включая гайды.
Первая версия любого артефакта — `1.0.0`.

---

## Правила изменения версии

### MAJOR — breaking change

Увеличивается когда изменение ломает существующих потребителей.
Потребитель обязан обновить свой код при переходе на новый major.

Примеры:
- Удалён или переименован компонент, токен, иконка
- Изменён обязательный prop или его тип
- Удалён вариант (`variant`) или состояние (`state`)
- Изменена структура слотов (переименован `leading` → `start`)
- Токен удалён или переименован на любом уровне
- Изменена геометрия иконки, если она используется как data-атрибут

### MINOR — новая функциональность

Увеличивается когда добавляется новое без поломки существующего.
Потребитель может обновиться без изменений в своём коде.

Примеры:
- Добавлен новый опциональный prop
- Добавлен новый вариант или состояние
- Добавлена поддержка нового слота
- Добавлена новая иконка или пиктограмма
- Добавлен новый токен на любом уровне
- Токены получили поддержку Dark Mode

### PATCH — исправление

Увеличивается при исправлениях, не меняющих поведение и API.

Примеры:
- Исправлена визуальная ошибка (неправильный отступ, цвет)
- Исправлена ошибка доступности без изменения API
- Обновлена документация или комментарии в коде
- Исправлена опечатка в гайде

## Зависимости между артефактами

Изменения в одном артефакте могут обязывать обновить версию другого.

### Core → Semantic

Токены Semantic ссылаются на Core. Если Core получает breaking change
(major), Semantic того же типа обязан получить major в той же итерации.

```
Colors/Core:     v1.0.0 → v2.0.0   (MAJOR: удалён primitive-цвет)
Colors/Semantic: v1.3.0 → v2.0.0   (MAJOR: обязательно, синхронно)
```

Это правило работает для всех типов токенов:
`Spacing`, `Radius`, `Typography` и других.

### Компонент → Компонент

Если компонент A зависит от компонента B, и B получает breaking change —
A обязан получить major в той же итерации.

```
Checkbox:      v1.0.0 → v2.0.0   (MAJOR: изменён API)
FieldCheckbox: v1.2.0 → v2.0.0   (MAJOR: обязательно, синхронно)
```

Цепочку зависимостей нужно проверять при каждом major-изменении
до начала разработки.

## Версия как контракт задачи

Версия артефакта фиксируется в задаче в момент её создания
и не меняется до завершения.

**Задача создаётся на конкретную версию.** Если в процессе
работы над `ButtonText v1.0.0` появляется `ButtonText v1.1.0`
с новой функциональностью — это отдельная задача.
Текущий спринт, оценка и объём работ не пересматриваются.

**QA тестирует строго зафиксированную версию.** Тестировщик
проверяет `ButtonText v1.0.0` по спеке этой версии и не учитывает
изменения из `v1.1.0`. Появление новой версии во время тестирования
не является основанием для расширения скоупа.

**Новая версия — новая задача.** `ButtonText v1.1.0` создаётся
как отдельная задача с отдельной спекой, отдельной оценкой
и отдельным циклом QA. Она может быть взята в следующий спринт
или поставлена в очередь — независимо от статуса `v1.0.0`.

---

## Когда присваивается версия

| Момент | Действие |
|---|---|
| Дизайн-архитектор завершил спеку | Версия фиксируется в спеке и задаче |
| Разработка берёт задачу | Версия не меняется |
| В процессе появляется новая версия | Создаётся новая задача, текущая не трогается |
| QA принимает артефакт | Версия фиксируется как Released в log-файле |
| Обнаружена ошибка после релиза | Создаётся patch-версия как новая задача |

## Примеры

**BadgeStatus: добавлен новый цвет-вариант**
```
v1.0.0 → v1.1.0   (MINOR: новый вариант, старые не затронуты)
```

**ButtonText: переименован prop `type` → `variant`**
```
v1.1.0 → v2.0.0   (MAJOR: потребители обязаны обновить код)
```

**Colors/Core: исправлен неверный hex**
```
v1.2.0 → v1.2.1   (PATCH: исправление без изменения структуры)
```

**Icons: добавлены 10 новых иконок**
```
v2.0.0 → v2.1.0   (MINOR: добавление без удаления существующих)
```

**FieldCheckbox после breaking change в Checkbox**
```
Checkbox:      v1.0.0 → v2.0.0   (MAJOR)
FieldCheckbox: v1.2.0 → v2.0.0   (MAJOR, синхронно)
```

**Colors/Semantic после breaking change в Colors/Core**
```
Colors/Core:     v1.0.0 → v2.0.0   (MAJOR)
Colors/Semantic: v1.3.0 → v2.0.0   (MAJOR, синхронно)
```

## Версионирование и changelog

Каждый артефакт ведёт changelog. Минимальный формат:

```
## v1.1.0 — 2026-06-21
### Added
- Поддержка слота `leading` для иконки слева от текста

## v1.0.0 — 2026-05-10
### Added
- Первый релиз компонента
```

При major-версии в changelog явно указывается:
что сломалось и как мигрировать.
