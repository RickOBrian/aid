# Claude Skills — Полный гайд по созданию и поддержке

> **Аудитория:** дизайнеры и разработчики дизайн-системы, которые пишут скиллы
> и добавляют их в общий репозиторий.
> **Цель:** снять рутину через воспроизводимые AI-процессы, накопить знание
> команды, онбордить новых людей без ручных объяснений.

---

## Что такое скилл и зачем он нужен

Скилл — это Markdown-файл с инструкцией, который Claude читает при старте
сессии и применяет как специализированный режим работы. Не плагин, не код —
структурированный текст, который превращает экспертизу команды в
воспроизводимый процесс.

**Три критерия хорошего скилла:**

1. Снимает конкретную рутину — можно измерить в минутах
2. Накапливает знание команды — становится точнее со временем
3. Онбордит новых людей без объяснений — 5 минут от `git pull` до первого запуска

Если скилл не делает хотя бы одно из трёх — это длинный промпт, а не скилл.

---

## Как работает активация (механика, важно понять до написания)

Claude Code при запуске читает `CLAUDE.md` в корне проекта и файлы из папки
`.claude/`. Файлы из `skills/` и `skills/_shared/` **не читаются автоматически** —
скилл должен явно запросить их через инструкции вида
«Прочитай `skills/_shared/token-rules.md`».

Это ключевое: разработчик, который пишет первый скилл, должен понимать, что
Claude не «знает» содержимое репозитория по умолчанию. Знает только то, что
скилл явно просит прочитать.

**Автоматическая активация скилла** происходит по `description`-полю во frontmatter:
Claude сопоставляет запрос пользователя с триггерными фразами из description.
Чем конкретнее фразы — тем надёжнее активация.

## Bootstrap: что создать до первого скилла

Прежде чем писать первый скилл, нужно поднять инфраструктуру репозитория.
Порядок важен — скиллы ссылаются на `_shared/`, которого ещё нет.

### Шаг 1. Структура репозитория

```
.claude/
  settings.json       ← список активных скиллов и конфиг окружения
  intake-user         ← имя текущего пользователя (создаётся каждым сотрудником)

skills/
  _shared/            ← единый источник правды, создаётся первым
    token-rules.md
    platforms.md
    git-workflow.md

memory/               ← данные памяти, отдельно от логики скиллов
  .gitkeep

.gitignore
README.md
```

### Шаг 2. Создать `skills/_shared/`

Три файла, которые скиллы читают по явной инструкции:

`**token-rules.md**` — правила трёхуровневой системы токенов:
primitive → semantic → component, что допустимо на каждом уровне,
что является блокером.

`**platforms.md**` — особенности реализации на Web / iOS / Android:
соглашения по именованию API, как пробрасываются токены на каждой платформе,
минимальные touch-target требования.

`**git-workflow.md**` — единый источник git-команд для всех скиллов.
Скиллы ссылаются на него вместо того, чтобы держать команды у себя.
Содержимое файла:

```markdown
## Синхронизация памяти после каждой записи

git pull --rebase
git add memory/<skill-name>/log.<имя>.json
git commit -m "<тип>(<skill>): <что произошло>"
git push

## Типы коммитов
- memory(<skill>): запись в журнал памяти
- spec(<component>): новая спека компонента
- audit(<target>): результат аудита
- feat(skills): новый скилл
- fix(skills): правка существующего скилла

## Правило --rebase
Всегда --rebase, никогда --merge для синхронизации memory/.
Личный log-файл не конфликтует с чужими — ребейз проходит чисто.
```

### Шаг 3. Создать `.gitignore`

```
# Генерируемые сводные файлы памяти
memory/**/*.master.json

# Системный файл пользователя (каждый создаёт сам)
.claude/intake-user
```

### Шаг 4. Создать `.claude/settings.json`

`settings.json` — место для конфига окружения проекта, который Claude
читает автоматически при старте сессии. Скиллы он **не активирует** —
активация происходит через `description` во frontmatter каждого SKILL.md.

```json
{
  "project": "design-system",
  "shared_rules": "skills/_shared/",
  "memory_root": "memory/"
}
```

Добавляй сюда только то, что должно применяться глобально ко всем скиллам:
путь к `_shared/`, корень памяти, название проекта. Не веди здесь список
скиллов — он быстро устаревает и ни на что не влияет.

### Шаг 5. Создать `README.md`

Одностраничный онбординг: как клонировать, создать `intake-user`,
запустить первый скилл. Ссылка на этот гайд.

## Архитектура репозитория

```
.claude/
  settings.json
  intake-user            ← одна строка: фамилия латиницей (ivanov)

skills/
  _shared/               ← единый источник правды для всех скиллов
    token-rules.md       ← трёхуровневая система токенов
    platforms.md         ← Web / iOS / Android специфика
    git-workflow.md      ← единый гайд по git

  ds-token-audit/
    SKILL.md
    TESTING.md           ← чеклист тестирования скилла (см. Фазу 3)
    references/
      checklist.md

  ds-component-spec/
    SKILL.md
    TESTING.md
    references/

memory/                  ← отделена от скиллов
  ds-token-audit/
    log.ivanov.json
    log.petrov.json
  .gitkeep
```

**Почему `_shared/` обязателен.** Без него каждый скилл дублирует правила
токенов и платформ. При изменении системы токенов нужно обновить N файлов —
гарантированное расхождение. `_shared/` обновляется один раз, все скиллы
подхватывают при следующем запросе.

**Почему `memory/` вынесена отдельно.** Логика скилла меняется редко и
осознанно. Данные памяти растут постоянно. Разные зоны ответственности —
разные папки. Это упрощает `.gitignore` и code review.

---

## Модель памяти: один файл на человека

Любой скилл, который накапливает данные, использует эту модель:

- **Каждый пишет только в свой файл** (`log.ivanov.json`) — нет git-конфликтов
- **При анализе читаются все файлы** по маске (`log.*.json`) — общая картина
- Имя файла берётся из `.claude/intake-user`
- Генерируемые сводные файлы (`*.master.json`) — в `.gitignore`

**Синхронизация после каждой записи:**

```bash
git pull --rebase
git add memory/<skill-name>/log.<имя>.json
git commit -m "memory(<skill-name>): <что произошло>"
git push
```

`--rebase` обязателен: подтягивает чужие изменения перед своими. Личный файл
не конфликтует с чужими — ребейз проходит чисто.

## Анатомия SKILL.md

Каждый скилл состоит из шести частей в строгом порядке.

### 1. Frontmatter

```yaml
---
name: ds-token-audit
metadata:
  version: "1.0.0"
  platforms: [web, ios, android]
  owner: design-system-team
description: >
  Что делает скилл (1–2 предложения для людей).
  Активируй когда: «фраза 1», «фраза 2», «фраза 3»,
  «фраза 4», «фраза 5», передан файл такого типа.
---
```

`description` — самое важное поле. Правила:

- Первые 1–2 предложения — что делает скилл (для людей)
- Дальше — конкретные триггерные фразы (для Claude)
- Минимум 5 триггеров: реальные слова, которые скажет пользователь
- Триггеры должны быть уникальны в рамках репозитория — если два скилла
активируются на одну фразу, Claude спросит уточнение или возьмёт
первый по алфавиту. Проверяй триггеры на уникальность перед мержем.

**Версия только в frontmatter.** Заголовок `# Name — v1.0.0` и changelog
обновляются для читателя, но источник истины — `metadata.version`.
Это исключает расхождения при ручном обновлении.

### 2. Описание (первый абзац)

Одна–две фразы: что делает скилл, что на входе, что на выходе.
Пишется для человека, который открыл файл впервые.

### 3. Контекст окружения

```markdown
## Контекст окружения

Прочитай в начале каждой сессии:
- `.claude/intake-user` — кто запустил скилл
- `skills/_shared/token-rules.md` — правила токенов
- `skills/_shared/platforms.md` — особенности платформ

Если `.claude/intake-user` не существует — спроси имя одной строкой,
покажи существующие `memory/<skill>/log.*.json`, уточни
«ты новый или один из этих?», создай файл.

Если `skills/_shared/<файл>.md` не существует — предупреди
«файл _shared/<имя> не найден, работаю на встроенных правилах»
и используй встроенную копию правил из секции references/ этого скилла.
```

Этот раздел отвечает на вопрос «откуда брать контекст перед работой».
Здесь же — graceful degradation для `_shared/` файлов: если файл не найден,
скилл предупреждает и работает дальше на встроенных правилах.

### 4. Шаги процесса

Каждый шаг тестируем независимо — можно взять тестовые данные и проверить
шаг в изоляции. Шаги не должны иметь скрытых зависимостей между собой.

### 5. Шаблон вывода

```markdown
## Шаг N. Выдай результат

ALWAYS use this exact structure. Each section is mandatory.
If a section has no content, write «нет» — do not omit the section.

[Шаблон здесь — см. раздел «Как писать шаблон вывода» ниже]
```

`ALWAYS use this exact structure` — инструкция для Claude, не украшение.
Без неё формат плывёт от запуска к запуску.

### 6. Память, тон, версионирование

Стандартные секции в конце каждого скилла.

## Как писать шаблон вывода

Шаблон — это образец того, что Claude должен сгенерировать. Здесь есть
техническая тонкость, которую важно знать.

**Проблема вложенных code-блоков.** Если шаблон содержит примеры кода
(tsx, swift, kotlin), нельзя обернуть весь шаблон в один большой `````-блок:
Markdown закроет внешний блок на первом же внутреннем `````. Claude прочитает
только первую часть шаблона.

**Решение — два варианта:**

**Вариант A (предпочтительный): шаблон через 4-space indent**
Весь шаблон записывается с отступом в 4 пробела. Внутри можно свободно
использовать `````-блоки. Claude читает это как pre-formatted текст и
следует структуре точно так же.

```
ALWAYS use this exact structure:

    # [ComponentName] — Spec

    ## Назначение
    [1–2 предложения]

    ## Реализация — Web
    ```tsx
    // пример кода
    ```
```

**Вариант B: шаблон без вложенного кода**
Если примеры кода в шаблоне необязательны — описывай API текстом,
без code-блоков. Это чище, и шаблон помещается в один `````-блок.

**Когда использовать какой вариант:**

- Скилл генерирует документацию с кодом → Вариант A (4-space indent)
- Скилл генерирует отчёт, таблицы, текст → Вариант B (один code-блок)

## Graceful degradation: внешние инструменты и `_shared/`

Одинаковый паттерн для любой внешней зависимости:

```markdown
1. Проверь, доступен ли [Figma MCP / GitHub MCP / _shared/файл]
2. Если доступен — используй
3. Если нет — предупреди явно: «[инструмент] не подключён / файл не найден»
   и предложи ручной путь или используй встроенные правила
```

Никогда не падай молча. Пользователь должен знать, почему поведение изменилось.

**Типичные MCP для дизайн-системы:**


| Инструмент      | Зачем                      | Fallback                     |
| --------------- | -------------------------- | ---------------------------- |
| Figma MCP       | Токены, компоненты, фреймы | Попросить скриншот или JSON  |
| GitHub MCP      | Создать PR, проверить diff | Показать текст для копипасты |
| Jira/Linear MCP | Создать задачу             | Показать текст для копипасты |

## Оркестрация скиллов

Один скилл может быть оркестратором — читать другие и делегировать им блоки.

```markdown
## Шаг 0. Подключи зависимые скиллы

Перед работой найди и прочитай:

| Скилл              | Где искать                         | Для какого блока       |
|--------------------|------------------------------------|------------------------|
| `ds-token-audit`   | `skills/ds-token-audit/SKILL.md`   | Проверка токенов       |
| `ds-a11y-check`    | `skills/ds-a11y-check/SKILL.md`    | Проверка доступности   |

Если скилл найден — следуй его методологии.
Если нет — используй встроенные правила из `references/` этого скилла.
```

## Что выносить в `references/`

**Выноси в `references/`, если:**

- Раздел длиннее ~50 строк
- Меняется независимо от логики скилла (правила домена, конфиги инструментов)
- Используется несколькими скиллами → тогда в `_shared/`, не в `references/`

**Оставляй в SKILL.md:**

- Шаги процесса
- Шаблон вывода (`ALWAYS use this exact structure`)
- Правила активации (description)
- Правила памяти и синхронизации
- Встроенные правила как fallback для `_shared/`-файлов (кратко)

Если SKILL.md больше 250 строк — проверь, не смешаны ли логика и данные.

## Версионирование и политика обновлений

**Semver, версия только в frontmatter:**

- `patch` (1.0.X) — правка текста, уточнение формулировок
- `minor` (1.X.0) — новая секция, новое правило, новая возможность
- `major` (X.0.0) — смена структуры шаблона вывода, breaking change

**Политика при major-обновлении:**

- Старые артефакты (спеки, отчёты, журналы), созданные предыдущей версией,
остаются валидными — скилл не ломает их ретроактивно
- В changelog явно указывается: «существующие артефакты формата v1.x
читаются, но новые создаются по формату v2.0»
- Если нужна миграция старых данных — это отдельный скрипт в `scripts/`,
не часть SKILL.md

## Полный флоу: от идеи до живого скилла

### Фаза 0. Bootstrap (только для первого скилла в репо)

Если `skills/_shared/` ещё не существует — сначала создай его
(см. раздел «Bootstrap: что создать до первого скилла»).
Для второго и последующих скиллов фазу пропускать.

### Фаза 1. Проектирование (30 минут, до открытия редактора)

Ответь письменно на пять вопросов. Если не можешь ответить на первый —
скилл не нужен.

1. **Какую рутину снимает?**
  Конкретно: «ревьюер тратит 20 минут на проверку токенов вручную перед PR»
2. **Кто пользователь?**
  Дизайнер, разработчик, QA — у каждого разный нужный формат вывода
3. **Какие триггеры?**
  5+ фраз, которые реально скажет пользователь. Проверить уникальность
   относительно существующих скиллов в репо.
4. **Нужна ли память?**
  Да — если скилл учится на прошлых запусках.
   Нет — если разовая утилита (достаточно хорошего шаблона вывода).
5. **Какие внешние зависимости?**
  MCP-инструменты, `_shared/`-файлы. Для каждого — что делать при отсутствии.

### Фаза 2. Написание SKILL.md

Порядок: frontmatter → описание → контекст окружения → шаги →
шаблон вывода → память → тон → версионирование.

Не пиши весь скилл сразу — сначала только Шаг 1 и шаблон вывода,
запусти тест, потом добавляй остальное. Дешевле итерировать
на маленьком файле, чем переписывать большой.

Создай рядом `TESTING.md` — чеклист для этого конкретного скилла
(см. Фазу 3).

### Фаза 3. Тестирование (обязательно, не пропускать)

`TESTING.md` живёт рядом с `SKILL.md` в папке скилла.
Это артефакт репозитория, не личный список. Формат:

```markdown
# TESTING — ds-token-audit

## Триггеры
- [ ] «проверь токены Button» → скилл активировался, задал уточняющий вопрос
- [ ] «аудит токенов» → активировался
- [ ] Передан файл tokens.json → активировался

## Граничные случаи
- [ ] Пустой / невалидный файл токенов → понятная ошибка
- [ ] `.claude/intake-user` отсутствует → скилл спросил имя
- [ ] `skills/_shared/token-rules.md` отсутствует → предупредил, продолжил
- [ ] Figma MCP не подключён → предупредил, предложил ручной путь

## Формат вывода
- [ ] Отчёт строго по шаблону (все секции на месте)
- [ ] Секция без контента содержит «нет», а не пропущена

## Память
- [ ] Запись в `memory/<skill>/log.<имя>.json` создана
- [ ] git commit с правильным message
- [ ] git pull --rebase отработал без конфликтов
```

**Тест на онбординг:** попроси коллегу, который не участвовал
в написании, запустить скилл по инструкции из `README.md`.
Если не справился за 5 минут — скилл написан плохо.

### Фаза 4. Коммит в репозиторий

```bash
git add skills/<skill-name>/
git commit -m "feat(skills): add <skill-name> v1.0.0

Снимает: <рутина> (~X мин)
Платформы: web, ios, android
Триггеры: «фраза 1», «фраза 2», файл такого типа
Память: memory/<skill-name>/log.<имя>.json"
git push
```

Структура commit message не ради красоты — по ней через полгода
понятно, зачем скилл был добавлен.

### Фаза 5. Онбординг нового сотрудника

Инструкция на четыре строки. Если нужно больше — что-то не так с репо.

```
1. git clone <repo> (или git pull)
2. Создай .claude/intake-user — одна строка, фамилия латиницей: ivanov
3. Открой Claude Code в корне проекта
4. Напиши триггерную фразу нужного скилла
```

## Типичные ошибки


| Ошибка                                  | Почему плохо                               | Как правильно                                    |
| --------------------------------------- | ------------------------------------------ | ------------------------------------------------ |
| Слабый `description` без триггеров      | Скилл не активируется                      | Минимум 5 конкретных фраз                        |
