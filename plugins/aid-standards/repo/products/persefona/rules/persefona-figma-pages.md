# Страницы файлов Figma

> Статус: Draft · v0.14.0 · обновлено 2026-10-29

---

## 1. Назначение

Сейчас у каждого файла своя система: смешаны языки (`Buttons` и
`Оформление`), разделители бывают `---` и пробелом, значок ✅ стоит только
в файлах токенов, обложка называется `Thumbnail`, `Cover` или «Обложка ·
Changelog», архив — `Archive` и `_archive`, чейнжлог — `Changes`.
По имени страницы нельзя понять, можно ли брать её содержимое и кто сейчас
с ней работает.

Правило отвечает на три вопроса:

1. **Где искать** — у файла одна раскладка зон (§3).
2. **Как назвать** — одна грамматика имени и закрытый словарь (§4).
3. **Можно ли брать** — статус в имени страницы (§5) и путь страницы по
   флоу задачи (§7).

**Охват.** Файлы библиотек AID — токены, компоненты, иконки Rider, Driver и
Persefona (`figmaFiles` в `products/<id>/product.json`) — и страницы аудита
и сборки в них. Оформление файлов библиотек — зона Persefona (корневой
`CLAUDE.md`, «Роли и чаты»). Макеты продуктов (Handoff) — позже, отдельным
разделом. Исключение — страницы к PRD в файле макетов
продукта: аудит против PRD (§6.7) и идеи к PRD (§6.8), решения PD 2026-10-28.

**Латиница в именах** (ответ PD 2026-10-23) действует только для файлов
папки Figma библиотек AID — `638447836` (`products/registry.json`): токены,
компоненты и иконки Rider, Driver и Persefona. Файлы вне папки, в том числе
файлы дизайнеров со страницами Components Swapper, не переименовываются.
Порядок перехода — §10.3.

## 3. Зоны файла

Файл делится на пять зон. Порядок зон постоянный, между зонами —
разделитель Figma (пункт меню **Add divider**, имя `---`). Пустая зона
вместе со своим разделителем не создаётся. Исключение — зона 5: страница
`Thumbnail` есть в каждом файле, даже пустая (решение PD 2026-10-23).

| # | Зона | Страницы | Статус в имени |
|---|---|---|---|
| 1 | Служебное | `Cover` первой, затем `Mapping`, `Doc blocks` | нет |
| 2 | Библиотека | Опубликованное содержимое: токены, компоненты, иконки | нет или ⚠️ |
| 3 | В работе | Аудит, сборка, правка, предложения, `Drafts` | 🚧 или 👀 |
| 4 | Архив | `Archive` | нет |
| 5 | Миниатюра | `Thumbnail` — всегда последней | нет |

Пример — файл компонентов:

```
Cover
---
Badge
Button
TabBar
---
👀 Chip · audit
🚧 Search · construction
Drafts
---
Archive
---
Thumbnail
```

**Почему так.** Библиотеку чаще всего открывают, чтобы взять готовое,
поэтому она сразу под обложкой. Работа в процессе отделена разделителем
и значком: её не возьмут по ошибке.

## 4. Имя страницы

### 4.1 Грамматика

```
[статус ]<Объект>[ · <вид>]
```

- **Статус** — один значок из §5 или ничего. Других эмодзи в имени нет.
  Исключения — страницы к PRD в файле макетов: аудит
  `🔍 PRD audit · <Раздел>` (§6.7) и идеи `💡 PRD idea · <Сценарий>`
  (§6.8) (решения PD 2026-10-28).
- **Объект** — имя так, как оно записано в библиотеке, без перевода:
  компонент — как мастер, в единственном числе (`TabBar`, не `Tab Bar` и
  не `TabBars`; в Persefona — `Badge`); токены — вид токенов из §6.4;
  иконки — `Icons` или категория иконок.
- **Имя объекта не совпадает со служебным** (§4.3) и не содержит ` · `.
  Иначе переименовывается объект, а не страница: в Persefona `Обложка` →
  `HeaderPage`, `Таблица · было | стало` → `TableComparison`.
- **Вид** — только для зоны «В работе», строчными, из словаря §4.2.
- **Разделитель** — ` · ` (средняя точка с пробелами), как в
  `figma-library-workflow`. Двоеточия, слэши, скобки не используются.
- **Чего нет в имени:** версии, даты, номера задачи, логина. Номер задачи
  и исполнитель — в шапке страницы (§6.2), дата — в архиве (§7.3).

**Язык.** Имена — на латинице: страницы, секции, компоненты, свойства и
их значения, стили, переменные (ответ PD 2026-10-23, охват — §1). Объект
называется так же, как в коде: компонент — PascalCase
(`naming-conventions`), токен — как в коллекции. Кириллица остаётся в
содержимом: описания, тексты, подписи блоков, метки статуса в шапке
(«Принято», «В работе»). Служебную страницу от объекта отличает закрытый
список §4.3, а не язык.

### 4.2 Словарь вида

| Вид | Когда |
|---|---|
| `audit` | Аудит по `figma-library-workflow` §3.1 |
| `construction` | Сборка по `figma-library-workflow` §3.2, этап 6 (решение PD 2026-10-26; не `build`) |
| `update` | Развитие опубликованного объекта, если правка не идёт в ветке файла |
| `proposals` | Пачка «было / стало / почему» (`persefona-kit-improvement`) |

Новое слово вида — только правкой этого правила.

**Переход.** Слова `аудит` и `сборка` записаны в протоколе
`figma-library-workflow` §3.1–3.2 (зона Standards). `audit` и
`construction` действуют сейчас, не дожидаясь протокола (решения PD
2026-10-25 и 2026-10-26): новые страницы — сразу так, существующие
`· аудит` и `· сборка` переименовываются сейчас. `update` и `proposals` —
с мержа PR протокола Standards; до него новые страницы — `правка` и
`предложения`. Один цикл агенты ищут страницу по обоим словам.

### 4.3 Служебные страницы

Закрытый список. Других имён в зонах 1, 4 и 5 нет.

| Имя | Что на ней | Замечание |
|---|---|---|
| `Cover` | Шапка, паспорт и содержание файла (§6.1) | Всегда первая. Заменяет страницу `Обложка` |
| `Mapping` | Отчёт Token Comparator «значение → токен» | Значок не ставится. Пока PR #365 не слит — имя `Маппинг`, не переименовывать: плагин создаст вторую страницу. После мержа — `Mapping`. Если плагин создал её в конце файла — перенести в зону 1 |
| `Doc blocks` | Служебные блоки для страниц файла | Заменяет `Оформление`. Временная: уходит, когда файл подключит библиотеку Persefona |
| `Drafts` | Наброски без задачи | Зона 3. Заменяет `Черновики`, `Draft`, `Идеи`. Брать оттуда нельзя |
| `Archive` | Снятое и завершённое (§7.3) | Последняя перед `---` и `Thumbnail`. Заменяет `Архив`, `_archive` |
| `Thumbnail` | Обложка файла — миниатюра в списке файлов Figma: один фрейм, **Set as thumbnail** | Всегда последняя, перед ней `---`. Есть в каждом файле; пока обложки нет — пустая. Обложку делают последней, когда файл собран (решение PD 2026-10-23) |

Отдельной страницы чейнжлога нет: таблица стоит на странице своего
артефакта (§6.5). Страница `Changes` в файлах токенов Rider и Driver —
не чейнжлог: на ней датированные отчёты `Changes <дата>`, и Token Comparator
их не создаёт. Её не трогают, пока не ясно, чей это отчёт (§8, вопрос 8).

## 5. Статусы

Значок в начале имени. Отсутствие значка — норма: страница опубликована и
принята.

| Значок | Статус | Значит | Зона |
|---|---|---|---|
| — | Принято | Содержимое принято и входит в библиотеку; опубликована ли она — метка на обложке | 2 |
| 🔍 | Аудит против PRD | Только страница аудита макета против PRD (§6.7), всегда, пока она открыта; в шапке — «Смотреть и решать» и кого ждут. Знак вида страницы, а не этапа (решение PD 2026-10-28) | файл макетов |
| 💡 | Идеи к PRD | Только страница идей к сценарию PRD (§6.8), всегда. Знак вида страницы, а не этапа (решение PD 2026-10-28) | файл макетов |
| ⚠️ | Устарело | Ещё в библиотеке, в новые макеты не брать; на что заменить — в шапке | 2 |
| 🚧 | В работе | Сборка, правка или предложения — до публикации, на приёмке тоже: брать нельзя | 3 |
| 👀 | Смотреть и решать | Аудит и предаудит — всегда, с создания страницы до начала сборки. Кого ждут — в шапке | 3 |

**Почему без ✅.** Когда ✅ стоит на каждой странице, значок ничего не
сообщает, а 🚧 среди них теряется. Значок нужен только там, где на
странице что-то не так, как обычно.

**Почему аудит 👀, а не 🚧** (решение PD 2026-10-25, для всех продуктов AID:
Persefona, Rider, Driver). На странице аудита нет
компонента, брать с неё нечего: это документ для решений, его смотрят
куратор, дизайнер и PD. 🚧 остаётся там, где из файла можно взять
недоделанное, — у сборки, правки и предложений. Идёт ли ещё подготовка или
уже приёмка, говорит шапка: кого ждут. Если у предаудита есть страница, это
та же страница `<Компонент> · audit`, сразу с 👀.

**Сборка — всегда 🚧** (PD 2026-10-28: «у нас в стандартах должно быть
🚧»): с начала сборки до публикации, на приёмке тоже. 👀 у страницы
сборки не ставится; кого ждут — строкой в шапке.

**Аудит после начала сборки** (решение PD 2026-10-28). Отдельной страницы
аудита больше нет: аудит — секция на странице сборки (§7.1), значок
страницы — 🚧, как у сборки.

**Кто меняет.** Статус меняет тот, кто переводит этап: исполнитель ставит
👀 на аудит при создании страницы, 🚧 — на сборку, правку и
предложения; на приёмке и при правках значок не меняется, меняется
строка «кого ждут» в шапке (у страницы `· audit` — так же до начала
сборки; дальше аудит — секция на странице сборки, §7.1); публикация снимает
значок и переносит страницу в зону 2. Значок в имени и бейдж в шапке страницы
совпадают всегда.

Статусы пунктов внутри аудита («Ждёт решения», «Принято» и другие) — это
`figma-library-workflow` §3.1; статус страницы их не заменяет.

## 6. Навигация

### 6.1 Обложка

Первая страница файла. На ней:

- **шапка** — экземпляр `HeaderPage`: метки (опубликована ли
  библиотека, версия, тема), название и описание файла;
- **паспорт**: куратор, ссылки на Presentbook и `products/<id>/product.json`;
- **содержание**: все страницы зон 2 и 3 в порядке файла, у каждой —
  статус и гиперссылка на страницу.

Миниатюры файла на обложке нет: она на последней странице `Thumbnail`
(§4.3) — продукт, вид файла (токены, компоненты, иконки), статус
библиотеки. В содержание `Thumbnail` не входит.

Содержание обновляется вместе со списком страниц; пока нет скрипта (§9), —
руками.

### 6.2 Шапка страницы

Каждая страница зон 2 и 3 начинается с шапки — экземпляра компонента Kit
`HeaderPage` в левом верхнем углу первой секции. Если шапка уже есть
внутри витрины, вторая не ставится.

- заголовок шапки = имя страницы без значка;
- первая метка — статус, слово из столбца «Статус» §5: «Принято»,
  «Устарело», «В работе», «Смотреть и решать». Вид работы («Аудит»,
  «Сборка») — в имени страницы, не в метке статуса;
- для зоны 3 — метка с номером задачи и исполнителем, кого ждёт приёмка;
  в зоне 2 такой метки нет;
- для ⚠️ — на что заменить;
- ссылки: ← `Cover` (гиперссылка на шапку обложки), Presentbook, гайд.

Замена мастера `HeaderPage` и принятие обновления библиотеки сбрасывают
гиперссылки в шапке: в содержании и у «← Cover» (#391). После них ссылки
проверяют и ставят заново.

### 6.3 Внутри страницы

- Содержимое — в секциях Figma (Section). Имя секции — по той же
  грамматике без статуса: объект или блок аудита по §3.1 протокола.
- Порядок чтения — сверху вниз, затем слева направо; вне секций на
  странице ничего нет.
- Ссылка на другое место файла — гиперссылкой на узел, не текстом
  «см. страницу X».
- **Фон секции — `bg-surface-main`** (белый). Карточки внутри
  (`IslandBlock`) — тоже `bg-surface-main`, их отделяет рамка
  `line-default`. `bg-surface-muted` — только для панелей и областей
  внутри карточки. Действует на всех служебных страницах Persefona, Rider
  и Driver: гайды, аудиты, витрины токенов и иконок, чейнжлоги (указание
  PD 2026-10-28: «Это коснется общих правил оформления, а не только этого
  пейджа»).
- **Блоки не выходят за секцию, секции не налезают друг на друга.**
  Вырос блок — секцию подгоняют сразу, в той же правке: увеличивают
  размер и сдвигают соседние секции так, чтобы между ними остался
  прежний зазор (80). Проверка — геометрией: ни один дочерний узел не
  выходит за рамку секции, рамки секций не пересекаются (указание PD
  2026-10-29: «если вылезают блоки за границы секций, секции нужно сразу
  подгонять, нельзя чтобы налезали блоки и секции друг на друга»).

### 6.4 Порядок страниц в зоне 2

| Файл | Порядок |
|---|---|
| Токены | Сначала, если в файле есть и токены, и компоненты. Порядок слоёв: цвет, градиенты, типографика, тени, стекло, отступы, радиусы. Имя — на языке библиотеки: Rider и Driver — `Colors`, `Gradients`, `Typography`, `Shadows`, `Glass`, `Space`, `Radius`; Persefona — `Colors`, `Space and Radius`, `Typography`, `Shadows`. Core и Semantic — две витрины-секции на одной странице, как в `Colors` у Rider и Driver (приёмка #367) |
| Компоненты | По алфавиту имени (значок ⚠️ не учитывается) |
| Иконки | `Icons` одной страницей или категории по алфавиту |

### 6.5 Таблица чейнжлога

Указание PD 2026-10-23: на каждой странице, где это нужно, ведётся своя
таблица чейнжлога. Что записывать и в каком формате, решают общие
стандарты (`changelog-guide`, зона Standards). Это правило отвечает за
другое: где таблица стоит и как выглядит в файлах, которые оформляет
Persefona. Это файл Kit Persefona и файлы библиотек Rider и Driver.
Соблюдение проверяет Standards · Persefona при приёмке (§9).

**На каких страницах.** На каждой странице зоны 2, где лежит
версионируемый артефакт: коллекция токенов, стиль (тени, стекло,
градиенты), набор иконок, компонент. Одна таблица — это один артефакт,
один JSON с `figmaTable` и одна страница Presentbook (`changelog-guide`
§3). Если артефактов на странице два, таблиц тоже две: в Rider на
`Typography` их две.

**Где таблицы нет.** На служебных страницах (зоны 1 и 4) и в зоне 3: в
аудите, сборке, правке, предложениях и черновиках. Такая работа записи в
чейнжлог не требует (`changelog-guide` §4). Исключение — гайд компонента
(ниже, «Гайд компонента»). Секция аудита на странице сборки (§7.1)
таблицы не имеет. Запись появляется на
публикации, когда страница переходит в зону 2 (§7.1).

**Место на странице.** Таблица — всегда отдельная секция Figma
`Changelog · <Артефакт>` справа от секции своего артефакта (витрины или
гайда), верхним краем по верху, отступ 80; в одну секцию с артефактом
она не входит (решение PD 2026-10-26: «чейнжлоги ВСЕГДА должны быть
отдельной секцией или фреймом рядом с гайдом, а не объединяться в единую
секцию с ним»). `<Артефакт>` — имя секции артефакта, которое совпадает
с именем страницы или витрины: `Colors` и `Changelog · Colors`. Если
артефактов на странице два, пар секций тоже две (`Typography`,
`Typography Outstanding`). Образец — Rider Tokens после AID-64 (#465,
#466, #468). id таблицы при переносе в секцию не меняется.

**Гайд компонента** (решение PD 2026-10-22: changelog у каждого
компонента; указание PD 2026-10-24: «в спеках нужно чейнжлог выносить
отдельной секцией, а не в теле гайда (как сейчас в токенах райдера
сделано, например)»). Таблица — не блок гайда, а отдельная секция Figma
`Changelog · <Компонент>` справа от секции гайда, верхним краем по верху
гайда, с тем же отступом, что между секциями страницы. Образец — страницы
файла токенов Rider. В гайде блока чейнжлога нет. В содержании шапки —
последний пункт-ссылка «Changelog →» на секцию. Секция есть с начала
сборки, то есть уже в зоне 3, с одной строкой «Не опубликовано»: это
заготовка, а не запись (`changelog-guide` §4). При переходе страницы в
зону 2 таблицу не переносят: её id и `figmaTable` остаются прежними.
Таблицу, которая уже стоит блоком в гайде, перемещают в секцию, а не
собирают заново (ниже, «Не пересоздавать»).

**Заголовок и имя слоя.** Заголовок таблицы совпадает с `artifact` в
JSON, например `Rider Space`. Имя самого фрейма плагину не важно, его ищут
по id. Существующие фреймы `CHANGELOG` не переименовываются.

**Состав.** Колонки, порядок строк и запись «Не опубликовано» — по
`changelog-guide` §5 «Таблица в Figma». Имена слоёв `Changelog Table Body`,
`Changes Row`, `__Changelog Badge` и `{separator}` — контракт Token
Comparator. Их не переименовывают, в том числе при переходе на латиницу, и
не меняют их вложенность.

**Пустой таблицы не бывает.** Плагин добавляет запись, копируя первую
строку таблицы. Поэтому у артефакта без опубликованной версии в таблице
одна строка «Не опубликовано».

**Не пересоздавать.** Копия таблицы получает новый id, и `figmaTable`
перестаёт на неё указывать. Таблицу только перемещают. После переноса на
другую страницу её id сверяют с `figmaTable`.

**Вид.** Блоки Kit Persefona. Таблица вставляется из образца Kit
`TableChangelog` (§8, вопрос 7). Сразу после вставки экземпляр отвязывают
(**Detach instance**): корень, тело, строки и ячейка изменений становятся
фреймами, а части внутри остаются экземплярами Kit. Пока образца нет,
таблицу собирают фреймом, как в Rider, но только из токенов и стилей Kit.

| Слой | Тип | Почему |
|---|---|---|
| Корень таблицы | фрейм | Плагин ищет по `figmaTable` только фрейм |
| `Changelog Table Body` | фрейм | Плагин вставляет в него строки |
| `Changes Row` | фрейм | Экземпляры строк плагин пропускает |
| Ячейка изменений (вторая в строке) | фрейм | Плагин удаляет и добавляет в ней слои |
| Бейдж, слой `__Changelog Badge` | экземпляр Kit | Первое свойство-вариант — `Added` / `Removed` / `Edited`, подпись — текстовым слоем |
| Версия, дата, автор | фрейм или экземпляр Kit | Плагин меняет только текст |
| Шапка таблицы, заголовки колонок | экземпляр Kit | Плагин их не трогает |

**Уже сделанные таблицы** (указание PD 2026-10-25: «такие чейнжлоги везде
(в персефоне файлах, либах драйвера и райдера) тоже на стили и компоненты
персефоны переехали (уже сделанные и все в будущем)»). Каждую таблицу в
файлах Persefona, Rider и Driver приводят к виду Kit **на месте**:
- фреймы корня, тела, строк и ячейки изменений остаются теми же узлами:
  меняются только заливки, обводки, отступы, радиусы и текстовые стили — на
  переменные и стили Kit;
- бейдж заменяют на `BadgeChangelog` через **Swap instance**, имя слоя
  `__Changelog Badge` и вариант сохраняют;
- шапку таблицы и заголовки колонок заменяют экземплярами Kit;
- слои-контракт (выше, «Состав») не переименовывают и не перекладывают;
- после перевода сверяют id корня с `figmaTable` и прогоняют
  `writeUnpublishedRow` на одной таблице файла.
- если таблицу только сдвинули (меняется позиция фрейма, а слои и id те же),
  прогон не нужен: плагин ищет таблицу по id (#463).

Таблицу не пересобирают из образца: копия получает новый id (выше, «Не
пересоздавать»). Файлы Rider и Driver для этого подключают библиотеки
Persefona Tokens и Components.

### 6.6 Аудит и предаудит

Указание PD 2026-10-25: предаудиты и аудиты, «уже сделанные и все
будущие», — на стилях и компонентах Persefona. Это касается файлов
Persefona, Rider и Driver, страниц в работе (зона 3) и секций аудита в
`Archive` (§7.3).

**Что из Kit.** Шапка страницы — `HeaderPage`, одна на страницу;
обложка секции аудита внутри страницы — не шапка страницы, а блок.
Заголовки секций — `HeaderSection`; карточки блоков, включая обложку
секции, — `IslandBlock`; таблицы — `TableCell` во фрейме на переменных Kit
с видом `TableComparison` (`TableComparison` — образец на четыре строки, а
не контейнер); статусы пунктов — `Badge`; пометки — `Banner`; схемы
анатомии — `TagMarker`. Всё остальное — только переменные и стили Kit.
Сырых значений и старой служебной палитры (`neutral-x`, `neutral-y`) на
странице нет.

**Сцена и оболочка.** Переменные и стили продукта (Rider, Driver) —
только внутри сцены: фон сцены и всё, что лежит на нём. Подписи и тексты
вне фона сцены — на стилях и переменных Kit.

**Ссылки** в оболочке — `text-accent-vivid` и стрелка `→` перед текстом.
Подчёркивание не нужно: стрелка отличает ссылку не только цветом.

**Чего в Kit нет.** Если блоку аудита не хватает компонента Kit, его не
собирают молча: сначала lookup по Kit, потом предложение через
`component-gate` на приёмку Standards · Persefona. До приёмки этот блок
собирают фреймом из переменных и стилей Kit.

**Что не меняется.** Состав и порядок блоков, тексты, решения и статусы
пунктов — по `figma-library-workflow` §3.1 (зона Standards). При переводе
сделанного аудита меняется только вид. Если по пути находится ошибка в
содержании, её отмечают пометкой для куратора, а не правят молча.

**Порядок перевода сделанных.** Сначала страницы в работе и секции аудита на страницах сборки (зона 3), потом
секции в `Archive`. В Rider и Driver куратор файла узнаёт до начала работ.
Каждый перевод проверяют снимками «до» и «после» и сверкой текста: текст
должен совпасть один в один.

### 6.7 Аудит макета против PRD

Указание PD 2026-10-28: такие аудиты «с этого момента по одним и тем же
стандартам». Аудит сверяет макеты раздела продукта с его PRD и собирает
расхождения в одну страницу, на которую дизайнер продукта отвечает.
Аудит показывает и проблемы самих PRD (блок 4, решение PD 2026-10-28):
на них отвечает продакт. Содержание аудита ведёт Product Logic,
оформление — это правило, ответы даёт дизайнер продукта, по блоку 4 —
продакт.

**Охват.** Файл макетов продукта, не файл библиотеки. Раскладка зон §3 и
латиница §4.1 к остальным страницам такого файла не применяются: их имена
остаются как есть. Для этой страницы действуют своё имя (ниже, решение
PD 2026-10-28), значок 🔍 (§5), шапка §6.2 (как в зоне 3), секции §6.3, оформление на Kit
§6.6 и архив §7.3.

**Общий стандарт.** Общих стандартов AID на аудит против PRD нет:
`figma-library-workflow` §3.1 — про компоненты библиотек. Это правило от
общих стандартов не отходит: статусы пунктов — из §3.1 протокола. Если
Standards заведёт общий протокол аудита против PRD, правило будет
ссылаться на него; расхождения с ним решаются через Standards.

#### Имя и место

```
🔍 PRD audit · <Раздел>
```

Решение PD 2026-10-28 (ответ на вопрос 9 §8). Это исключение из
грамматики §4.1: тип страницы `PRD audit` стоит первым, раздел — после
` · `. Других страниц с таким порядком нет.

- **Значок** — всегда 🔍 (§5): знак этого вида страницы. Страница —
  документ для решений, брать с неё нечего; 👀 и 🚧 не ставятся.
- **`PRD audit`** — постоянная часть имени, латиницей, всегда так.
- **Раздел** — экран или раздел так, как он назван в PRD. ` · ` внутри не
  ставится; язык — как в PRD.
- **Место** — в конце файла, после разделителя `---`, отделяющего её от
  страниц макетов; если в файле есть `Archive` или `Thumbnail` — перед
  ними.
- Один раздел PRD — одна открытая страница. Повторный аудит, пока
  страница открыта, — новые пункты на ней же, со следующими номерами.
- Значок не меняется, пока страница открыта. Когда у всех пунктов статус
  «Принято» или «Снято», страница уходит секцией в `Archive` (§7.3), без
  значка: `PRD audit · <Раздел> · ГГГГ-ММ-ДД`; причину и номер задачи
  в начале секции пишет тот, кто ведёт аудит. Если `Archive` в файле нет —
  он заводится в конце файла, перед `Thumbnail`, если она есть.
- Аудит того же раздела после архива — новая страница, номера с начала:
  номер уникален в пределах страницы, а архивная секция отличается датой.

#### Раскладка страницы

Сверху вниз, одной колонкой, в секциях Figma (§6.3): шапка и легенда —
первая секция, каждый блок — своя секция с именем блока. Фон секций —
белый, по §6.3.

| # | Часть | Из Kit | Что внутри |
|---|---|---|---|
| 1 | Шапка | `HeaderPage` | Заголовок — имя страницы без значка. Подзаголовок: источник — PRD (название, дата или версия), страница макетов, кто собрал аудит. Метки шапки: «Смотреть и решать», номер задачи, кого ждут. Ссылки: → страница макетов, → PRD (если у PRD есть ссылка) |
| 2 | Легенда | `IslandBlock` | Строка на каждую метку блока: `Badge` и объяснение `body-m`. Последней строкой — про клоны: что это копии, над каждой ссылка на оригинал, оригиналы не менялись |
| 3 | Блок 1 «Figma расходится с PRD» | `HeaderSection`, пункты | В PRD сказано одно, в макете — другое |
| 4 | Блок 2 «Есть в Figma, нет в PRD» | `HeaderSection`, пункты | Поведение или состояние в макетах, которого PRD не описывает |
| 5 | Блок 3 «Есть в PRD, нет в макетах» | `HeaderSection`, пункты без клонов | Норма PRD, для которой макета нет |
| 6 | Блок 4 «Проблемы PRD» | `HeaderSection`, пункты; клоны — по желанию | Проблема в самих PRD: противоречие двух PRD, расхождение текста и картинок внутри PRD, пробел — норма ссылается на то, чего нет |

Блок без находок не убирается: в нём `Banner` «Не найдено», чтобы было
видно, что проверка была.

Метка блока — `Badge`, тон по смыслу; точный тон Designer · Persefona
берёт из набора `Tone` Kit на приёмку:

| Блок | Метка | Тон |
|---|---|---|
| 1 | Расхождение | Warning |
| 2 | Нет в PRD | Info |
| 3 | Нет в макетах | Neutral |
| 4 | Проблема PRD | Vivid Soft |

Блок 4 — не Warning: блок 1 спрашивает дизайнера, блок 4 — продакта, и
метки не должны путаться. Error не берётся: проблема PRD — вопрос на
решение, а не ошибка.

#### Пункт

Карточка `IslandBlock`: слева описание фиксированной ширины, справа —
клоны макетов в ряд. В блоке 3 клонов и поля «Ссылки» нет: оригинала
нет. В блоке 4 клоны и «Ссылки» — по желанию: когда проблема видна на
макете. Имя фрейма карточки — `Пункт <номер>`.

Описание, сверху вниз:

1. **Номер, метка и статус** — номер `<блок>.<n>`, `Badge` метки блока и
   `Badge` статуса пункта. Статусы — из `figma-library-workflow` §3.1:
   «Ждёт дизайнера» при создании; «Ждёт решения», если дизайнер ответил,
   но вопрос ушёл продакту или PD и ответа от них нет (хозяин — в
   «Решении»); «Принято» — решено; «Снято» — отпал. «Согласовано
   куратором» здесь не используется: куратора у макета продукта нет.
   Пункт блока 4 создаётся со статусом «Ждёт решения» и сразу с полем
   «Решение»: хозяин — продакт (пока продакт — PD).
2. **Заголовок** — `heading-s`, суть одной строкой.
3. **Поля** — подпись `body-s` `text-secondary`, под ней текст `body-m`:
   - «PRD» — норма и её номер, как в PRD (блоки 1 и 3); в блоке 4 — одна
     или несколько норм, у каждой название PRD и номер нормы;
   - «Макет» — что в макете (блоки 1 и 2; в блоке 4 — по желанию);
   - «Комментарий AID» — суть и вопрос дизайнеру; в блоке 4 — вид
     проблемы (противоречие, текст ≠ картинка, пробел) и вопрос продакту;
   - «Ссылки» — гиперссылки на оригиналы в файле, вид
     `→ <Страница> › <Секция> › <Фрейм>`, цвет `text-accent-vivid` (§6.6).
     Если по пункту есть идея на странице `💡 PRD idea` (§6.8), сюда же
     ставится ссылка на её секцию: `→ 💡 PRD idea · <Сценарий> › <Идея>`.
     Ссылка ведёт в обе стороны: в идее — «Откуда идея», в пункте — эта
     строка (указание PD 2026-10-29: «В аудите в блоке соответствующем
     тоже нужно добавлять ссылку, если есть раздел идеи по этой задаче»);
   - «Решение» — появляется, когда по пункту есть итог или хозяин
     решения; до того поля нет.

**Клоны макетов** — копии фреймов оригинала, не экземпляры и не перенос:
оригинал не меняется, клон фиксирует макет на дату аудита и не правится.
Над каждым клоном — подпись-ссылка на его оригинал (`body-s`,
`text-accent-vivid`, `→`).
Клон — сцена: внутри стили и переменные продукта, вокруг — только Kit
(§6.6 «Сцена и оболочка»).

**Место пункта блока 4.** Пункт заводится на странице аудита того
раздела, который проблема задевает. Если PRD несколько — на странице
главного раздела, а в «Комментарии AID» — ссылки на остальные разделы;
на их страницах пункт не дублируется.

#### Номера

Номер пункта неизменяем: по нему Product Logic сопоставляет ответы
дизайнера.

- Номер даётся при создании пункта: следующий свободный в своём блоке.
- Пункты не перенумеровываются — ни при удалении, ни при перестановке,
  ни при повторном аудите. Номер не переиспользуется.
- Снятый пункт не удаляется: он остаётся со статусом «Снято» и причиной в
  «Комментарии AID», пока страница не уйдёт в архив.
- Пункт не переносится между блоками. Если блок выбран неверно — пункт
  снимается (статус «Снято», причина — «перенесён в <номер>»), в нужном
  блоке заводится новый со ссылкой на старый номер.
- Номер стоит в тексте карточки и в имени её фрейма (`Пункт 1.3`);
  имя фрейма не переименовывается.

#### Ответ дизайнера и продакта

Дизайнер продукта отвечает комментарием Figma на пункты блоков 1–3,
продакт — на пункты блока 4 (`4.n`), по тем же правилам:

- комментарий крепится к фрейму `Пункт <номер>` (точка — на номере), не
  к клону и не к полю страницы;
- первая строка комментария — номер пункта (`1.3`);
- один пункт — одна ветка комментариев; уточнения — в той же ветке;
- текст пунктов на странице дизайнер не правит; макеты правит на
  страницах макетов, не в клонах. Продакт PRD правит в самом PRD, не на
  странице.

Итог по пункту переносит на страницу тот, кто ведёт аудит (Product
Logic): меняет статус пункта и заполняет поле «Решение». Когда у всех
пунктов статус «Принято» или «Снято», страница уходит в архив.

#### Что не меняется при оформлении

Перевод готовой страницы аудита на Kit меняет только вид: тексты
пунктов, номера и имена фреймов `Пункт <номер>`, клоны и страницы
макетов остаются как были. Добавляются только части Kit, которых на
странице не было (бейдж статуса), — со значением по факту: «Ждёт
дизайнера», пока ответа нет. Проверка — снимки «до» и «после» и сверка
текста один в один (§6.6).

### 6.8 Идеи к PRD

Решение PD 2026-10-28: страницы идей к PRD «теперь всегда называть по
структуре "💡 PRD idea · сценарий"». Указание PD 2026-10-28: оформлять
«только по ее стилям» — стилям Kit Persefona.

Страница идей — предложение Product Logic, как может работать сценарий,
которого нет в макетах или в PRD: экраны-клоны, переходы, развилки,
вопросы дизайнеру и наброски того, для чего компонента нет. Это не макет:
финал — за дизайнером продукта. Содержание ведёт Product Logic,
оформление — это правило.

**Охват** — как у §6.7: файл макетов продукта; раскладка зон §3 и латиница
§4.1 к остальным страницам файла не применяются. Действуют имя (ниже),
шапка §6.2, секции и белый фон §6.3, сцена и оболочка §6.6, архив §7.3.

#### Имя и место

```
💡 PRD idea · <Сценарий>
```

Исключение из грамматики §4.1, как `PRD audit`: тип страницы первым,
сценарий — после ` · `.

- **Значок** — всегда 💡 (§5); 👀 и 🚧 не ставятся.
- **`PRD idea`** — постоянная часть имени, латиницей, единственное число,
  всегда так.
- **Сценарий** — так, как он назван в PRD; ` · ` внутри не ставится; язык —
  как в PRD. Аудит и идеи к одному месту PRD называются одинаково:
  `🔍 PRD audit · Главная` и `💡 PRD idea · Главная`.
- **Место** — в конце файла, после `---`, рядом со страницей
  `🔍 PRD audit` того же сценария (сразу после неё, если она есть); перед
  `Archive` и `Thumbnail`, если они есть.
- Один сценарий — одна страница идей; каждая идея — своя секция.
- Прежние имена (`💡 Идеи · <Сценарий>`, `Идеи · <Сценарий>`)
  переименовываются; id страницы и содержимое не меняются.
- Идею дизайнер перенёс в макеты или она снята — её секция уходит в
  `Archive` (§7.3) с датой; причину и номер задачи в начале секции пишет
  Product Logic. Пустая страница идей удаляется.

#### Раскладка секции идеи

Сверху вниз, фон секции белый (§6.3).

| # | Часть | Из Kit | Что внутри |

| 1 | Шапка | `HeaderPage` | Заголовок — имя идеи. Подзаголовок — одна фраза: что за идея. Основание в подзаголовок и в «How to Read» не пишется (строка 2). Метки: «Идея, не макет» · Neutral первой, номер задачи, кого ждут |

| 3 | Схема | фрейм на поле секции, фон `bg-surface-main` | Экраны-клоны, переходы, развилки, вопросы, наброски |

**Основание** (требование PD 2026-10-29, через Product Logic: «В идеях

1. **Откуда идея** — первой строкой ссылка на пункт аудита, из которого

Содержание блока ведёт Product Logic, вид — это правило. Отдельный

**Экран.** Клон экрана продукта — сцена (§6.6), не правится. Под ним:

**Развилка** — ромб: заливка `bg-surface-main`, контур

**Аудит переезжает на страницу сборки** (решение PD 2026-10-28, через
Designer · Persefona, дословно: «если мы создаем пейдж сборки, то пейдж аудита нам не нужен (аудит переносится рядышком на пейдж сборки)»). Протокол, этап 6,

- **Когда.** С созданием страницы `🚧 TabBar · construction` (этап 6).
  До этого, на этапах 2–5, аудит живёт на `👀 TabBar · audit`.
- **Как.** Секции аудита **перемещаются**, а не копируются: id узлов
  сохраняются, и на них по-прежнему ведут ссылки из шапок, PR и
  комментарии Figma. На странице сборки аудит — одна секция
  `TabBar · audit` справа от секций сборки (§6.3: имя без статуса,
  латиницей). Секции блоков вкладываются в неё (Figma допускает
  секцию в секции) с прежними именами по §6.3, порядок блоков — как был.
- **Страница аудита.** После сверки по §6.6 — на новом месте все блоки,
  число узлов и тексты совпадают со снимком «до» — пустую страницу `· audit`

- **Публикация.** Секция `TabBar · audit` уходит в `Archive` (§7.3); на

странице сборки.

- Правка опубликованного — в ветке файла или страницей
  `🚧 TabBar · update` в зоне 3; опубликованная `TabBar` остаётся без

`<имя> · <вид> · ГГГГ-ММ-ДД`, например `TabBar · audit · 2026-10-23`;

Нынешний файл `YDjPxFrW1yXqm9RzBGQXuc` стал `Persefona Tokens` (ответ 2а):

вставить после публикации: так ключ сохраняется и экземпляры у потребителей
не теряются.

**Что где запрещено.**

- В Components — своих переменных и стилей нет, все привязки ведут в
  `Persefona Tokens`.
- В Tokens — главных компонентов нет, только экземпляры из
  `Persefona Components` (витрины, шапки, таблицы чейнжлога).
- В Icons — у иконок (главных компонентов) привязок к переменным нет, как
  у Driver (§9.1). Служебные страницы (`Cover`, `Archive`, `Thumbnail`) —
  исключение: шапка `HeaderPage` на `Cover` обязательна (§6.1) и берёт
  переменные Tokens через Components. Это не опубликованные ассеты, и
  потребители Icons от Tokens не зависят.

**Взаимная зависимость** (оговорка `internal`, §9.1). Tokens берёт
экземпляры из Components, Components — переменные и стили из Tokens.
Витрины токенов строятся из компонентов Kit (ответ 1а): так же Kit будут
брать файлы Rider и Driver. Страницы с витринами — не опубликованные
ассеты, поэтому повторная публикация Tokens ради витрин не нужна.

**Порядок публикации.**

| Что изменилось | Порядок |
|---|---|
| Токен или стиль | 1) опубликовать Tokens → 2) в Components принять обновление, проверить вид, опубликовать Components → 3) в Tokens принять обновление компонентов (витрины) |
| Компонент | 1) опубликовать Components → 2) в Tokens принять обновление; Tokens не публиковать, если в нём не менялись переменные и стили |
| Новый компонент на новом токене | Сначала токен (строка 1, шаги 1–2), потом компонент (строка 2) |
| Иконка | Опубликовать Icons → принять обновление в Components |

Каждый шаг — после приёмки по своему гейту (token-change-gate,
component-gate). Публикацию делает человек в интерфейсе Figma (MCP её не
выполняет): PD или куратор-человек. Версия Kit одна на продукт, чейнжлог —
у каждого артефакта свой (§6.5): изменение токена и компонента, которое
его использует, — две записи в двух файлах.

**Ссылки из репозитория.**

- `figma.fileKey` в pending компонентов — ключ `Persefona Components`, в
  pending токенов — `Persefona Tokens`; node id — по файлу, где лежит
  артефакт.
- `figmaTable` чейнжлога — в файле артефакта: таблица токена — в Tokens,
  компонента — в Components.
- Token Comparator видит Persefona двумя библиотеками

стилей, в Tokens 0 главных компонентов; число экземпляров по каждому
компоненту и переопределения совпадают со снимком «до»; экземпляров без
